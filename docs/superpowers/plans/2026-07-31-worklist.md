## 2. 🆕 날짜 기준 통일 — 전부 KST 자정 (B3 와 같은 배치)

### 결정과 근거
**목표는 “안 헷갈리기”이고, 자정만이 그걸 달성한다.** “전부 10시”는 **달성 불가능**하다 —
제품 규칙(연애 일일 턴)을 10시로 바꾸면 유저 영향이 발생하므로 못 바꾸고, 그러면 2기준이 계속 공존한다.

**추가 이득**: 외부 데이터와 대조가 된다. Meta 광고 리포트·토스 정산·GA 가 전부 자정 기준이다.
(2026-07-30 판독에서 광고비와 가입을 나란히 놓으려고 자정으로 다시 맞춰야 했던 것이 이 문제였다.)

### 실측 비용 (2026-07-30, prod)
| 항목 | 자정 | 10시 롤오버 |
|---|---|---|
| 2일 이상 방문자 | 7명 | 7명 (동일) |
| 그 기준 탓에 방문일이 늘어난 사람 | **1명** | **3명** |
| 자정 걸침 세션 | **1건** | — |

→ **왜곡 1명.** 10시 롤오버가 도입된 이유(트래픽 피크가 22~2시라 밤 세션이 갈리는 것 방지)는
원리상 맞지만, 세션이 짧아 **실제로 자정을 걸치는 사람이 1명뿐**이다.

### 🆕 방문일은 **세션 시작 시점**으로 귀속한다 (2026-07-30 사용자 제안 → 채택)

**이게 “자정 vs 10시” 논쟁을 원천 해소한다.** 10시 롤오버가 존재하는 유일한 이유가 “밤 세션이 두 날로
갈리는 것 방지”였는데, 세션 시작 귀속이 그걸 직접·정확하게 해결한다. 그러면 자정의 장점(제품 규칙 일치 +
외부 대조)만 남고 반대 근거가 사라진다.

**정의**: 같은 `anon_id` 안에서 **30분 이상 공백이면 새 세션**. 방문일 = 그 세션의 **첫 이벤트 시각**의 KST 자정 날짜.

**임계 30분의 근거 (실측 n=301)**: 세션 평균 4분 · p90 12.4분 → 30분은 p90 보다 넉넉히 커서 진짜 세션을
쪼개지 않고, 30분 이상 벌어진 방문은 실제로 별개 방문이다. 자정 걸침 세션 **0.33%(1건)**.
⚠️ “평균 4분”을 체류시간으로 읽지 말 것 — 대화 중엔 라우트 이동이 없어 PV 가 안 찍힌다(SPA). 실제 체류는 더 길다.
다만 자정 걸침 판정에는 영향 없다(갈림은 자정 양쪽에 PV 가 찍혀야 발생).

**실측 효과 — 재방문 실인원 (재방문/UV)**

| 날짜 | A 페이지뷰(자정) | B 페이지뷰(10시)=현행 | **C 세션시작(자정)=채택** |
|---|---|---|---|
| 07-27 | 1 / 52 | **3** / 54 | 1 / 52 |
| 07-28 | 2 / 49 | **3** / 46 | 2 / 49 |
| 07-29 | 2 / 26 | 1 / 27 | **1** / 25 |
| 07-30 | 1 / 38 | 1 / 26 | 1 / 38 |

→ C 가 A 와 다른 건 딱 한 칸(07-29). **현행 B(10시)가 오히려 왜곡이 가장 크다** — 07-27·28 에 재방문자를 부풀린다.

**적용 범위**: `admin_traffic_visitor_mix` RPC 만. **PV/UV 추세는 페이지뷰 기준 유지**(PV 는 정의상 페이지뷰 수).
구현 = window function 2개(세션 경계 판정 + 누적합) ~20줄. 자정 전환 마이그레이션과 같은 배치.

```sql
-- 세션 경계 → 세션 시작일
with ev as (
  select anon_id, created_at,
         case when lag(created_at) over (partition by anon_id order by created_at) is null
                or created_at - lag(created_at) over (partition by anon_id order by created_at)
                   > interval '30 minutes'   -- SESSION_GAP
              then 1 else 0 end as newsess
  from page_views where is_bot = false and anon_id is not null
    and (user_id is null or user_id <> all(p_exclude))
), sess as (
  select anon_id, created_at,
         sum(newsess) over (partition by anon_id order by created_at) as sno from ev
), visit_days as (
  select distinct anon_id,
         ((min(created_at) at time zone 'UTC' + interval '9 hours')::date) as bucket
  from sess group by anon_id, sno
)
-- 이후 기존 lag(bucket) 3분할 로직 그대로
```

⚠️ **`SESSION_GAP` 30분은 새 튜너블이다.** SQL 주석에 근거(p90 12.4분)를 남기고, 바꿀 땐 위 표를 다시 뜰 것.
**감시 지표**: `cycle-snapshot-a-retention.sql` 에 “자정 걸침 세션 수 / 전체 세션”을 추가한다 —
지금 0.33% 인데 세션이 길어지면 오르고, 그때는 세션 귀속의 이득이 커진다(전환이 아니라 이미 적용돼 있으니 관측용).

전부 **메커니즘 지표**였다(연애 첫 발화 6%→83%, 회피 상용구 소멸, 마커 100%) ②“6개 변경 중첩” 재발 방지의
답은 달력 동결이 아니라 **변경마다 태깅 + 각자의 메커니즘 지표로 판정**이다 ③기다림의 정보 가치가
음수인 경우가 있다(rel 소재는 표본이 9→15 명이 될 뿐).

**남긴 규율 딱 2개**:
1. 같은 지표를 때리는 변경 2개를 같은 주에 겹치지 않기 — 특히 **무료 체험권 배포일에 다른 퍼널 변경 금지**
2. 배포마다 날짜·코호트 태그, 판정은 **그 변경의 메커니즘 지표**로

d7(8/2)·d14(8/9) 스냅샷은 계속 돌린다. 단 **게이트가 아니라 관측**이다.

## 7. `rel` 광고세트 — 삭제하지 말고 OFF 유지 (판단 근거)

**결론: 일시중지만. 삭제 금지.** 삭제의 유일한 이득은 화면 정리인데 대가가 비가역이다.

| | OFF 유지 | 삭제 |
|---|---|---|
| 지출 | ₩0 (동일) | ₩0 |
| 학습 이력 | 보존 | **영구 소멸** |
| 되돌리기 비용 | 토글 1번 | 세팅 재입력 + 학습 단계 재진입 |
| 관리 화면 | 비활성 항목 1개 남음 | 깔끔 |

1. **우리 판정이 아직 미완이다.** ROAS 0.08 은 명백하지만 **유입 9명 · 관측 5일**이고, 그 5일이 예산 축소
   구간과 겹쳤다. "영구 폐기" 근거로는 얇다. 소재가 나쁜 건지 *지면·타겟*이 나쁜 건지도 안 갈렸다.
2. **다시 켤 시나리오가 실재한다** — E6(연애 시뮬)이 나오면 "그 사람" 축 소재가 다시 유효해진다.
   그때 학습 이력이 있는 세트를 되살리는 게 새로 만드는 것보다 싸다.
3. **귀속 연속성** — `ad_spend.creative_key` ↔ `user_acquisition.utm_content` 조인이 이름에 의존한다.
   삭제 후 재생성 때 이름이 달라지면 과거·미래 데이터가 갈린다.
4. **비활성 세트가 계정 성과를 해치지는 않는다** — 일시중지 오브젝트에 알고리즘 페널티는 없다.
   (⚠️ 단 **소재가 '거부됨' 상태라면** 계정 품질에 영향이 있을 수 있다. 콘솔에서 거부 표시를 확인하고,
   거부된 소재가 있으면 그 **소재만** 지우고 세트는 남길 것.)

**권장 조치**: 세트 이름 앞에 상태를 박아둔다 — 예 `[보류 2026-07-30 ROAS0.08] relationship`.
반년 뒤에 왜 꺼져 있는지 콘솔만 보고 알 수 있다.
