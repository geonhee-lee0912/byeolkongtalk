# 앱 알림 단계 2 — 광고 동의 장치 Implementation Plan

> 운영자 사전 허락(2026-11-08): 이 계획은 승인을 기다리지 않고 바로 구현한다. 설계에 없는 결정은 `HANDOFF.md` "결정 필요"에 적고, 그 결정에 안 걸리는 부분부터 진행한다.

**Goal:** 광고 알림을 보내도 되는 사람·시각·횟수를 한 곳(순수 판정 함수)에서 정하고, 광고 수신 동의를 받고·기록하고·통지하고·철회받는 장치를 만든다. 단계 3·4 의 광고 알림은 이 장치 위에서만 나간다.

**Spec:** `docs/superpowers/specs/2026-11-06-앱-알림-design.md` §2·§4·§5·§6·§7(단계 2)·§8. 단계 1 계획 `docs/superpowers/plans/2026-11-06-앱-알림-1-뼈대-다시볼날.md` 의 Global Constraints 를 그대로 따른다.

**끝났다는 기준(spec §7):** 동의하지 않은 사람·21시 이후·로그아웃 기기에 광고가 안 간다(판정 함수 테스트). 수신거부 버튼 한 번으로 철회되고 통지가 뜬다(라우트 테스트 + [로컬에서] 실기기).

## 구조

### DB — `supabase/migrations/20261108000000_push_ad_consent.sql` (먼저 따로 PR)

- `ad_consents` — 회원당 1행. `status`('granted'|'withdrawn'), `first_granted_at`(최초 동의, 바뀌지 않음 — 2년 재확인 기산점), `granted_at`, `withdrawn_at`, `last_reconfirm_notice_at`. 행이 없으면 '미동의'(철회와 구분, spec §4-2).
- `ad_consent_events` — `event`('grant'|'withdraw'|'result_notice'|'reconfirm_notice') + `source`(묻는 순간·설정·수신거부 버튼/줄·재확인 팝업/푸시).
- `push_asks.kind`('push'|'ad', 기본 'push') — 다시 묻기 상한을 거절 종류별로 세기 위해.
- `push_sends.unsubscribed_at` — 수신거부 표의 1회용 표시.
- `push_schedules`·`push_sends` 는 그대로(종류 값 확장은 단계 3·4).
- RPC `push_set_ad_consent(p_user_id, p_grant, p_source, p_send_id)` — 상태 변경 + 이벤트 2개(변경·결과 통지) + 수신거부 표 사용 표시를 **한 트랜잭션**으로. `SECURITY INVOKER`(service_role 이 표 권한으로 부른다), `REVOKE ALL … FROM PUBLIC, anon, authenticated` + `GRANT EXECUTE … TO service_role`.
- 전부 `ENABLE RLS` + service_role GRANT(시퀀스 포함), `users(id)` FK 는 `ON DELETE CASCADE`.

### 서버

| 경로 | 바뀌는 것 |
|---|---|
| `GET /api/push/settings` | `{ revisit, ad: { status, grantedOn, reconfirm } }` |
| `POST /api/push/settings` | `{ revisit }` 또는 `{ ad: true|false, source }` → 동의·철회 + 결과 통지 내용 `{ notice: { kind, date } }` 또는 `{ reconfirmSeen: true }` |
| `GET /api/push/asks?moment=&os=` | `{ moments, ask: 'push'|'ad'|null, ad }` — 서버가 구독·동의·질문 기록으로 `nextAsk` |
| `POST /api/push/asks` | `moment` 5종 + `kind` 받기 |
| `POST /api/push/unsubscribe` | 로그인 없음. 표 검증 → 그 발송이 광고였는지 → RPC 로 철회 + 표 사용 표시. 위조 403, 재사용 409 |
| `GET /api/cron/push-dispatch` | 다시 볼 날 뒤에 **2년 재확인 푸시**(정보성, 기한 7일 전부터) |

결과 통지 기록(`result_notice`)은 동의·철회를 처리한 같은 트랜잭션에서 남긴다 — 통지 내용은 그 응답으로만 화면에 가고, 응답을 받은 화면이 곧바로 팝업을 띄운다.

## 구현하며 정한 것 (설계 문언 안에서 — 운영자 확인 대상은 `HANDOFF.md` "결정 필요")

- **'알림 받을래'는 날짜를 안 골라도 누를 수 있다** — 설계 §4-2 그대로. 단계 1 은 칩을 골라야 눌렸다. 날짜 없이 누르면 알림만 켜고 카드로 바뀐다(카드에서 언제든 고른다).
- **체크하고 OS 창을 거부해도 광고 동의는 남긴다** — 설계 §4-2 표. 결과 통지는 OS 창이 닫힌 뒤에 뜬다.
- **별마루 첫 방문의 광고 질문(②)은 유료 구독자에게 띄우지 않는다** — 문구가 "내일 아침에도 알려줄까?"인데 구독자에겐 아침 흐름이 이미 정보성으로 간다. 구독자의 ②는 생일 순간만.
- **두 번째 실행 시트는 이미 알림 허용 + 광고를 정한(동의·철회) 사람에겐 띄우지 않는다** — 다시 볼 날을 뺀 시트라 물을 게 없다. 첫 상담 끝 시트는 다시 볼 날이 본체라 단계 1 처럼 늘 연다.
- **두 번째 실행 질문은 홈(`/`)에서 띄운다** — 로그인한 상태로 웹뷰가 뜬 횟수를 기기에 센다(`localStorage`). 다른 화면(알림으로 연 리딩 등)에서 시작했으면 홈에 올 때 띄운다.
- **2년 재확인 팝업·푸시의 날짜는 가장 최근 동의일**(재동의했으면 그 날). 기한 계산은 최초 동의일 기준(설계 §4-5).
- **결과 통지 기록은 동의·철회와 같은 트랜잭션** — 화면은 그 응답으로만 팝업을 띄운다.
- **광고 알림에서 이미 철회된 상태의 수신거부 표** — 표는 쓰인 것으로 표시하고 "이미 광고 알림을 받지 않고 있어"(통지 없음 — 바뀐 게 없다).
