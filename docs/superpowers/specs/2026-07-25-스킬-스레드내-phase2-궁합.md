# 스킬을 스레드 안으로 — Phase 2: 우리 궁합 (설계)

- 날짜: 2026-07-25
- 상태: 설계 합의 → 스펙 리뷰 대기
- 큰 그림: "우리 사이" 스킬을 **별도 페이지/별도 reading 없이 하나의 연애 상담 스레드 안에서** 제공하도록 재설계(대화 분산 제거). 스킬별 순차: **판정 → 궁합 → 카드뽑기**. Phase 1(판정)은 prod 라이브. 이 스펙은 **Phase 2 = 궁합(compat)** 만 다룬다.

## 배경 / 문제

현재 관계 스킬 "우리 궁합"(compat)은 이동형이다: 칩 → 확인 모달(40⭐) → `/api/fortune/create`(type:"compat")로 **별도 `readings`** 생성 → **구조화 JSON 리포트**(등급 5단계 · 테마 · 요약 · 오행케미 · 끌림 · 갈등 · 장기전망 · 조언3 · 한마디) 생성 → `/fortune/result?id=`의 리치한 카드 UI로 이동 → 스레드 복귀 시 `pending_skill_recap` 인사 버블. 즉 연애 상담 대화가 딴 화면으로 **분산**된다.

Phase 1이 판정을 인-스레드로 옮겼듯, 궁합도 스레드 안에서 진행해 "별콩이 = 하나의 연애 상담 에이전트, 스킬은 대화 중에 쓰는 능력" 비전을 완성한다. 단 판정(대화형)과 달리 궁합은 **두 사주 기반 원샷 구조화 리포트**라, "이 리치한 카드를 스레드 안에서 어떻게 보여줄지"가 핵심 결정이었다.

**결정(브레인스토밍 + 목업 검증)**: 스레드 안 **접기/펴기 카드**. 별콩이가 결과를 스레드에 바로 붙이고, 접힌 상태(등급 배지 + 테마 + 요약 2줄)에서 "펼쳐보기"로 전체 리포트가 인라인 확장. 팝업/모달은 "잠깐 다른 화면" 감각이라 반려. 접기/펴기는 대화 스크롤 히스토리에 결과가 눌러앉아 "별콩이가 지금 여기서 건네준" 감각을 살리고, 접힘 기본이라 스레드도 안 지저분하다.

## 목표 / 비목표

**목표 (Phase 2)**
- 궁합을 스레드 안에서 진행: 확인 모달(40⭐) → 서버가 두 사주로 구조화 리포트 생성 → **같은 스레드에 접기/펴기 카드**로 렌더 → 일반 대화로 자연 복귀. 별도 페이지/별도 reading 없음.
- 궁합 결과가 스레드 메시지로 남아 분산 0. 새로고침 후에도 카드 영속.
- 궁합 JSON이 모델 대화 맥락을 오염시키지 않게(최근창 치환) + 별콩이가 궁합 결과를 기억(skill_log).
- 별콩이가 스레드에서 궁합을 제안할 때 "보고 와서 이어서"가 아니라 "지금 여기서 바로" 톤(P2 페르소나 픽스, 궁합 부분).

**비목표 (다음 Phase)**
- 카드뽑기(Phase 3) 스레드화.
- 복귀 인사/CTA/recap-seen·`pending_skill_recap` 계열 제거(Phase 3에서 일괄 — checkin·deep_feelings가 아직 이동형이라 Phase 2엔 그대로 둠).
- 인-스레드 궁합 카드에 두 사주판 시각화(텍스트 리포트만 — 채팅 컬럼에 과함 + saju_data 저장 불필요).
- `/fortune` 독립 궁합 상품 + `compat_social`(친구·가족 궁합)은 손대지 않음(구조화 카드 + `/fortune/result` 유지).

## 결정 로그 (브레인스토밍)

| 결정 | 선택 |

| 대화모드/종료 | compat은 **원샷** — `active_skill` 대화모드·`[SKILL_DONE]`·안전 턴캡·캡 우회 **불필요**. `active_skill`은 **생성 중 인-플라이트 락**으로만 사용(중복 차감 방지). |
| 과금 | 계속 40⭐ 유료(확인 모달). |
| 하루 캡 | 궁합 카드는 user 발화가 없어(skillStart) 캡에 자연 미가산. 카드 메시지는 `skill_key='compat'` 태깅. |
| 생성 프롬프트 | 기존 `SECTION_GUIDE.compat` **그대로 재사용**(새 페르소나 파일 없음). |
| 사주판 | 인-스레드 카드엔 미표시(텍스트 리포트만). saju_data 미저장. |
| 복귀 인사 | 없음(인-스레드 = 이동 없음) → `appendSkillLog`(recap 미설정), 판정과 동일. |

## 설계

### 데이터

- **마이그레이션 불필요** — `messages.skill_key`(VARCHAR(30))는 Phase 1에서 이미 추가됨.
- 궁합 리포트를 **스레드 reading**(`relationships.thread_reading_id`)에 assistant 메시지 1건으로 저장:
  - `content` = `serializeCompatReport(buildCompatReport(ai))` (기존 `CompatReport` v:1 JSON).
  - `skill_key = 'compat'`.
  - 별도 `readings` row 없음, `saju_data` 미저장(카드는 텍스트 섹션만 렌더).
- `relationships.memo.active_skill`(Phase 1 타입)을 **인-플라이트 락**으로 재사용: `{ key:'compat', started_at, assistant_turns:0 }`. 생성 시작 시 세팅, 완료/실패 시 해제.
- 종료 시 `appendSkillLog(memo, "compat", threadReadingId, report.summary, now)` — `skill_log`만 적립, `pending_skill_recap` **미설정**.

### 개시 (client → chat 라우트)

- `useSkillLaunch`: compat(kind `compat`)은 지금처럼 확인 모달(40⭐) + 상대 생일 게이트를 유지. 단 "확인하고 시작" 시 `launchCompat`(POST fortune/create + 이동) 대신 **`onInThreadSkill("compat")`** 호출(dialogue와 동일 경로). `launchCompat` 제거.
- `ThreadChat.sendSkillStart`를 스킬 `kind`로 분기:
  - `dialogue`(verdict): 기존 텍스트 스트림 경로.
  - `compat`: `/api/relationship/chat`에 `{ skillStart:"compat" }` POST → **JSON 응답**(리포트) 파싱 → 카드 메시지 삽입 → `setActiveSkill(null)`(원샷 종료) → `onSkillDone?.()`. 로딩 버블("별콩이가 두 사주로 궁합을 보는 중 ✨") 표시.
- 차감은 **서버(chat 라우트 skillStart 처리)에서** `spendStars(userId, 40, source:"rel_skill_compat")`. 잔액 부족 402 → 클라가 `/shop`.

### 채팅 라우트 (`/api/relationship/chat`) 변경

`skillStart` 분기(현 verdict 전용)를 compat로 확장:

- `skillStart==="compat"`:
  1. `active_skill` 있으면 400(중복 방지). **단 compat 락이 stale(started_at > 3분)이면 override** — 하드 크래시로 stuck된 락 복구.
  2. 두 프로필(`self_profile_id`·`partner_profile_id`) 로드 + **생년월일 존재** 검증. 상대 생일 없으면 400(`partner_birth_required`), 나 생일 없으면 400(`self_birth_required`). (클라 게이트가 1차, 서버가 최종 권위.)
  3. `spendStars(40, "rel_skill_compat")` (실패 402). 성공 후 `active_skill={key:'compat',started_at:now,assistant_turns:0}` 락 세팅.
  4. `calcSaju(profileRowToSajuInput(self))`·`calcSaju(...(partner))` → `buildFortuneSystem("compat", {saju, sajuB, names})` → `generateOnce(system, [{role:'user',content:FORTUNE_KICKOFF}], MAX_TOKENS_BY_FORTUNE.compat, logCtx)` → `parseCompatReportJson`(실패 시 1회 재생성, fortune/create 패턴) → `buildCompatReport`.
  5. 카드 메시지 insert(`reading_id=threadReadingId, role='assistant', content=serializeCompatReport(...), skill_key='compat'`) + `appendSkillLog(...)` + `active_skill=null` (한 update).
  6. **리포트 JSON 반환**(`application/json`, 예: `{ report: <CompatReport> }`). verdict의 스트림과 다름.
  7. 차감 후 어느 단계든 실패 → 40⭐ 환불(`chargeStars refund`) + `active_skill=null` 롤백 + 500/에러 JSON.
- 라우트 `export const maxDuration = 120` 상향(동기 compat 생성 커버 — Claude 1회 호출, bounded).
- **일반 메시지 경로**: `active_skill.key==='compat'`는 대화모드가 **아니다**(verdict만 대화모드). compat 락은 일반 메시지 처리에 영향 없음(락 있는 ~수십초 동안 클라는 로딩 중이라 정상 대화 불가 상태).

**모델 맥락 치환**: 일반 메시지·verdict skillStart에서 `pastRows` 로드 후 `splitThreadMessages` 넘기기 전, 각 메시지 content가 `tryParseStoredCompatReport`로 파싱되면 짧은 자연어(`(별콩이가 우리 궁합을 봤어 — ${grade}, ${theme})`)로 치환. JSON 블롭이 최근창에 안 들어가고, assistant 메시지→assistant 텍스트라 alternation 불변. skill_log 요약 + 파일 블록이 연속성 이중 보강.

### 클라이언트 (ThreadCompatCard)

- `components/relationship/ThreadCompatCard.tsx` (신규) — 접기/펴기 카드:
  - 접힘: 💑 헤더 + 등급 배지 + 테마 + summary 2줄 클램프 + "전체 궁합 펼쳐보기 ▾".
  - 펼침: 오행 케미 + 끌림·성격 + 갈등 포인트 + 장기 전망 카드 + 조언 3 + 별콩이 한마디(note) + "접기 ▴".
  - `CompatReportView`의 필드 구조·연애 variant 라벨을 재사용하되 **사주판 없이**, 앱 팔레트(cream/lilac/gold). 기본 접힘.
- `ThreadChat` 메시지 렌더: assistant 메시지 content가 `tryParseStoredCompatReport` 성공이면 `ChatBubble` 대신 `ThreadCompatCard` 렌더(`initialMessages`·방금 받은 카드 둘 다). 관계 label로 카드 헤더("나 ⟡ {label}") 구성.

### 페르소나 (P2 — 궁합 인-스레드 제안 톤)

- `data/persona/byeolkong_relationship.md` §스킬 제안:
  - `compat`을 verdict처럼 **인-스레드 예외**에 추가 — "갔다 와서 이어서"가 아니라 "지금 여기서 바로 둘 사주로 궁합 봐줄게" 톤.
  - "연속성 예고 (필수)"(이동형 예고)를 **남은 이동형 스킬(checkin·deep_feelings)에만** 적용되게 범위 조정.
- 생성 프롬프트(`SECTION_GUIDE.compat`)는 그대로 재사용 — 새 페르소나 파일 없음.

### 제거 (Phase 2 한정)

- `lib/relationship/useSkillLaunch.ts`의 `launchCompat`(compat이 더는 이동/fortune-create 호출 안 함).
- `app/api/fortune/create/route.ts`의 관계 태깅 분기 — `relationshipId` 검증(257–270행) + `skill_key: relationshipId ? "compat" : null`(394행) + compat `logSkillToThread`(515–519행). **단 `/fortune` 독립 궁합 + `compat_social`은 `relationshipId`를 안 넘기므로 무손상 확인 후 제거.** (`getActivePass` import가 fortune/create에서 고아화되면 함께 정리.)
- (복귀 인사/CTA/recap-seen·`pending_skill_recap`·`applySkillToMemo`·`logSkillToThread`는 **유지** — checkin·deep_feelings가 아직 이동형. Phase 3에서 최종 정리.)

## 흐름 (end-to-end)

```
연애 상담 스레드
  └─ (궁합 칩/시트) → 확인 모달 40⭐ (상대 생일 게이트)
       └─ 확인 → chat 라우트 skillStart:"compat"
            └─ 서버: 두 프로필 검증 → 40⭐ 차감 → active_skill 락 → calcSaju×2
                 → compat 프롬프트 generateOnce → 리포트 JSON
                 → 카드 메시지 저장(skill_key=compat) + appendSkillLog + 락 해제 → JSON 반환
            └─ 클라(스레드): 로딩 버블 → 접힌 카드(등급+테마+요약2줄)
                 └─ 펼치기 → 전체 리포트 인라인 → 일반 대화 복귀 (전부 같은 스레드)
```

## 엣지 / 무결성

- **중복 시작(더블탭)**: `active_skill` 인-플라이트 락 → 두 번째 skillStart 400. 클라 `inFlightRef`/`sending`/`activeSkill` 가드가 1차, 서버 락이 2차. 40⭐ 이중 차감 방지.
- **stuck 락**: 하드 크래시로 락이 남으면 GET이 activeSkill='compat' 반환 → 스킬 칩 비활성. 다음 skillStart의 stale override(>3분)로 복구.
- **환불**: 차감 후 생성/저장 실패 시 40⭐ 환불 + 락 해제 + 에러(기존 fortune/create refundOnFailure + verdict skillStart 환불 패턴).
- **상대 생일 없음**: 클라 게이트(PARTNER_BIRTH_MSG) + 서버 400. 나 생일 없음도 서버 400.
- **캡 상호작용**: 궁합은 user 발화 없어 캡 미가산. 카드 메시지 skill_key 태깅으로도 이중 안전. 궁합 후에도 일반 대화 캡 온전.
- **모델 오염**: compat JSON은 최근창 치환으로 모델이 안 봄 → 별콩이가 JSON을 되뇌지 않음. 연속성은 skill_log 요약으로.

## 테스트

- 유닛: compat JSON 메시지 → 컨텍스트 치환 헬퍼(순수 함수); `appendSkillLog`(compat 키); `tryParseStoredCompatReport` 렌더 분기 판정.
- 라우트: skillStart:"compat"이 (a) 40⭐ 차감 + 카드 메시지 저장(skill_key=compat) + appendSkillLog + JSON 반환, (b) 상대/나 생일 없음 400, (c) 잔액 부족 402, (d) 중복 시작 400, (e) 생성 실패 시 환불 + 락 해제.
- QA 하네스: compat 리포트가 인-스레드에서 유효 구조화 JSON 생성(프롬프트 불변 → 대체로 통과 예상).
- 브라우저 E2E(dev): 칩 → 40⭐ 확인 → 로딩 → 접힌 카드 → 펼침 → 대화 계속, 새로고침 후 카드 영속, 모델이 JSON 안 되뇜.
