# E1 — 하단탭 IA · 상품 위계 · SEO 콘텐츠 존 설계

**작성** 2026-07-27 · **상태** 설계 확정, 구현 플랜 대기
**대체 관계** `plans/2026-07-26-seo-content-hub.md`(보류)를 이 스펙이 흡수한다. 구 플랜의 코드 골격은 재활용, **콘텐츠 우선순위는 뒤집는다**(§4-2).

## 목적

상품이 6종에서 9종으로 늘어나는 시점에 **자리 규칙**을 먼저 정한다. 개별 상품마다 배치를 정하면 다음 상품이 붙을 때 IA 를 다시 논의하게 되고, 그게 이 문서를 만든 이유다.

이 스펙이 답하는 것:
1. 하단탭 5칸을 무엇에 쓰나
2. 홈 화면의 슬롯 구조
3. 앞으로 나올 상품이 어디에 사는지 정하는 **규칙**
4. 비브랜드 검색 유입 자산(콘텐츠 존)의 URL·우선순위·범위
5. 배포를 어떻게 쪼개서 수익성 판정 창을 오염시키지 않나

**신규 상품 3종(E3 운세 캘린더 · E4 편지 교환 · E6 연애 시뮬레이션)의 배치를 여기서 확정한다.**

## 배경 — 왜 지금

**① 현행 탭축이 "의도"가 아니라 "메커니즘"이다.**

`components/layout/BottomTab.tsx` 의 5탭은 고민톡(`/`) · 별콩 운세(`/fortune`) · 연애 상담(`/relationship`) · 별콩 상점(`/shop`) · 내 정보(`/mypage`)다. 앞의 3개가 각각 SSE 채팅 / 원샷 리포트 / 지속 스레드라는 **소비 형식**으로 나뉘어 있다. 그래서 "걔 속마음이 궁금해"인 유저가 3탭 중 어디로 가도 맞다 — 고민톡(타로 태그) · 연애 상담(걔속마음 스킬 40별) · 별콩 운세(궁합 40별)가 같은 수요를 나눠 먹는다.

**② 상품이 3종 더 붙는데 들어갈 자리가 없다.** 그리고 사주 리포트는 앞으로 계속 추가될 예정이다(사용자 확인 2026-07-27).

**③ 비브랜드 검색 유입이 구조적으로 0이다.** `app/robots.ts:12-23` 이 `/fortune`·`/tarot`·`/saju`·`/shop`·`/concern`·`/readings`·`/mypage`·`/login`·`/select` 를 disallow 하므로 색인 허용은 `/` · `/relationship` · 약관 3종 · `/start` 뿐이고, `app/sitemap.ts` 는 URL 4개다. 광고 CAC 는 ₩505, 기여마진은 ₩66(회수 13%) — [[pnl-findings-2026-07-25]].

**④ 재방문 채널이 0개다.** PWA manifest 없음 · service worker 없음(웹푸시 불가) · `users` 테이블에 email 컬럼 없음 · 카카오 `talk_message` scope 없음 · 카톡 채널 CRM 은 발송비로 패스 결정. 3주째 재방문 실유저 0 은 "웹이라 약해서"가 아니라 **부를 수단이 없어서**다.

## §1. 조직 축

**1순위 = 재방문 이유(리텐션).** 하단탭은 전 화면에서 보이는 상시 지면이므로 "돌아올 이유"에 쓴다.

**교차 이용(ARPU 축)은 탭이 아니라 다른 지면이 담당한다** — 결과 화면 크로스셀(d14 배포 예정)과 인챗 칩. 교차 이용은 ARPU 4.9~6.0배로 유일하게 실측된 레버이고, 그 레버는 고의도 순간(결과 직후)에 있다. 홈 카탈로그가 아니다.

**⚠️ 과대평가하지 말 것: 탭 바는 재방문을 만들지 못한다.** 재방문을 만드는 건 알림이다(E3 의 ICS/캘린더 = OAuth·발송비 0으로 OS 알림을 빌려오는 유일한 수단). 탭이 하는 일은 ①돌아온 유저가 처음 보는 화면에 오늘 볼 게 있게 ②알림 딥링크가 착지할 자리 확보, 둘뿐이다.

| 2 | **운세** | `/fortune` | 별콩 운세 → 운세 | 사주 리포트 전체 — 의도축 카테고리(연애 / 나 / 시기) |

**URL 변경이 0이다** — 리다이렉트·구 링크 하위호환·canonical 작업이 전부 불필요하다. 바뀌는 것은 라벨과 화면 내용뿐이다.

**라벨 "고민톡" → "홈" 의 부수 효과**: `app/fortune/page.tsx:144` 가 *"결과는 내 고민톡에서 다시 볼 수 있어"* 로 **보관함**을 가리키는데 탭 "고민톡"은 홈이었다. 이 충돌이 해소된다.

**⚠️ "연애 상담" → "그 사람"** 은 이미 배포된 이름을 바꾸는 것이다. d28 이후 배포이고 등록 유저가 15명 수준이라 감당 가능하다고 판단했다.

### 3번 탭 이름에 대한 기록

"그 사람"은 상대 파일 하나를 가리키는 이름이라, E4 편지(별콩이와의 관계)가 이 탭에 들어오면 맞지 않는다. 그래도 지금은 "그 사람"으로 간다 — E4 의 정본 지면이 아직 미정이고, **라벨 변경은 IA 변경이 아니라 저비용**이다. 미래 상품 때문에 현재 상품(시뮬 + 스레드)의 선명함을 흐리는 게 더 비싸다.

```
├ ③ 상품 영역           고민톡 태그 10 + 크로스링크 슬롯 2

└ 푸터 (홈 전용)        + 콘텐츠 링크 행        ← 크롤 경로
```

### ① hero 슬롯 — 상태별 교체

현행 hero 는 `app/page.tsx:161-181` 에서 `pt-16 pb-12` + 180px 이미지 + 2줄 h1 = **~381px**, 말풍선(`:185-201`, `-mt-6` 상쇄 후) **~50px** 을 쓴다. 섹션 `pt-7` + "이렇게 사용해요" 카드 + 헤딩까지 더하면 **첫 태그 카드가 나오기까지 ~600px**(계산치 — §7-1 에서 실측).

390×844 기기의 가용 높이(헤더·하단탭·세이프 제외)가 ~700px 이므로 첫 화면에 상품 카드 1장, 375×667 에서는 **0장**이다. **상품을 밀어내고 있는 것은 오늘 블록이 아니라 hero 다.**

| 유저 상태 | hero 슬롯 내용 | 리스크 |
|---|---|---|
| 무이력 (신규 · 오가닉 · **크롤러**) | **현행 hero 그대로** | 변경 0 → 신규 CVR·SEO 리스크 0 |
| 재방문 | **내부 홍보 배너 (~120px)** | hero 381px 중 **261px 회수** |

크롤러는 항상 비로그인 = 무이력 뷰만 보므로 홈 색인 내용이 바뀌지 않는다.

**무이력 뷰는 현행과 완전히 동일하다** — hero 가 그대로이고, 오늘 블록도 항목이 0건이라 렌더되지 않는다. 신규 유입이 보는 화면에 변경이 없다는 것이 이 설계의 CVR 리스크가 0인 근거다.

**광고 유입은 홈을 거치지 않는다** — `app/start/page.tsx` 가 자체 태그 피커 → `sessionStorage` → `/concern` 으로 직행한다(`:117-119`). 홈 변경이 지금 돈이 나오는 경로를 건드리지 않는 근거다.

### 배너 정책 — 캐러셀 (최대 3장)

| | 결정 | 근거 |
|---|---|---|
| 장수 | **최대 3장** | 리서치의 "스토리텔링형 최적 5~8장"은 **하나의 서사**를 나눌 때 얘기다. 내부 홍보 배너는 카드마다 독립 상품이라 서사가 없어 뒤쪽이 죽는다 |
| **1번 카드** | **서버 우선순위가 결정** — ① 첫충전 +20% 미사용 → ② 신상품 출시 → ③ 미열람 결과 → ④ 브랜드 | 첫 카드 이후 ~70% 이탈이 사실이라면 **1번 선정이 여전히 가장 중요**하다. 우선순위 규칙을 폐기하지 않고 "1번 카드 결정 규칙"으로 남긴다 |
| 회전 | 자동 회전 5초+ · `prefers-reduced-motion` 존중 · **인디케이터 도트 필수** | 도트가 "뒤에 더 있다"는 유일한 신호 |
| 계측 | 카드마다 `?b=<slot_id>` → 기존 `page_views` | 새 테이블·새 이벤트 0 |

**⚠️ 캐러셀은 사용자 결정(2026-07-27)이다.** 제기된 반대 근거("첫 카드 이후 ~70% 이탈 → 2번째 슬라이드는 노출 0에 가까움")는 폐기하지 않고 위 가드레일 3개(장수 상한 · 1번 카드 규칙 · 카드별 계측)로 흡수했다. **카드별 계측에서 2·3번 클릭이 0에 가까우면 단일 슬롯으로 되돌린다** — 추측이 아니라 실측으로 판정한다.

### ② 오늘 블록 — 개인화 진열

항목이 있을 때만 렌더한다(0건이면 블록 자체가 없음). **전 항목이 상품으로 가는 링크**이므로 상품 목록의 경쟁자가 아니라 개인화된 진열이다.

| 항목 | 목적지 | 언제 |
|---|---|---|
| "오늘의 운세 아직 안 봤어" | 무료 → 소진 후 5별 | 지금 가능 |
| "안 본 결과 카드 N장" | 이어가기(정가×0.6) | 지금 가능 |
| "…와 이어서 얘기하기" | 패스 | 지금 가능 |
| "모레 좋은 날이야" | 좋은날 리포트 ⭐35 | E3 이후 |
| "별콩이 편지가 도착했어" | 편지 상품 | E4 이후 |

**⚠️ E3·E4 전에는 3줄뿐이다.** 지금보다는 낫지만 풍성해지는 것은 d28+ 이다.

### ③ 상품 영역 — 고민톡 전용

**사주 리포트를 홈에 나열하지 않는다.** 사주의 통로는 운세 탭 라벨(전 화면 상시 노출)이 담당하고, 그게 홈 하단 섹션보다 발견성이 높다. 교차 이용은 결과 화면이 맡는다(§1).

연애 태그 6 + 크로스링크 슬롯 2 + 다른 고민 4 라는 **현행 골격을 유지**한다. 태그 카드는 현재 큰 카드 + 아이콘 + 설명으로 전환 최적화된 형태이므로 **축소하지 않는다**(사용자 제약).

> **"사주를 홈에 나열하지 않는다"의 유일한 예외가 크로스링크 슬롯이다.** 슬롯 ②(연애 궁합)는 사주 리포트지만 카탈로그 진열이 아니라 연애 의도 안의 문맥 연결로 들어간다 — 자격 조건은 §3-b, 정본 지면은 여전히 운세 탭이다(§5 지면 지도).

## §3-b. 크로스링크 슬롯 규칙

`app/page.tsx:327-362` 에 이미 존재하는 궁합 금테 카드가 이 슬롯의 원형이다. **카탈로그 진열이 아니라 같은 의도 안의 자연 연결**이다.

**자격 조건 (셋 다 만족해야 슬롯 진입)**

1. **연애 의도와 겹친다** — 연애 고민을 하러 온 사람에게 자연스러운 것만. `2026년 사주 분석`·`오늘의 운세` 는 탈락
2. **태그 상담으로 대체 안 되는 다른 형식이다** — 태그는 "고민 종류", 크로스링크는 "다른 형식의 답"
3. **슬롯이 비어 있다 (최대 2)** — 3개가 되는 순간 카탈로그로 되돌아간다

**현재 배정**

| 슬롯 | 상품 | 형식 | 상태 |
|---|---|---|---|
| ① | 연애 시뮬레이션 | 역할극 + 코칭 | 신설 (E6) |
| ② | 연애 궁합 ⭐40 | 사주 리포트 | 이미 존재 (`page.tsx:327-362`) |

시뮬을 위에 둔다 — 신상품·별콩톡 특화이고 무료 인트로가 있어 진입 장벽이 낮다(궁합은 40별 선불).

**교체 규칙**: 새 상품이 자격을 충족하고 슬롯이 꽉 찼으면 **클릭률이 낮은 쪽을 뺀다.** 다음 상품이 붙을 때 IA 를 다시 논의하지 않는다.

**배너 슬롯과의 분업**

| | hero 배너 슬롯 | 크로스링크 슬롯 |
|---|---|---|
| 성격 | 시한성 · 개인 상태 | 상시 · 문맥 |
| 위치 | 최상단 (첫 화면) | 연애 태그 뒤 (스크롤 후) |
| 교체 | 서버 우선순위로 매번 | 클릭률 기준으로 드물게 |

시뮬 출시 시 배너에 한시적으로 뜨고 크로스링크에 상시 남는다. 중복이 아니라 분업이다.

## §4. 그 사람 탭 — 파일 프레임 + 3화자

### 파일 프레임

`app/relationship/page.tsx:421` 주석은 *"핵심은 지속 대화, 스킬은 부가"* 라고 선언하는데, 실제로 팔린 것은 스킬/스프레드 갭결제였다(전환 75%). **선언과 매출이 반대다.**

유저는 "계속 이야기할 상대"를 원해서 오지 않는다. *"걔 속마음이 뭐야" · "재회할까" · "이 싸움 누가 잘못했어"* — **질문에 답**을 받으러 온다. 지속 스레드는 우리가 원하는 구조(반복 매출)이고 유저가 원하는 형태가 아닐 수 있다. 등록 15건 중 14건 무발화의 더 깊은 층은 **등록 직후 첫 행동이 "백지 앞에서 고민을 서술하기"** 라는 것이다.

> **연애 상담의 실체는 "스레드"가 아니라 "그 사람 파일 + 그 위에서 돌리는 도구들"이다.**

- 상대를 등록하면 **그 사람 파일**이 된다. 사주·MBTI·성격은 게이트가 아닌 **옵션 강화재**
- 파일 위에서 도구를 돌린다: **시뮬레이션** · 걔 속마음 · 싸움 판정 · 우리 궁합 · 관계 체크인
- 스레드는 도구 사이를 잇는 **대화 로그**이고 간판 상품이 아니다

**연애 상담을 폐지하지 않는다.** 8/2(d7)에 rel 첫 발화 게이트가 예정돼 있고, 현재 6.7% 는 **무료 3턴이 없던 시절 숫자**다(무료턴은 7/26 배포). 파일 프레임은 **d7 판정 결과 양쪽에서 IA 가 그대로 성립**한다 — 스레드가 살면 파일 위 도구 중 하나로 남고, 죽으면 파일+도구만 남는다. 탭 구조는 안 건드린다.

### 탭 안 화면 구성 — 허브 + 독립 2화면

**리허설과 대화를 같은 화면에 섞지 않는다** (사용자 결정 2026-07-27). 섞으면 네 가지가 깨진다:

| | 섞으면 |
|---|---|
| 화자 혼동 | 스레드는 2화자(나·별콩이), 리허설은 3화자(나·상대 인격·별콩이 관찰자). 한 대화창에 섞이면 **지금 누구와 말하는지** 모른다 |
| 기억 오염이 UI 로 새어나옴 | 화자 태그로 기억을 분리해도 화면이 섞이면 유저 눈에는 "별콩이가 그 사람 흉내를 낸 기록"으로 보인다 — 리허설 프레임이 무너진다 |
| 스크롤백 | 리허설 20턴이 스레드 로그에 섞이면 지난 상담을 못 찾는다 |
| 세션 성격이 반대 | 리허설은 **시작-진행-디브리핑-종료**가 있는 1회 세션. 스레드는 **종결 없는** 연속. 종결 있는 것을 종결 없는 것 안에 넣으면 경계가 사라진다 |

```
/relationship                     ① 파일 허브
  ├── 파일 카드 (이름·관계·기록 칩) + 다음 행동 2개 + 쌓인 보낼 말
  ├── [리허설] → /relationship/rehearsal   ② 3화자 세션
  └── [별콩이랑 얘기] → 대화 스레드         ③ 현행 화면 + ⚡ 도구 4종
```

**① 파일 허브 (`/relationship`)** — 상품 나열이 아니라 **사람 프로필**이다. 상품 목록으로 만들면 등록 직후에 또 "무엇을 살까"를 묻게 되고, 그게 무발화의 재발 경로다.

| 상태 | 화면 |
|---|---|
| 미등록 | 콜드스타트 — 최소 입력(이름/관계)만. 사주·MBTI·성격은 게이트가 아닌 옵션 강화재 |
| 등록 후 | 파일 카드(이름·관계·`리허설 N회`·`대화 N턴`·`판정 N` 칩) → **[리허설]**(강조 테두리 — 독립 상품 1호) → **[별콩이랑 얘기]**(진행중이면 "N일 전 대화 이어가기") → **쌓인 보낼 말** 목록 |

"쌓인 보낼 말" = 리허설 디브리핑 결과의 적립물. **파일이 두꺼워지는 경험**이 §5 "장기 기억" 모드의 재방문 이유다.

**② 리허설 (`/relationship/rehearsal`)** — 시각적으로 완전히 분리한다.

- **배경 톤 · 헤더 · 상대 아바타가 전부 다름** → 화자 혼동이 물리적으로 불가능
- **상단 프레임 고지**: "이 〈이름〉이는 네가 말해준 걸로 별콩이가 그려본 모습이야. 진짜 그 사람이 아니라 연습 상대야." → E6 리스크 ② 대응이 마케팅 문구가 아니라 **제품 발화**로 들어간다
- **별콩이 개입은 채팅 버블이 아니라 노트 형태** → 대화 참가자가 아니라 지켜보는 사람이라는 신호. 3화자를 시각적으로 2+1 로 나눈다
- **[정리하기] = 디브리핑 트리거.** 유저가 언제든 역할극을 빠져나오는 문이고, **위기 신호 감지 시 서버가 누르는 것도 같은 문**이다(§4 안전망)
- 종료 시 허브로 복귀하며 "보낼 말"이 허브에 적립

**③ 대화 스레드 (현행 화면)** — 건드리지 않는다.

- ⚡ `SkillSheet` + 인-스레드 도구 4종은 **2026-07-25 에 39커밋으로 배포된 상태**이므로 그대로 둔다
- 별콩이는 관찰자였으므로 **리허설 결과를 알고 이어받는다** — 기억은 공유되나 원문 오염은 없다(디브리핑 요약만 주입)

**동선**: 등록 → **② 리허설** → 디브리핑 → ① 허브 적립 → **③ 대화로 깊이**. 등록 직후가 백지 대화창이 아니라 리허설이라는 것이 무발화 14/15 의 원인(첫 행동이 자유 서술)을 직접 치는 지점이다.

**기존 유저 마찰**: 현행 `/relationship` 은 등록 후 바로 대화창이라 허브를 끼우면 대화 진입이 1탭 늘어난다. → 홈 오늘 블록의 "…와 이어서 얘기하기"가 **③ 직행 딥링크**이므로 실제로는 홈에서 1탭이다(오히려 짧아짐). 허브에 진행중 대화가 있으면 상단에 크게 놓는다.

### 3화자 구조 (확정)

별콩이가 상대를 연기하지 **않는다.** 별콩이는 **제3자 관찰자**로 남고, **별개 인격**이 상대 역을 맡는다.

| 화자 | 역할 |
|---|---|
| 유저 | |
| **상대 인격** | 차갑고 회피하고 화낼 수 있어야 리허설이 성립 |
| **별콩이 (관찰자)** | 관찰 · 피드백 · 디브리핑. 코어 페르소나 그대로 |

이 구조가 E6 의 열린 리스크를 푼다:

| E6 리스크 | 3화자 구조에서 |
|---|---|
| ① 코어 페르소나 정면 충돌 | **해소** — 별콩이 코어(단정금지·따뜻함·hotline)를 한 글자도 건드리지 않는다. 신규 화자만 추가 → "코어 편집 = 전 종목 전역 변경" 이라는 최대 위험 회피 |
| ①-b 역할극 중 위기 신호는 누가 잡나 | **해소** — 관찰자가 상시 있으니 기능이 아니라 역할. 유저 발화에 `lib/sensitive.ts` 판정은 계속 돌고, high 면 즉시 역할극 중단 → 별콩이 복귀 → hotline |
| ② 정확도 근거 0 | **완화** — 별콩이가 제품 안에서 프레임을 말할 자리를 갖는다: "이 사람은 네가 말해준 걸로 내가 그려본 모습이야, 진짜 그 사람이 아니라 연습 상대야" |
| ③ 등록 마찰 재발 | **완화** — 등록을 공유하고 최소 입력만 게이트 |

**기억 오염도 자동 해결된다** — 상대 인격 발화는 화자가 다르므로 별콩이 기억에 "그 사람이 실제로 한 말"로 섞이지 않는다. 별도 저장 설계 없이 화자 태그로 끝난다.

**동선**: 등록 → 시뮬 체험 → **디브리핑(별콩이 복귀)** → 스레드/도구. 시뮬이 스레드의 유입원이 된다.

**⚠️ 제약**: 시뮬 상대는 차가울 수 있어야 하므로, 무료 구간이 "그 사람이 답장 안 해줌"으로 끝나면 최악이다. **무료 구간에 디브리핑(별콩이 복귀 + 보낼 말)까지 반드시 포함**한다.

## §6. SEO · 콘텐츠 존

### 6-1. robots 는 건드리지 않는다

`/fortune` 인덱스는 카드 목록뿐인 thin page 이고 하위는 입력 폼 + **개인 결과**다. robots 매칭이 문자열 프리픽스라 `/fortune` 을 열면 하위가 같이 열린다 — 개인 결과 색인 사고 리스크. 브랜드 쿼리는 이미 홈(`/`, priority 1.0)이 잡고, 비브랜드 쿼리는 에디토리얼 본문이 있는 `/guide/themes/*` 가 훨씬 잘 잡는다.

→ 현행 disallow **유지**. 신규 `/guide`·`/free` 는 disallow 목록에 없어 자동 허용이다. **`/tarot-cards` 같은 이름을 쓸 수 없는 이유가 이 프리픽스 매칭이다.**

### 6-2. 콘텐츠 우선순위를 뒤집는다

구 플랜은 타로 78장을 1순위로 놨는데, **AI Overview(한국어 2024-12 도입)가 정의형 쿼리를 정확히 잡아먹는다.** "바보 카드 의미"는 정의형의 교과서다. 78장을 먼저 쓰면 62,400자를 가장 위험한 쿼리에 먼저 헌납한다.

| 순위 | 자산 | URL | 노리는 쿼리 | 왜 | 개수 |
|---|---|---|---|---|---|
| **1** | 감정 태그 랜딩 | `/guide/themes/[tag]` | "재회 타로"·"짝사랑 타로" | **상업 의도** — 우리 태그와 1:1 이라 CTA 가 자연스럽고 전환 직결. AI 가 대체 못 함(개인 상황형) | 10 |
| **2** | 무료 도구 | `/free/daily-card` | — | **커뮤니티 미끼** — 현재 전 상품이 카카오 로그인 뒤에 있어 공유할 것이 0개. 인터랙티브라 AI Overview 회피 | 1 |
| **3** | 스프레드 가이드 | `/guide/spreads/[slug]` | "관계 스프레드 보는 법" | 준정의형이나 우리 상품 구조와 직결. `lib/tarot/spreads.ts` 재사용 | 14 |
| **4** | 타로 도감 | `/guide/tarot-cards/[slug]` | "바보 카드 의미" | 전환보다 **기반** — 롱테일·도메인 권위·내부 링크 허브. 정의형이라 후순위 | 78 |

**1차 발행 = 25페이지 (1+2+3), 약 12,000자.** 78장은 62,400자로 별도 시계.

**구 플랜의 배치 발행 구조를 그대로 쓴다** — `data/seo/*.json` 에 항목이 있는 슬러그만 `generateStaticParams` 가 생성하므로(thin page 방지) 순서만 바꾸면 되고 코드 변경은 0이다.

### 6-3. URL 구조

```
/guide                              콘텐츠 허브 목차
/guide/themes/[tag]                 감정 태그 랜딩 10
/guide/spreads/[slug]               스프레드 가이드 14
/guide/tarot-cards/[slug]           타로 도감 78 (후순위)
/free/daily-card                    무료 도구
```

코드는 `app/(content)/guide/*` · `app/(content)/free/*` 신규 라우트 그룹. **서버 컴포넌트 + `generateStaticParams` + Metadata/JSON-LD**, 에디토리얼 본문은 `data/seo/` 로 코드와 분리. 기존 페이지를 건드리지 않는다.

### 6-4. 콘텐츠 존은 착지 페이지다

| | 기존 유저 | 검색 유입 신규 |
|---|---|---|
| 시작 | 앱 홈 `/` | 구글 검색창 |
| 경로 | 홈 → 태그 → `/concern` → 상담 | **`/guide/themes/reunion`** → CTA → `/concern` → 상담 |
| 콘텐츠 존 | 안 지남 | **첫 화면** |

**주 입구가 앱 안이 아니라 구글이므로 탭 슬롯을 주지 않는다.** 탭을 줘도 검색 유입은 늘지 않는다. 앱 내 진입 경로(홈 콘텐츠 카드 2개 + 푸터 링크 행)의 목적은 ①로봇이 찾아갈 길 = 고아 페이지 방지 ②기존 유저의 부수 발견이다.

**콘텐츠 페이지에도 AppShell(헤더+하단탭)을 유지한다** — cold 트래픽을 제품에 연결하는 통로.

**CTA**: 홈 태그 클릭과 동일 진입(`sessionStorage` + `/concern`). 구 플랜 `components/seo/GuideCta.tsx` 그대로.

**`/free/daily-card` 는 두 지면 공유** — 콘텐츠 존이면서 홈 콘텐츠 카드 + (E3 이후) 홈 오늘 블록에서도 진입.

### 6-5. 네이버는 별도 채널, 복붙 금지

독립 도메인은 네이버 **스마트블록에 진입할 수 없다**(네이버 블로그·카페만 들어감). 그래서 표준 전략이 "자사 도메인 = 구글 / 네이버 = 별도 블로그"다. **C-Rank**(주제 전문성 누적 점수)가 3개월 이상 쌓여야 노출이 시작되므로 8월 착수 → 11월 반영이다.

**규칙**: 자사 `/guide` 본문을 네이버에 그대로 옮기면 중복 콘텐츠다. 네이버는 **다른 앵글**(경험담·사례·"~해봤더니")로 쓰고 자사 페이지로 링크한다.

### 6-6. 시계와 시즌

- 성과 리드타임 **6~9개월**. d28(8/23) 판정에 SEO 는 기여하지 않는다 — **별도 시계**로 본다
- **🔔 신년운세 시즌 콘텐츠는 10~11월 착수** (검색 스파이크 전 색인 숙성)
- 애드센스는 콘텐츠 존 **월 2.5만+ PV 시점 재검토**. 결제 퍼널 페이지엔 광고 금지 원칙 유지

## §7. 배포 분리

| 덩이 | 내용 | 시점 | 근거 |
|---|---|---|---|
| **A. 콘텐츠 존** | `/guide` 25p + `/free/daily-card` + `sitemap.ts` 확장 | **창 중간 가능** (8/3~8/8 골격 → 8/10~8/15 본문) | 신규 URL · 기존 페이지 무변경 = 퍼널 무접촉. 리드타임이 길어 일찍 켜는 게 이득 |
| **B. 탭 IA + 홈 재구성** | 5탭 재정의 · hero 슬롯 분기 · 오늘 블록 · 크로스링크 슬롯 2 · 홈·푸터 콘텐츠 링크 · 운세 탭 카테고리 | **d28 이후 (8/23+)** | 전 유저 노출 = 창 중간 절대 금지 |
| **C. 신상품** | E3 알림 레이어 · E4 · **E6 시뮬 = 리허설 화면 + 파일 허브** | 각 상품 스펙 | E1 은 자리만 정함 |
| **D. 네이버 블로그** | 개설 · 연재 | 8/17~8/22 착수 (사용자) | C-Rank 3개월 숙성 |

**A 를 쪼개는 지점**: 홈 하단 콘텐츠 카드 2개 + 푸터 링크 행은 홈을 건드리므로 **B 에 합류**한다. A 는 `sitemap.xml` + 콘텐츠 존 내부 링크만으로 색인을 시작한다.

> 푸터는 홈 최하단이라 퍼널에 물리적으로 닿지 않는다 — 앞당기고 싶으면 푸터 링크만 A 에 넣는 것도 가능하다. 실익(푸터 클릭률)이 미미해 기본은 합류.

**C → B 순서 의존 2건**

1. **홈 크로스링크 슬롯 ①**: 시뮬(E6)이 이 슬롯을 차지한다. **B 배포 시점에 시뮬이 없으면 슬롯 ①은 비우고 궁합 1개만 운용한다.** 미완성 상품 자리를 미리 그려두지 않는다 — `FORTUNE_CONFIG` 의 `active:false` 타로 운세 5종과 이행률 1.3%로 폐기된 RECO 가 그 교훈이다.
2. **파일 허브는 시뮬과 함께 배포한다.** 시뮬 없는 허브는 `[별콩이랑 얘기]` 하나만 있는 화면이 되어 대화 진입에 1탭을 더하는 **순수 마찰**이다. → **B(탭 IA)에는 그 사람 탭의 라벨 변경만 포함**하고, 허브 + 리허설 화면은 **C(E6)에 묶는다.**

## §9. 기각한 대안 (재논의 방지)

| 대안 | 기각 이유 |
|---|---|
| **홈 = 전상품 카탈로그**(의도축 3섹션에 대화·리포트 혼합, 배지로 구분) | 항목 16개 → 리포트 20종이면 40개로 구조 붕괴. 연애 태그 4개를 칩으로 압축해야 자리가 나는데 그건 전환 최적화된 카드를 건드리는 것. 재방문자에게 주는 것 0 |
| **홈 안 서브탭**(칩 토글 [타로 고민톡 / 사주 운세]) | "홈에서 전 상품이 보인다"를 라벨 수준만 만족. 사실상 하단탭을 홈 안으로 접은 것이라 발견성이 **탭보다 낮아짐**(탭 라벨은 전 화면 상시). 비활성 존이 DOM 에 없어 홈 색인 텍스트 감소. `/fortune` 탭은 이미 존재하므로 구현도 더 큼 |
| **콘텐츠 전용 탭** | 콘텐츠 존의 목적은 검색 유입이고 탭이 없어도 달성된다. 앱 내 유저가 일반 타로 도감을 읽는 것은 재방문 훅으로 약함 — 운세 소비는 "내 것"이 훨씬 세다. 탭 슬롯 대비 기대값 최하 |
| **보관함 탭 승격** | 홈 오늘 블록이 이어가기·미열람을 이미 노출 → 기능 중복 |
| **상점 탭 제거**(헤더 흡수) | 검토했으나 **사용자 결정으로 유지**. 헤더에 잔액+링크가 있어(`Header.tsx:78-88`) 중복이긴 하나 매출 직결 지면 |
| **시뮬 전용 탭 / 시뮬 독립 지면** | 상대 등록·기억·패스를 이중화하거나 복제해야 함. 등록 마찰이 14/15 무발화의 원인이므로 1순위 리스크 재발 |
| **연애 상담 폐지** | 무료 3턴 효과 측정 전(7/26 배포). d7(8/2) 게이트가 이 질문을 묻게 예정돼 있어 지금 결정하면 판정을 선점함 |
| **별콩이가 상대를 연기** | 코어 페르소나 정면 충돌 + 위기 감지 주체 불명 + 기억 오염. 3화자 구조가 셋 다 해결 |
| **리허설과 대화를 한 화면에 섞기**(초안: 스레드가 본체, 시뮬은 그 위 카드) | 화자 혼동 · 기억 오염이 UI 로 새어나옴 · 스크롤백 지옥 · 종결 있는 세션을 종결 없는 스레드에 담는 모순. §4 참조 |
| **단일 배너 슬롯**(캐러셀 없음) | 검토 후 **사용자 결정으로 캐러셀 채택**(2026-07-27). 반대 근거는 가드레일 3개로 흡수하고 카드별 계측으로 사후 판정 |
| **타로 78장 우선 발행** | 62,400자를 AI Overview 직격 쿼리에 먼저 투입. 배치 발행 구조가 있으므로 후순위·점진이 정확 |
