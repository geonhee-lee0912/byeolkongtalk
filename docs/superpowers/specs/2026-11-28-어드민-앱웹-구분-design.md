# 어드민 앱/웹 구분 + 실제 결제자 줄 — 설계

- 날짜: 2026-11-28 · 브랜치 `claude/admin-app-web`
- 상위 설계: `2026-10-12-앱-전환-design.md` ④ "앱 유입·결제가 어드민에 따로 보인다"

## 왜

iOS 심사·안드로이드 등록을 기다리는 지금, 출시 날부터 앱과 웹의 방문·가입·결제를 나눠 볼 수 있게 미리 깔아 둔다. 지금은 방문 기록(`page_views.browser_env = 'app'`)과 결제 수단(`payments.pg_provider` apple·google·tosspayments)에 근거가 쌓이지만, 그걸 나눠 보여 주는 화면은 결제/정산의 "스토어 결제" 칸 하나뿐이다.

같이 고칠 것: 대시보드 "결제율"이 **가입 후 48시간 안에 처음 결제한 신규**만 세는데, 화면에는 "결제율"이라고만 적혀 있어 실제 결제자 전체로 읽힌다. 운영자가 "실제 결제자는 더 많은데 숫자가 안 맞는다"고 느낀 원인이다(11-28 운영 원본 대조로 확인 — 계산은 정의대로 맞고, 기존 가입자의 첫 결제·재결제·탈퇴자 결제가 빠진다).

## 목표

1. **대시보드**에 앱/웹 칸 — 오늘·어제·최근 7일의 방문(UV)·가입·결제를 앱/웹으로 나눠 보인다. 결제는 토스·애플·구글로.
2. **대시보드 결제율 칸 아래**에 "그 기간 실제 결제자" 줄 — 같은 날짜 창에 결제한 사람 전체를 신규(48시간 안)·신규(48시간 뒤)·기존 첫 결제·재결제·탈퇴로 나눠 보인다.
3. **트래픽 화면 일별 UV/PV**에 앱 UV·앱 PV와 가입 앱/웹을 더한다.

## 안 하는 것

- 로그인·가입 코드와 `users` 표 구조는 건드리지 않는다(B안을 버린 이유 — 아래).
- 기존 결제율 정의(48시간·코호트)는 바꾸지 않는다. 신규 유입 질을 보는 지표로 그대로 두고, 옆에 실제 결제자를 붙인다.
- 앱 설치 수·스토어 전환(웹→스토어 이동)·앱 전용 깔때기는 이번에 안 한다.
- 결제/정산 화면의 "스토어 결제" 칸은 이미 있으므로 손대지 않는다.

## 실패로 치는 것

- 원본 행을 앱으로 끌어와 세는 것(Max rows 에 조용히 잘린다). 집계는 전부 SQL RPC 로.
- 앱/웹 합이 전체와 안 맞는 표(아래 불변식).
- 마이그레이션과 그걸 읽는 화면 코드를 한 번에 올려 배포 사이에 화면이 깨지는 것.

## 방식 (운영자가 A 선택, 11-28)

- **A. 가입 직후 첫 방문 기록으로 판정 (채택)** — 가입 시각 이후 24시간 안의 그 회원 첫 방문 기록(`page_views.user_id = 회원`, 봇 제외)의 `browser_env` 가 `app` 이면 앱 가입, 다른 값이면 웹 가입, 기록이 없으면 '모름'. 로그인 코드 무변경, 지난 가입에도 바로 적용. 운영 실측(최근 30일 가입자): 99% 이상이 첫 방문 기록을 갖고, 가입 뒤 첫 방문까지 최대 30초 남짓 — 판정 창 24시간은 넉넉하다.
- **B. 가입 순간에 회원 기록에 앱/웹 적기 (버림)** — 가장 정확하지만 로그인·회원 표를 바꾸는 되돌리기 어려운 일이고(PR 2개·반대편 리뷰·승인), 출시 직전 로그인을 건드리는 위험이 이득보다 크다.

## 정의 (운영자가 정한 것 + 설계 판단)

- **앱 방문** = `browser_env = 'app'`. **웹 방문** = 그 외 전부(`ig`·`fb`·`kakao`·`other_inapp`·`browser`·NULL). *(설계 판단: NULL 은 UA 없는 요청이라 앱일 수 없다 — 앱 웹뷰는 UA 꼬리를 늘 붙인다.)*
- "최근 7일" 방문 = 7일 동안 **서로 다른** 방문자 수(하루 UV 를 더하지 않는다 — 이틀 온 사람을 2로 세면 이번에 고치려는 오해가 또 생긴다). 그래서 대시보드는 날짜별 RPC 가 아니라 기간 요약 RPC 를 쓴다(아래). *(설계 판단 — 빌더 검토에서 나옴)*
- UV = 그날 서로 다른 `anon_id` 수(기존 추세 UV 와 같은 정의). 한 anon_id 가 앱·웹 둘 다 찍히면 양쪽에 1씩 → **앱 UV + 웹 UV ≥ 전체 UV** 일 수 있다. 실제론 앱 웹뷰와 브라우저가 쿠키를 공유하지 않아 거의 없다. *(설계 판단: 화면에 "합이 전체보다 클 수 있음" 한 줄.)*
- 가입 = 위 A 정의. 앱 + 웹 + 모름 = 그날 가입 수(불변식).
- 결제 = `payments.status = 'completed'`, 결제 시각 KST 날짜 기준. 수단은 `pg_provider`. 앱 결제 = apple·google, 웹 결제 = tosspayments. 금액 0원 스토어 결제(샌드박스 시험)도 그대로 센다 — 출시 전 시험 기기만 만든다. 환불돼 `status` 가 `refunded` 로 바뀐 결제는 빼고, 화면에 "환불 제외" 한 줄을 단다 — 대시보드의 다른 결제 숫자(오늘 결제·결제율)와 같은 기준. 결제/정산의 "스토어 결제" 칸은 환불 포함이라 애플·구글 숫자가 그쪽보다 작을 수 있다. *(설계 판단)*
- 실제 결제자 분류(그 창에 completed 결제가 있는 사람 기준, 사람당 1번):
  - 신규·48시간 안: 창 안에 가입 + 첫 결제가 가입 후 48시간 안 → 결제율이 세는 사람과 **거의** 같다(아래 날짜 창 — 경계에서 1~2명 다를 수 있다)
  - 신규·48시간 뒤: 창 안에 가입 + 첫 결제가 48시간 뒤
  - 기존·첫 결제: 창 전에 가입 + 평생 첫 결제가 창 안
  - 재결제: 창 전에 이미 결제한 적 있음
  - 탈퇴: `payments.user_id` 가 NULL(탈퇴로 익명화) — 사람 구분이 안 되므로 **건수**로 센다
- 날짜 창: 결제율 "성숙 7일" 줄과 **같은 날짜(오늘-8 ~ 오늘-2)**. 다섯 줄 모두 **결제한 날** 기준이다(운영자 결정 11-28 — "그 7일 동안 실제로 결제한 사람 전체"가 목적이라 표 합계 = 창 안 결제자 수가 되게). 결제율은 가입한 날 기준이라, 창 끝 무렵 가입해 창 뒤에 결제한 사람은 결제율에만, 창 직전 가입해 창 첫날 결제한 사람은 이 표의 "기존·첫 결제"에 잡힌다. 화면에 "결제율과 날짜 기준이 달라 신규 줄이 딱 맞지는 않음" 한 줄.
- 제외: 기존 대시보드와 같이 `adminExclusionArray()`(운영자 계정).
- 날짜식은 전부 `(created_at AT TIME ZONE 'UTC' + INTERVAL '9 hours')::date`.

## 만드는 것

### 마이그레이션 (먼저 단독 push)

새 RPC 3개. 둘 다 `SECURITY DEFINER` + `REVOKE … FROM PUBLIC, anon, authenticated` + `GRANT EXECUTE … TO service_role`. 기존 RPC 는 바꾸지 않는다(반환 모양을 바꾸면 DROP 이 필요하고 배포 사이 창이 생긴다).

1. `admin_platform_daily(p_since TIMESTAMPTZ, p_exclude UUID[])` → KST 날짜별
   `uv_app, uv_web, pv_app, pv_web, signups_app, signups_web, signups_unknown, pay_toss, pay_apple, pay_google, won_toss, won_apple, won_google`
   (pay_* = 결제 건수, won_* = 금액). 방문 필터는 기존 `admin_traffic_trend` 와 같다(봇 제외, `user_id IS NULL OR user_id <> ALL(p_exclude)`).
2. `admin_platform_summary(p_since TIMESTAMPTZ, p_until TIMESTAMPTZ, p_exclude UUID[])` → 기간 한 행, 열은 1번과 같다(UV 는 기간 안 서로 다른 방문자). 대시보드가 오늘·어제·최근 7일로 세 번 부른다.
3. `admin_period_payers(p_since TIMESTAMPTZ, p_until TIMESTAMPTZ, p_exclude UUID[])` → 분류별 한 행
   `segment, people, payments, won` (탈퇴 행은 people = NULL).

적용 전에 두 함수 본문을 운영에서 읽기 전용으로 인라인 실행해 본다(파일 하나가 실패하면 전부 실패한다 — AGENTS.md).

### 화면 (마이그레이션이 dev 에 적용된 뒤 push)

- **대시보드** (`app/admin/page.tsx`, 데이터는 `lib/admin/daily-load.ts`)
  - 결제율 표 아래 "그 기간 실제 결제자" 작은 표: 분류 5줄 × 사람·건·금액, 맨 아래 합계. 제목 옆에 "결제한 날 기준 · 환불 제외 · 결제율과 날짜 기준이 달라 신규 줄이 딱 맞지는 않음" 한 줄.
  - 결제율 칸 제목을 "결제율 (신규 가입 후 48시간 안 첫 결제)"로 바꿔 오해를 줄인다.
  - 새 칸 "앱 / 웹": 행 = 오늘·어제·최근 7일, 열 = 방문(앱·웹) · 가입(앱·웹·모름) · 결제(토스·애플·구글, 건·금액).
- **트래픽** (`app/admin/traffic/page.tsx`, API `app/api/admin/traffic/route.ts`)
  - 일별 UV/PV 그래프에 "앱 UV" 선을 더하고, 아래에 일별 표(날짜 · UV 앱/웹 · PV 앱/웹 · 가입 앱/웹/모름)를 둔다.
- 읽기 실패는 기존처럼 칸별 `LoadFailed`.
- 폰 폭에서 넘치는 표는 기존 표처럼 가로 스크롤.

## 확인 방법

- 단위: 행 → 화면 줄 변환 함수(합계·불변식)를 `node:test` 로.
- 운영 대조: RPC 본문을 인라인 실행한 결과를 독립 쿼리와 비교 — ①날짜별 앱 + 웹 + 모름 가입 = 그날 `users` 가입 수 ②"신규·48시간 안" 사람 수와 같은 창의 `admin_pay_rate` 결제자 합의 차이가 전부 경계 날짜 가입자로 설명되는지(사람 단위로 대조) ③분류별 건수 합 = 창 안 completed 결제 건수.
- 화면: `/admin`·`/admin/traffic` 을 폰·PC 폭으로 찍어 확인(로컬, 어드민 쿠키 주입).
- 권한: dev 에서 anon 키로 세 RPC 실제 호출 → 401.
- 앱 가입 판정 실물: 운영 실측 99% 는 사실상 웹 가입자 기준이다. 시험 기기 앱으로 새 계정 가입 1회 → 그 계정이 '앱'으로 잡히는지 본다(로컬·앱 빌드 필요).
