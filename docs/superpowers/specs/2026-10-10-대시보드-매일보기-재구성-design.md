# 대시보드 "매일 보기" 재구성 — 설계

- 날짜: 2026-10-10
- 범위: 로드맵 ④ 어드민 총 개선의 **B 덩어리**. (A = 광고비 API 자동수집, prod 완료 `45aaa084`·`efeabf11`)
- 상태: 사용자 승인(2026-10-10). 이 작업 뒤 "대시보드 전체 재확인 → 탭 단위 위계 정리"가 이어진다(별도 스펙).

## 1. 왜

- **어드민은 사실상 대시보드 한 장이다** (prod page_views 30일, 어드민 계정): `/admin` 541PV·31일 매일 / `/admin/survey` 61PV·28일 / 나머지 분석 화면(roadmap·analytics·traffic·paywall·relationship) 0~3PV.
- 사용자가 매일 판단하는 숫자 중 **결제율·P1·오늘 결제·소재 성과**는 대시보드에 없어서 그동안 SQL 로 물었다.
- 설문 화면을 매일 여는 이유 = **새 설문이 있나 보고, 있으면 원문을 읽는다**(사용자: "그게 큰 도움이 됨").
- 1층의 **매출의 질·가드레일은 안 본다**("뭔지 잘 모르겠다", "가드레일은 의미부여가 와닿지 않는다"). 2층 **"왜 ▾" 접힘 섹션도 잘 안 연다** → 원칙: **매일 봐야 하는 건 접힘 안에 넣지 않는다.**

사용자 우선순위: 아주 높음 = 결제율(1)·오늘 결제(3) / 높음 = 소재 성과(2, 단 지금은 광고 성과가 나빠 의미가 덜함)·별마루 구독(5) / 필요 = 고장 감시(4, 요즘 에러 적음).

## 2. 새 순서

| # | 블록 | 상태 |
|---|---|---|
| 1 | 기여 히어로 | 그대로 (사용자: 맨 위가 맞다) |
| 2 | 오늘·어제 카드 | 그대로 |
| 3 | **오늘 들어온 것** — 새 설문 · 오늘 결제 · 고장 신호 | 신규 |
| 4 | **결제율** — 오늘/어제/7일 × P1·P2 | 신규 |
| 5 | **별마루 구독** — 오늘/7일 신규·해지·활성 | 2층에서 승격 |
| 6 | 흐름 · 단가 | 그대로 |
| 7 | **광고 소재 표** (펼친 상태) | 신규(기존 집계 재사용) |
| 8 | "왜 ▾" 보관함 — 2층 8섹션 + **매출의 질** + **가드레일** | 맨 아래로 |
| — | 처리 대기 칸 · 전체(누적) 칸 | 처리 대기는 3의 고장 신호로 흡수. 전체(누적)는 보관함 아래로 |

**삭제 0** — 기존 화면·2층 섹션·지표 정의는 그대로 남는다. 1층에서 빠지는 것은 보관함으로 옮겨질 뿐이다.

## 3. 블록 상세

### 3-1. 새 설문

- 새 테이블 `admin_seen_markers(key TEXT PK, seen_until TIMESTAMPTZ NOT NULL, updated_by UUID → users ON DELETE SET NULL, updated_at)`. 이번엔 `key='survey'` 하나. RLS ON·정책 0·REVOKE 3종.
- 대시보드: `survey_responses.created_at > seen_until` 인 응답 **수** + **최신 5건 원문**(닉네임·KST 시각·문항/답). 5건 넘으면 "외 N건 — 설문 화면에서" 링크.
- 원문 렌더는 기존 `/admin/survey` 의 렌더(문항-답 목록)를 컴포넌트로 공유한다 — 두 곳의 표시가 갈리지 않게.
- **[확인했어요]** → `POST /api/admin/seen {key:'survey', until:<화면에 보인 최신 응답의 created_at>}`. **누른 시각(now)이 아니라 보인 마지막 응답 시각**으로 저장 — 화면을 보는 사이 들어온 응답을 놓치지 않게. `requireAdminWrite` + `logAdminAction('seen_mark')`. 마커가 없으면(첫 사용) 최근 7일을 "새 것"으로 본다.
- 0건이면 "새 설문 없음 · 마지막 확인 {시각}" 한 줄.

### 3-2. 오늘 결제

- `payments`(status='completed', 오늘 KST, 어드민 제외) 최신순, 표시 상한 50 + 닿으면 경고 줄.
- 줄마다: 시각 · 닉네임(→ `/admin/users/[id]`) · 패키지(`package_type`, `stars_given`별) · 금액 · **첫 결제/재결제**(그 유저의 이전 completed 결제 유무).
- **오늘 별을 쓴 곳**: 같은 유저의 오늘 `star_transactions`(type='spend') 를 `소스 라벨 금액별` 로 이어 붙인다(예: "타로 130 · 이어가기 10"). 메뉴판 상품(55·130)은 소스가 `tarot_reading` 로 같아서 **금액으로 구분**된다.
- 소스 라벨은 대시보드 전용 작은 맵(`tarot_reading`→타로 · `clarifier`→추가 질문 · `extend`→연장 · `fortune_*`→사주 리포트 · `byeolmaru_subscription`→별마루 구독 · 그 외 원문). 맵에 없는 값은 원문 그대로 — 동적 키로 config 를 조회해 크래시 내지 않는다(메모리 `recurring-crash-class-config-by-dynamic-key`).
- 헤더: "오늘 결제 N건 · ₩합계".

### 3-3. 고장 신호 (있을 때만 표시)

다음 중 하나라도 참이면 빨간 줄(항목별 링크). 전부 거짓이면 블록 자체를 렌더하지 않는다.
- 미해결 에러(기존 `s.alerts.unresolvedErrors` > 0) → `/admin/errors`
- 미검토 민감 알림(기존 `s.alerts.unreviewedSensitive` > 0) → `/admin/sensitive`
- **광고비 동기화**: 최신 `ad_sync_runs` 가 `ok=false`, 또는 마지막 `ok=true` 의 `finished_at` 이 **2시간 이상 전** → `/admin/ads`. (매시 cron 이라 2시간 = 연속 2회 누락)
- 조회 자체가 실패하면 그 항목은 "확인 실패"로 빨간 줄에 넣는다 — 실패를 "이상 없음"으로 위장하지 않는다.

### 3-4. 결제율

새 RPC `admin_pay_rate(p_since TIMESTAMPTZ, p_exclude UUID[])` → 가입 KST 날짜별:

| 컬럼 | 정의 |
|---|---|
| `d` | 가입 KST 날짜 (`(u.created_at at time zone 'UTC' + interval '9 hours')::date`) |
| `signups` | 그날 가입자 (어드민 제외) |
| `payers` | 가입 후 **48시간 안** completed 결제가 1건 이상인 사람 |
| `p1` | payers 중 **첫 결제 시각 < 첫 리딩 created_at** (리딩이 없으면 P1) |
| `p2` | payers 중 첫 결제 시각 ≥ 첫 리딩 created_at |
| (성숙 판정) | RPC 가 아니라 앱에서: `d <= 오늘(KST)-2` 면 그날 가입자 전원이 48시간을 채웠다 |

- 화면: 오늘(진행 중) · 어제(진행 중) · 최근 7일(성숙한 날만 합산 = 오늘-8 ~ 오늘-2, "성숙 7일" 명시) 세 줄 × `가입 · 결제자(율) · P1(율) · P2(율)`.
- 율의 분모는 전부 `signups`. 소표본이라 율 옆에 실인원을 같이 쓴다(메모리 규율: 퍼센트가 아니라 실인원으로 읽기).
- **반반(A/B) 그룹으로 나누지 않는다** — 판정(~10-25) 엿보기 금지.
- 정의는 10-04 매출 하락 진단(메모리 `revenue-drop-diagnosis-2026-10-04`)의 48h·P1/P2 와 같다. 단 그 진단은 메타 유입만 봤고 여기는 전체 가입이다(라벨에 "전체 유입").

### 3-5. 별마루 구독

- 기존 `admin_layer2_subscription(p_since, p_until, p_exclude)` 를 오늘·7일 두 번 호출 → `started`(신규) · `expired`(해지/만료) · `active_now`(활성). 2층 subscription 섹션은 그대로 남긴다.

### 3-6. 광고 소재 표

- 기존 `admin_funnel(p_since=7일, p_exclude, p_aliases=CREATIVE_ALIASES, p_limit)` 재사용 → 소재 · 지출 · 가입 · 결제자(`first_paid`) · 매출 · CAC · ROAS.
- **클릭** = `ad_spend` 7일 `creative_key` 별 `sum(clicks)` 를 `canonicalCreative` 로 같은 별칭 병합 후 붙인다 → 클릭→가입 비율. (집계 RPC 하나 더 만들지 않고 앱에서 7일×소재 수십 행을 합친다 — 행수가 소재×일로 상한이 작다. `limit` 명시 + 닿으면 경고)
- 지출 0·가입 0 소재(유기 유입 `(organic)` 등)는 표 아래로.

## 4. 데이터·권한

- 신규: 마이그레이션 1개(`admin_seen_markers` 테이블 + `admin_pay_rate` RPC). 둘 다 `REVOKE … FROM PUBLIC, anon, authenticated` + service_role GRANT.
- `admin_pay_rate` 는 **적용 전 prod 에서 본문을 인라인 실행**해 숫자를 확인한다(AGENTS.md 규칙). 날짜식은 `at time zone 'UTC'` 포함, NULL 3값 논리 주의(리딩 없는 결제자 = P1 을 `first_reading IS NULL OR …` 로 명시).
- 그 외는 기존 테이블 직접 조회(표시용 목록, 상한+경고) 또는 기존 RPC 재사용.
