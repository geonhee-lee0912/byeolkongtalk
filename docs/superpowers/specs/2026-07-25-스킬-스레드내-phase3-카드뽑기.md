# 스킬을 스레드 안으로 — Phase 3: 카드뽑기 (설계)

- 날짜: 2026-07-25
- 상태: 설계 합의 → 스펙 리뷰 대기
- 큰 그림: "우리 사이" 스킬을 **별도 페이지/별도 reading 없이 하나의 연애 상담 스레드 안에서** 제공하도록 재설계(대화 분산 제거). 스킬별 순차: **판정 → 궁합 → 카드뽑기**. Phase 1(판정) prod 라이브, Phase 2(궁합) dev 로컬 완료. 이 스펙은 **Phase 3 = 카드뽑기(`checkin`·`deep_feelings`)** 와, 이동형이 완전히 사라짐에 따른 **복귀 인사(recap) 체인 일괄 제거**를 다룬다.

## 배경 / 문제

`kind="tarot_draw"` 두 스킬(관계 체크인 45⭐ / 걔 속마음 40⭐)은 남은 유일한 이동형이고, 왕복이 6단계로 가장 길다:

```
/relationship 스레드 → sessionStorage(REL_SKILL_KEY) → /tarot/draw(별도 화면)
  → POST /api/consultations/tarot(전용 readings row + source:"tarot_reading" 차감)
  → /tarot/reading(전용 SSE 채팅, 최대 15~16턴) → /tarot/result(결과)
  → pending_skill_recap → /relationship 복귀 → recap-seen 인사 버블(타자기)
```

즉 "별콩이 = 하나의 연애 상담 에이전트"인데 정작 가장 값비싼 스킬 두 개가 대화를 딴 화면으로 완전히 들고 나간다. Phase 1·2가 판정·궁합을 스레드로 들여왔으니, 카드뽑기까지 들이면 이동형이 0이 되고 recap 체인 전체가 dead code가 된다.

**핵심 난점**: 카드뽑기는 판정(대화형)·궁합(원샷 JSON)과 또 다르다 — (a) 뽑는 **의식**(덱 스와이프 + FLIP + 정/역 선택)이 풀스크린 인터랙션이고, (b) 결과가 구조화 JSON이 아니라 **카드 시각물 + 산문 풀이**이며, (c) 지금은 그 풀이가 최대 16턴 전용 대화라 "무엇을 파는 상품인지"가 인-스레드에서 재정의된다.

## 목표 / 비목표

**목표 (Phase 3)**
- 카드뽑기를 스레드 안에서 완결: 스킬 칩 → **뽑기 모달**(가장자리 여백 · 뒤 스레드 비침) → 확인(45/40⭐) → 같은 스레드에 **카드 스트립 + 풀이 스트리밍** → 그대로 자유 대화 연속. 라우팅·별도 reading 없음.
- "대화 분량까지 산 것"을 보전: 스킬 직후 **캡 면제 턴(그레이스)** 을 스킬별로 지급(checkin 10 / deep_feelings 8).
- 이동형 소멸에 따른 **recap 체인 + `/tarot/draw` 관계 분기 + `/api/consultations/tarot` 관계 태깅 일괄 제거**.
- 인-스레드 스킬 별소모가 애널리틱스에서 종목별로 살아남게(Phase 2에서 실제로 당한 회귀 방지).

**비목표**
- 가격 변경 없음(45/40⭐ 유지). 패스 필수 조건도 현행 유지.
- `/tarot` 일반 타로 상담 흐름(피커 → draw → reading → result)은 **무손상**. 손대는 것은 관계 스킬 분기뿐.
- 과거에 생성된 관계 스킬 reading의 열람(보관함 · `/tarot/result` · 복귀 CTA)은 **그대로 유지** — `readings.relationship_id`/`skill_key` 컬럼 및 결과 렌더 코드는 남긴다. 없어지는 건 **생성 경로**뿐.
- 마이그레이션 없음(아래 데이터 절 참고).
- 스프레드 포지션 라벨 변경 없음(아래 결정 로그 참고).

## 설계

### 데이터 (마이그레이션 없음)

스레드 reading(`relationships.thread_reading_id`)에 assistant 메시지 **2건**을 남긴다:

1. **카드 스트립** — `content` = `serializeThreadDraw(...)`:
   ```json
   {"v":1,"skill":"checkin","spread":"checkin_6",
    "cards":[{"card_id":12,"direction":"upright","label":"지금의 나"}, …]}
   ```
   `skill_key = 'checkin' | 'deep_feelings'`. 스트림 **시작 전** 저장(뽑은 결과가 먼저 스레드에 눌러앉음).
2. **풀이** — 평문(`[CARD:n]` 마커 포함), 같은 `skill_key`. 스트림 완료 후 저장.

두 건은 `created_at` 자연 순서로 정렬된다(스트립 먼저 insert).

`relationships.memo` 확장/축소:
- **추가** `skill_grace: { key: string; remaining: number } | null` — 캡 면제 잔여 턴. 재구매 시 **누적 가산**(`remaining += graceTurns`). **날짜 만료 없음**(구매한 분량. 패스가 죽으면 대화 자체가 막히므로 악용 여지 없음).
- **재사용** `active_skill` — 인-플라이트 락(`{ key, started_at, assistant_turns:0 }`), 3분 초과 시 stale override(Phase 2 패턴).
- **제거** `pending_skill_recap` — 아래 "제거" 절.
- 종료 시 `appendSkillLog(memo, key, threadReadingId, summary, now)` — `skill_log`만 적립(recap 미설정, compat/verdict와 동일). `summary`는 풀이 마지막 문단(`extractClosingLine` 재사용).

### 개시 (client)

- `useSkillLaunch`: `tarot_draw`도 `compat`/`dialogue`와 **동일 경로** — `onInThreadSkill(skill.key)`. `launchTarotDraw`(sessionStorage + `router.push`)와 `REL_SKILL_KEY`/`RelSkillMarker` 제거.
  - 단 tarot_draw는 개시 시점에 확인 모달을 띄우지 않는다(현행과 동일) — 모달을 열고 **카드를 뽑은 뒤** 확인. 즉 `launch()`의 tarot_draw 분기는 `openConfirm` 대신 `onInThreadSkill`.
- `ThreadChat`: `onInThreadSkill(key)`로 받은 스킬의 `kind`가 `tarot_draw`면 스트림/JSON 대신 **`ThreadDrawModal` 오픈**(state).
- `ThreadDrawModal` (신규, `components/relationship/ThreadDrawModal.tsx`):
  - portal(`document.body`) + `fixed inset-0` dim(`bg-night/70 backdrop-blur-sm`) + 내부 패널(`inset` 여백 + `rounded-3xl` + `overflow-y-auto`).
  - 닫기: ✕ · 배경 클릭 · ESC · **shallow history**(`history.pushState` → `popstate` = 닫기, `ClarifierSheet` 패턴).
  - 본문: `CardDrawRitual`(`cardCount`=`SPREAD_INFO[spread].cardCount`, `slotLabels`=`getPositionLabels(spread,"love",null)`, `accent`=`SPREAD_INFO[spread].accent`, `completeLabel`="이 카드로 볼게").
  - `onComplete(drawn)` → `StarConfirmModal`(`cost`=`skill.starCost`, 잔액 조회) → 확인 시 `onSubmit(drawn)`(부모 = ThreadChat).
  - **실패 시 모달 유지** — 뽑은 카드를 보존하고 재시도 버튼만 노출(카드를 다시 뽑게 하지 않음).

### 채팅 라우트 (`/api/relationship/chat`)

`skillStart` 분기에 tarot_draw 처리를 추가한다(compat/verdict 코드는 불변). body 확장: `{ skillStart, drawnCards? }`.

`skillStart`가 `kind==="tarot_draw"`인 스킬 키일 때:

1. **인-플라이트 락 검사** — `active_skill` 있으면 400(`skill_already_active`). 단 같은 키 + `started_at` 3분 초과면 stale override.
2. **패스 검증** — `getActivePass(rel.id)` 없으면 402(`pass_required`). (현행 `/api/consultations/tarot`가 하던 검증의 이관.)
3. **카드 위조 검증** (`validateDrawnCards`, 순수 함수):
   - 배열 길이 == `SPREAD_INFO[skill.spread].cardCount`
   - `card_id` 정수 + 카드 데이터에 존재 + **중복 없음**
   - `direction ∈ {"upright","reversed"}`
   - `label`은 **클라 값을 버리고** 서버가 `getPositionLabels(spread,"love",null)`의 i번째로 재계산
   - 실패 → 400(`invalid_cards`)
4. **차감** — `spendStars(userId, skill.starCost, { readingId: threadReadingId, source: "rel_skill_" + skill.key })`. 실패 402(`INSUFFICIENT_STARS`).
5. **락 세팅** — `active_skill = { key, started_at: now, assistant_turns: 0 }`.
6. **스트립 메시지 insert** — `{ reading_id: threadReadingId, role:'assistant', content: serializeThreadDraw(...), skill_key: key }`. `.select("id").single()`로 **id를 확보**해 둔다(실패 시 이 row만 정확히 삭제하기 위함).
7. **시스템 메시지** — `buildRelationshipSystemMessage({ fileBlock, isFirstEver:false, dailyClose:false, drawContext: { spreadLabel, cardsBlock: formatDrawnCardsBlock(cards) }, activeSkill: { key, assistantTurns:0, forceEnd:false } })`.
8. **SSE 스트림** — `streamChat(system, apiMessages, 2800, logCtx)`. 최근창은 일반 경로와 동일하게 구성하되(`splitThreadMessages`), 비영속 트리거 user 메시지 `DRAW_KICKOFF`("방금 카드를 뽑았어 — 펼쳐서 봐줘" 류)를 붙여 alternation을 맞춘다(라우트 상단 `VERDICT_KICKOFF`(56행) 옆에 상수 신설, 같은 패턴). `maxTokens` 2800 = 일반 턴 1400의 2배(분량이 상품 — [[reading-depth-and-value-tuning]]).
9. **완료 처리**(한 update) — 풀이 메시지 insert(`skill_key`) + `appendSkillLog` + `grantSkillGrace(memo, key, skill.graceTurns)` + `active_skill = null` + `last_visited_at`.
10. **실패 시** — `spendStars` 이후 어느 단계든 실패하면 `chargeStars` 환불(source `rel_skill_<key>_refund`, 실제 결과를 응답에 반영) + 락 해제 + 스트립 메시지 정리(delete) + `logError`.
- `maxDuration` — 이미 Phase 2에서 300으로 상향됨(추가 변경 없음).
- **민감 감지**: 스킬 개시는 user 발화가 없으므로 `resolveSensitive` 대상 아님(verdict 개시와 동일). 이후 자유 대화는 기존 경로에서 그대로 검사된다.

**일반 메시지 경로 — 그레이스 소진**:
- `skill_grace.remaining > 0`이면: 소프트캡 검사 **우회**(`dailyClose=false`), user·assistant 메시지 둘 다 `skill_key = skill_grace.key`로 태깅(→ `getTodayThreadTurns`가 자동 제외), `remaining -= 1`(한 왕복 = 1턴). `remaining`이 0이 되면 `skill_grace = null`.
- `remaining === 0`이면 현행과 완전히 동일.

**모델 맥락 치환**: `past` 로드 후 스트립 JSON 메시지를 `(별콩이가 관계 체크인 카드를 6장 뽑아봤어)`류 짧은 자연어로 치환(`redactDrawForModel`). Phase 2 `redactCompatForModel`과 **합성**해서 쓴다(`redactDrawForModel(redactCompatForModel(rows))`) — Phase 2 코드를 건드리지 않는 최소 변경. 카드 정보는 풀이 본문에 이미 산문으로 녹아 있어 손실 없음.

### 프롬프트 (`lib/claude.ts` + 신규 가이드)

- `formatDrawnCardsBlock` — private → **export**(관계 라우트에서 재사용). 타로 경로 동작 불변.
- `RelationshipTurnContext`에 `drawContext?: { spreadLabel: string; cardsBlock: string } | null` 추가. 있으면 `dynamicPart`에 `getRelationshipDrawGuide()` + 스프레드 라벨 + 카드 블록 주입.
- `data/persona/byeolkong_relationship_draw.md` (신규) — 인-스레드 카드 풀이 가이드:
  - 구조: 자리별 해석(각 단락 앞에 `[CARD:n]` 단독 줄) → 여섯 장을 잇는 종합 흐름 → 이 관계에 지금 필요한 처방 1~2개 → 따뜻한 마무리 한마디.
  - 스레드 맥락(관계 파일 · 호칭 · 그동안의 기억)을 카드 해석에 **엮으라**는 지시.
  - **`[END]`·`[SKILL_DONE]` 금지**(스레드는 계속됨). 질문으로 끝내지 말고, 이어 얘기할 여지를 남기는 마무리.
  - 분량 지침(카드 수 × 자리별 + 종합 + 처방 → 일반 턴의 2배 수준).
  - `{호칭}` 플레이스홀더는 **예시 대사에 넣지 않음**(Phase 1에서 모델이 토큰째 출력한 사고 — [[relationship-skills-inthread-rework]]).

### 클라이언트 렌더

- `components/relationship/ThreadCardStrip.tsx` (신규) — 스트립 카드: 헤더(스킬 이모지 + 라벨 + "6장") + 카드 그리드(`public/cards-webp` 이미지 + 포지션 라벨 + 역방향 표기/회전) + 탭하면 확대(라이트박스 또는 확대 토글).
- `ThreadChat` 메시지 렌더 분기(compat 카드 분기와 나란히):
  - `tryParseThreadDraw(msg.content)` 성공 → `ThreadCardStrip`.
  - 그 외 assistant 메시지에 `[CARD:n]`이 있으면 → `splitByCardMarker(text)`로 단락 분할 후, 각 단락 앞에 **카드 칩**("자리 · 카드이름 (역)") 렌더. 칩 라벨은 해당 메시지 **직전의 가장 가까운 스트립 메시지**(backward scan)의 n번째 카드에서 가져온다.
  - `[CARD:n]` 마커 자체는 화면에서 제거(기존 `MARKER_REGEX` 계열과 동일 처리).
- 스트리밍 중: 클라가 **자기가 뽑은 카드로 스트립을 낙관적 렌더**(서버 저장본과 라벨이 동일 함수 결과라 일치) + 아래에 스트림 버블. 생성 중 채팅 입력 비활성(`drawLoading`, Phase 2 `compatLoading` 패턴).
- 새로고침 후: 서버 저장본(스트립 + 풀이)이 그대로 렌더 → 영속.

## 흐름 (end-to-end)

```
연애 상담 스레드
  └─ 스킬 칩/시트 "관계 체크인"
       └─ ThreadDrawModal (여백 모달 · 뒤 스레드 비침)
            CardDrawRitual: 덱 스와이프 → 6슬롯 FLIP → 정/역 선택
            └─ 확정 → StarConfirmModal(45⭐)
                 └─ POST /api/relationship/chat { skillStart:"checkin", drawnCards }
                      서버: 락 → 패스 → 카드 검증(label 재계산) → 45⭐ 차감
                          → 스트립 메시지 저장 → SSE 스트림(관계 시스템 + 드로우 가이드 + 카드 블록, 2800토큰)
                          → 풀이 저장 + skill_log + 그레이스 10턴 적립 + 락 해제
                 └─ 클라: 모달 닫힘 → 스트립 카드 → 풀이 스트리밍([CARD:n]→칩)
                      └─ 이어서 자유 대화 (이후 10턴은 하루 캡 미가산) — 전부 같은 스레드
```

## 엣지 / 무결성

- **중복 개시(더블탭)**: 클라 `sending`/`activeSkill`/모달 단일성 1차, 서버 `active_skill` 락 2차 → 이중 차감 방지. 3분 stale override로 크래시 복구.
- **카드 위조**: 장수·중복·존재·방향 검증 + label 서버 재계산. 클라가 보낸 label은 신뢰하지 않음.
- **패스 없음**: 402(`pass_required`) → 클라가 패스 시트 오픈.
- **잔액 부족**: 402 → `/shop`.
- **차감 후 실패**: 환불(실제 `chargeStars` 결과 반영, 실패 시 `logError`) + 락 해제 + 스트립 메시지 정리 + 모달 유지(카드 보존, 재시도 가능).
- **그레이스 × 캡**: 그레이스 턴은 `skill_key` 태깅으로 `getTodayThreadTurns`에서 제외 → 하루 마무리 톤(`dailyClose`)도 걸리지 않음. 그레이스 소진 후 캡 동작은 현행과 동일. 스킬 재구매 시 잔여에 누적.
- **그레이스 중 다른 스킬 개시**: 허용(그레이스는 락이 아님). 새 스킬의 그레이스가 잔여에 가산되고 `key`는 최신 스킬로 갱신(태깅용).
- **모델 오염**: 스트립 JSON은 최근창에서 치환되어 모델이 JSON을 보지 않음(별콩이가 되뇌지 않음). 연속성은 풀이 본문 + `skill_log`로 유지.
- **일반 타로 회귀**: `/tarot/draw`에서 관계 분기만 제거 → 피커 → draw → reading → result 경로는 코드 경로가 단순해질 뿐 동작 불변. `/api/consultations/tarot`는 `relationshipId`를 보내는 호출부가 사라진 뒤 제거(무손상 확인 후).
