# 별마루 — 체험 중·체험 전 구독 노출 + 구매 경로 구멍 3개 (2026-10-11)

- 상태: 사용자 승인(2026-10-11 저녁, 전부 추천대로) · **dev 만** · prod 배포 = 메뉴판 판정(10-25 21:29 KST 이후 실행) 뒤 사용자 go
- 원설계(`2026-09-04-별마루-2-구독게이트-design.md` §3 "체험 소진 시에만 구독 CTA")를 이 문서가 바꾼다

## 1. 진단 (prod 09-28~10-11, 지인 6명 제외)

가입 388 → 별마루 113 → 절단선 51 → 체험 21 → 만료 16 → **만료 후 재방문 2** → 구독 CTA 노출 2 → 클릭 0

- 구독 버튼은 `trialUsed && !entitled` 에서만 뜬다 — **체험 72시간 동안엔 어디에도 없다**
- 체험자 17/21 이 가입 40분 안에 시작, 18명이 ~6분 안에 별마루를 떠났다. 서비스 전체 다른 날 재방문 6.2%
- → 0건은 상품 매력에 대해 아무 말도 안 한다(0/2). 선택지를 **체험 중·첫 세션**에 보여줘야 판단이 시작된다

## 2. 결정 (사용자 2026-10-11)

1. 체험 중 구독의 30일 = **체험이 끝난 뒤부터**. 체험 전에 사면 체험 3일 + 30일. SQL 불변 — TS 가 `p_days` 를 계산
2. 안 1 — ① 체험 중: 유료 리포트 끝 넛지(사주·타로·우리 세 탭) ② 체험 전: 절단선 캡션 자리에 '바로 구독' 링크
3. 문구 = §3-2 (초안 그대로)
4. 가격 20별 유지
5. 충전하고 돌아오면 구독창 자동 재오픈
6. 배포는 메뉴판 판정(10-25) 뒤
7. 별마루 잔액 부족은 Meta AddToCart 에서 뺀다(AddToCart = 타로 광고 최적화 신호)
8. 성공 기준 = §6

## 3. 설계

### 3-1. 구매 일수 — `lib/byeolmaru/subscribe-offer.ts` `subscriptionPurchaseDays` (순수 함수 · 유닛 테스트)

| 단계 | 판정(computeEntitlement 결과) | p_days | 체험 기록 |
|---|---|---|---|
| 체험 전 | 비자격 · trialUsed=false | 30 + 3 = **33** | 성공 뒤 `trial_started_at = now`(startTrial 그대로 — NULL 일 때만) |
| 체험 중 | reason=trial | 30 + **남은 체험(시간 기준 올림)** | — |
| 체험 후 | 비자격 · trialUsed=true | 30 | — |
| 구독 중 | reason=subscription | 30 (RPC 가 활성 만료 뒤에 이어 붙인다) | — |

- 경계: 남은 71.9h → 3일 · 0.1h → 1일 · 정확히 48h → 2일. 올림이라 남는 몇 시간은 유저 몫이다
- RPC `purchase_byeolmaru_subscription` 은 `GREATEST(활성 만료, now()) + p_days` 그대로다. 체험은 구독 행이 아니라 RPC 가 모르므로, 남은 체험을 TS 가 일수에 더한다
- 체험 전 구매에 체험을 기록하는 이유: 안 하면 33일이 끝난 뒤 '3일 무료 체험'이 다시 뜬다(trialUsed=false)
- ⚠️ 부작용: 체험 전·중에 산 구독 행은 30일보다 길다(최대 33일) — 어드민 구독 기간·방문일 분모가 그만큼 늘어난다. 체험 전 구매자는 `trial_started_at ≈ 구독 started_at`(수 초 차)로 가려진다

### 3-2. 노출

| 단계 | 자리 | 내용 | surface |
|---|---|---|---|
| 체험 전 | 절단선 캡션(주 버튼은 체험 그대로) | "체험 끝나면 20별 / 30일 · 바로 구독하면 체험 3일 + 30일 →" | `cut` |
| 체험 중 | 유료 리포트 바로 아래(세 탭) — `TrialSubscribeNudge` | "체험 D-{n}야. 지금 구독해 두면 체험 끝난 다음부터 30일 이어서 받아." · [이어서 구독하기 · 20별] · "자동결제 아니야 — 20별 한 번이면 끝." | `report_end` |
| 체험 후 | 허브 배너 · 절단선 · 받은 글 아래 안내 | 기존 그대로 | `banner` · `cut` · `kept_report` |

- 넛지 조건 `entitled && !subscriptionExpiresAt`(= 체험 중). 금색·자물쇠·'끝나면 못 봐' 금지(페르소나 원칙) — 보조 스타일 한 줄 + 버튼 하나, 화면당 하나
- D-N 은 HubBanner 와 같은 계산(올림·최소 1) — `daysLeft` 하나를 둘이 같이 쓴다
- 구독 확인창 부제는 단계별: 체험 전 "체험 3일 + 30일" / 체험 중 "체험 끝난 다음부터 30일" / 체험 후 지금 문구

### 3-3. 충전하고 돌아오기

- 잔액 부족 → 확인창 [별 충전하러 가기] 와 서버 402 **둘 다** 그 자리 `RechargeSheet`(need=20 · 잔액 전달 · source `byeolmaru_subscribe`). FortunePurchasePanel 관례대로 열릴 때만 마운트
- returnTo = 지금 경로 + `bm_sub=<surface>`. 결제 성공 → /shop 이 returnTo 로 돌려보냄 → 돌아온 화면이 **자격을 읽은 뒤 한 번만** 확인창을 다시 열고 표시를 주소에서 지운다
  - 주소 정리는 `history.replaceState(history.state, "", …)` — null 로 덮지 않는다(첫 로드에 Next 의 `__NA` 상태가 지워진다) · `router.replace` 금지(대기 중인 이동을 버린다)
  - 이미 구독 중이면 안 연다(다른 탭에서 샀을 수 있다)

## 4. 같이 고친 구멍 3개

1. **연타 이중 차감** — 확인·체험 시작에 ref 동기 잠금(state 만으론 같은 틱 연타를 못 막는다) + 버튼 '여는 중…' + 진행 중 확인창 닫기 막음
2. **충전 후 미복귀** — §3-3
3. **500 미로깅** — `subscription.ts` 가 에러를 돌려주고 라우트가 402 외 실패를 `logError`(402 는 설계된 정상 신호라 안 남긴다)

덤: 구독 성공 뒤 `byeolkong:balance-updated` — 다른 구매 경로와 같이 헤더 잔액이 바로 줄어든다.

### 4-1. 서버 쪽 중복 방어 — 판단: 지금은 클라 잠금으로 충분(미구현, 제안만)

- 남는 구멍 = 두 탭·두 기기 동시 구매. RPC 가 `star_balances FOR UPDATE` 로 직렬화하므로 둘째 요청은 **이어 붙이기(+30일, 20별 더)**가 된다 — 돈이 사라지진 않지만 의도치 않은 연장
- 마이그레이션 없이 가능한 것: 라우트가 RPC 전에 "이 유저의 60초 안 구독 행"을 보고 있으면 차감 없이 그 만료로 200. 순차 중복(첫 요청 커밋 뒤 도착)은 막지만 **진짜 동시**(둘 다 커밋 전 조회)는 못 막는다 — 그건 RPC 안 잠금 아래로 옮겨야 한다(SQL 변경)
- 규모(4주 구매 1건 안팎)에서 비용 대비 이득이 작다 → 판독 SQL 의 '같은 유저 1분 안 구독 행 2개'로 감시하고, 한 건이라도 나오면 그때 넣는다

## 5. 계측

- 새 `byeolmaru_subscribe_offer_shown{surface, phase, slot?}` — 구독 선택지가 그려질 때 마운트당 1회(체험 전 링크·체험 중 넛지·체험 후 배너/절단선/받은 글 안내 전부)
- `byeolmaru_subscribe_clicked` · `byeolmaru_subscribe_completed` 에 `surface`·`phase`(+ completed 는 재오픈 구매면 `resumed:true`)
- 새 `byeolmaru_subscribe_failed{status: 402|500|기타 숫자|"network", surface, phase}`
- 충전 시트 source `byeolmaru_subscribe` — `paywall_shown{surface}`·`recharge_sheet_opened{source}` 둘 다 **Meta AddToCart 에서 제외**(`rechargeCapiEventId`)
- 기존 `byeolmaru_gate_shown` 은 추세 잇기용으로 그대로
- ⚠️ `byeolmaru_trial_started` 는 잠금 때문에 events 수가 줄어든다(실인원 불변) — **배포 전후 events 수 비교 금지**
- 판독: `scripts/byeolmaru-subscribe-offer-check.sql`(읽기 전용 · `params.deploy_at` 필수). 어드민 `admin_byeolmaru_funnel` 은 이벤트 4개 고정이라 새 이벤트를 안 본다 — 이 판독은 SQL 로 한다

## 6. 성공 기준 (배포 후 4주 · 실인원 · 지인 6명 제외)

- 체험 중 노출 ~40명 중 클릭 0 → **상품·가격**
- 클릭은 있는데 충전에서 멈춤 → **현금 장벽**
- 구매 4명+ → **유지**
- 기대치는 4주 구매 1건 안팎(0건 확률 ~30%) — 0건으로 실패를 단정하지 말고 **막힌 단계**로 판정한다
- 즉시 조치 고장: 구독 500 1건 · 완료 이벤트인데 구독 행 없음 · 같은 유저 1분 안 구독 행 2개

## 7. 배포·확인

- prod 는 메뉴판 판정 뒤 사용자 go. 배포 시각을 판독 SQL `params.deploy_at` 에 넣는다
- 배포 뒤 사용자 실결제 1회 확인(prod 구매 경로는 한 번도 실행된 적 없다): 잔액 부족 → 충전 시트 → 토스 결제 → 별마루 복귀 → 구독창 자동 재오픈 → 구독 → 20별 차감(헤더) → 배너 '구독 중 · D-N'
