## 3. 설계

### A. 코어 §5 정정 (무조건 → 조건부)

| 현재 | 정정 |
|---|---|
| "기본값은 ②③④(질문 아님)" | "세션 정보의 **`턴 마무리 상태`**를 따른다" |
| "넉넉잡아 세 턴에 한 번 이하로" | **삭제** — 상태가 대체 |
| "유저가 방금 알려줬으면 새로 캐묻지 말고" | "받아 안은 **다음**, 그 정보에 이어지는 구체 질문 하나는 괜찮아" |
| §심문피로 "유저 답 길이와 무관하게" | "**단답이 2회 연속되면**" (원 진단 복귀) |
| "직전 턴이 질문이면 이번 턴 질문 금지" | **유지** (발동 2.1%로 무해, 원 진단에도 있음) |

### B. ② 를 진짜 고리로

"답을 요구하지 않기" → **"유저가 답하고 싶어지게 열되, 물음표는 안 써"**

예시문을 구 코호트 실제 성공 문장으로 교체:
- "약속 날짜 정해지면 어떻게 정해졌는지 **들려줘**. 그거 들으면 흐름이 더 또렷해져."
- "뭐가 제일 지치게 만들었는지 **한 장 더 펼쳐서 볼 수도 있어.**"

### C. 첫 풀이 (C1) — §6 조건부화

"첫 풀이는 디테일 질문으로 닫지 마" → **"유저 고민이 40자 미만으로 짧으면 첫 풀이 맺음에 디테일 하나를 청해도 돼"**

### D. 서버 3상태 — 상한만 정하고 모델이 내려감

`lib/claude.ts` `TurnSignals` 확장. `turnClose: "ask" | "invite" | "settle"`.

```
settle  ← userShortStreak(단답 2연속)
          OR computeWrapMode(...).mode !== "free" (수렴·마무리 구간)
ask     ← [첫 턴이 아닐 때] 유저가 방금 물음표를 씀
                            OR 이번 발화가 직전 발화보다 20자 이상 길다
          ← [첫 턴일 때]    readings.question 이 40자 미만 (이것만)
invite  ← 그 외 (기본값)

후처리: lastTurnEndedWithQuestion 이면 ask → invite 로 강등
우선순위: settle > ask > invite (settle 조건이 하나라도 맞으면 settle)
```

🔴 **첫 턴에는 물음표·성장 게이트를 쓰지 않는다** (2026-09-12 품질 리뷰 반영). 프로덕션에서 첫 턴의 `currentUserText` 는 유저가 쓴 **고민 본문 그 자체**다(클라가 `concern` 을 첫 메시지로 보낸다). 고민 끝의 물음표는 "되물어달라"는 신호가 아니라 어법이라, 이걸로 `ask` 를 주면 재료가 충분한 긴 고민(40자 이상 = **69%**)에도 첫 풀이를 되묻기로 닫게 된다 — 코어 §6 이 막으려던 '첫 답변 직후 심문 2연속'이 정확히 그것이다.

⚠️ **판독 주의**: 연애 상담 라우트는 `ctx` 를 넘기지 않아 하루 소프트캡 마무리 턴에도 유저가 물음표를 쓰면 `ask` 가 기록된다. 행동은 코어 §5 의 "(세션 정보에 수렴/마무리 지시가 오면 그 지시가 우선)"이 덮지만, `turn_close × 다음 턴 생존` 교차 시 **`dailyClose` 턴을 제외**할 것.

**구현 가능성 확인됨**: `reading.question` 은 `app/api/consultations/tarot/chat/route.ts:106` 의 select 에 이미 포함돼 있고, `wrapMode` 는 같은 라우트 195행에서 `computeTurnSignals` 호출 전에 계산된다 — 인자로 넘기면 된다. `computeTurnSignals` 시그니처가 `(pastMessages, currentUserText)` 에서 `(pastMessages, currentUserText, ctx)` 로 확장된다(ctx = `{ wrapMode, questionLen, isFirstTurn }`).

**모델은 상한 안에서 내려갈 수만 있다** — `ask` 가 떠도 내용상 물을 게 없으면 `invite`/`settle` 로 내려도 되고, 위로는 못 올린다. `buildTurnSignalBlock` 이 이 계약을 명시적으로 서술한다.

`SHORT_LEN = 12` 는 현행 유지 — 실측 유저 발화의 **22.2%가 12자 이하**라 단답 판정으로 타당하다(2연속 조건까지 걸리면 더 좁아진다).

⚠️ §3-A 가 남기는 페르소나 규칙("직전 턴이 질문이면 이번 턴 질문 금지")과 여기 후처리는 **의도적 이중 방어**다. 충돌 시 **서버 상태가 authoritative** — 페르소나 문구에 그렇게 명시한다.

🔴 **다만 프롬프트 블록 안에서는 이중 방어를 하지 않는다** (2026-09-12 품질 리뷰 반영). `turnClose` 가 있으면 `lastTurnEndedWithQuestion`·`userShortStreak` 경고는 **처방 없이 근거만** 내보낸다. 두 신호는 이미 상태에 수학적으로 흡수돼 있고(질문 2연속 → `ask` 강등, 단답 2연속 → `settle` 강제), 처방을 중복하면 `settle` 상태에서 경고줄이 "정리·**예고**·여백"이라며 ②(다음 볼거리 예고)를 다시 허가해 **상태 계약을 깨뜨린다.** 이중 방어는 서로 독립적인 방어일 때 싼 것이지, 한쪽이 다른 쪽을 무효화할 때는 아니다.

🔴 **§위기가 이 블록보다 항상 우선이다.** `buildTurnSignalBlock` 은 `crisisActive` 와 무관하게, 그리고 `CRISIS_STAY_GUIDE` **뒤에** 주입되므로 블록 헤더에 위기 최우선을 명시하지 않으면 위기 확인 질문을 덮는다(§4 "위기 안전망은 건드리지 않는다"와 직결).

- 🔴 **관계 스레드 스킬 발화의 상태화** (2026-09-12 품질 리뷰가 escalate) — `app/api/relationship/chat/route.ts` 의 assistant insert 는 **5곳**이고(궁합 / 카드뽑기 스트립 / 카드뽑기 해석 / 판정 도입 / 일반 턴) 그중 **일반 턴 1곳만** `turnClose` 를 받는다. 나머지 4곳은 애초에 `turnSignals` 를 계산하지 않는 별개 빌더 경로다.
  - 특히 **카드뽑기 해석**(`drawText`, `streamChat` 실시간 생성)은 유저가 별을 쓴 직후 받는 진짜 페르소나 응답이라 "무언 이탈"과 맥이 닿는다. 여기까지 확장할 값어치는 있다.
  - **그런데 이번 범위에 넣지 않는다**: ① 측정된 문제(무언 이탈 27%)는 `consultation_type='tarot'` 에서 잰 것이고 관계 스킬에서 잰 게 아니다 ② 관계 스킬층은 실측상 거의 죽어 있다(스킬 4종 08월 총 1회) ③ 새 빌더 경로를 뚫는 건 이 태스크의 코어 편집과 성격이 다르다.
  - 필요해지면 **별도 태스크**로. 그때까지 `turn_close IS NULL` 은 "계측 누락"이 아니라 "상태 대상이 아닌 발화"를 포함한다(마이그레이션 주석에 명시).
- 사주·연애상담·시뮬의 회귀 QA 범위 — 코어 편집이라 필요하나, 구현 플랜에서 다룬다
