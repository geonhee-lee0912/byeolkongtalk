# 별콩톡 앱 전환 — 상위 설계 (하위 프로젝트 분해)

- 날짜: 2026-10-12
- 상태: 사용자 검토 대기 → 승인 시 하위 프로젝트 ①부터 상세 설계 → writing-plans
- 근거 논의: 메모리 `ad-dependency-structure-2026-10-11` (10-11~12 세션)
- 관련 설계: `specs/2026-09-06-타로톡-연속기억-design.md` · `specs/2026-10-11-타로-로그인전-맛보기-design.md`

이 문서는 **무엇을 왜, 어떤 순서로** 만드는지 정한다. 하위 프로젝트마다 상세 설계와 계획은 따로 쓴다.

## 1. 왜 하나

**문제는 첫 방문이 아니라 재방문이다.**

- 가입의 98.5%가 메타 광고를 거쳐 온다(07-26~10-03 가입 2,029명 중 1,999명). 광고 없이 오는 가입은 주 3명 정도이고, 검색 유입은 8월 이후 주 8~16명에서 그대로다.
- 매출의 85%가 가입 7일 안에서 나온다. 가입 후 14일 안에 다른 날 다시 오는 사람은 9.1%다.
- 메타에 가입 한 명당 약 ₩380을 내고, 가입 한 명에게서 7일간 약 ₩232를 번다. 광고비가 매출의 약 165%다.
- 광고비를 2.1배로 늘리자 가입은 1.46배, 매출은 1.08배에 그쳤다(10-04~09). 09-20에는 우리 쪽 변화 없이 첫 리딩 전 결제율이 5.6%에서 0.8%로 떨어졌다. 결과는 광고가 누구를 보내느냐에 달려 있다.

**진단**

- 첫 방문의 결제는 웹 탓이 아니다. 같은 웹에서 결제율이 7% 안팎이었다.
- 재방문은 웹이 구조적으로 막는다. 유입 대부분이 인스타그램 앱 안 브라우저이고 아이폰이 74%다. 이 조합에는 돌아올 아이콘도, 알림도 없다.
- 이 업계 1위권(점신·포스텔러·헬로우봇)은 모두 앱이다. 헬로우봇은 정해진 시간에 보내는 푸시로 하루 이용자를 최대 30% 늘렸다(2021).

**검토하고 버린 대안**

- **카카오톡 채널**: 메시지 가이드의 '미신 조장 금지' 조항이 운세에 적용되는지 불확실하다. 채널 메시지 발송 API가 없어 사람이 직접 보내야 하고, 사람마다 다른 문구를 못 보낸다. 광고성 메시지는 밤에 못 보내고, 매일 보내면 비용이 매출보다 크다.
- **웹 푸시**: 아이폰은 '홈 화면에 추가'한 웹앱만 받는다. 인스타에서 빠져나와 거기까지 가는 데 4단계가 걸려서 소수만 닿는다.
- **캘린더 '다시 볼 날'**: 비용이 0이고 쓸 만하지만 1회성이다. 매일 들르는 습관은 못 만든다.

**결론**: 앱은 재방문의 필요조건일 가능성이 높다. 다만 충분조건은 아니다. 문을 다는 것과 함께 들어올 이유(다시 볼 날, 이어서 묻기, 데일리)를 같이 만든다.

## 2. 확정된 결정 (사용자, 2026-10-11~12)

| D2 | 광고는 앱 설치로 보낸다(B) | 앱이 심사를 통과하기 전까지는 지금처럼 웹으로 보낸다 |

| D9 | 사업자 | 개인사업자·간이과세자를 유지하고, 업종 '응용 소프트웨어 개발 및 공급업(722000)'을 추가한다 |

## 3. 범위

### 하는 것
- iOS·Android 앱(웹 감싸기)을 만들어 한국 스토어에 낸다
- 로그인: 앱은 카카오(네이티브) + 애플, 웹은 카카오 + 애플
- 앱 결제: 애플·구글 인앱결제로 별을 충전하고, 환불되면 별을 회수한다
- 푸시: 다시 볼 날 · 이어서 묻기 · 별마루 데일리, 광고 수신 동의 관리
- 웹 (C): 알림을 고르는 순간 "알림은 앱에서" 안내 + 스토어 링크
- 계측: 앱 유입과 웹 유입을 나눠 보고, 메타 앱 설치 광고를 측정한다
- 스토어 심사 대응 자료

### 이번에 안 하는 것
- 위젯, 카카오톡 채널, 웹 푸시, 캘린더 기능
- 앱 전용 네이티브 화면 재작성(심사에서 막힐 때만 한다)
- 카카오 계정과 애플 계정 합치기(수요를 보고 나중에)
- 해외 출시(한국 스토어만 낸다 → 해외 매출 영세율 처리도 사실상 없다)
- 가격 재설계(보류 결정에 따른다)

## 4. 전체 구조

```
 [앱: React Native(Expo) + 웹뷰]
   ├─ 웹뷰가 byeolkongtalk.com 을 불러옴 (처음엔 화면·기능 전부 웹)
   ├─ 앱 쪽(React Native)이 맡는 것: 푸시 · 스토어 결제 · 카카오 SDK 로그인 · 애플 로그인 · 딥링크 · 토큰 보관
   ├─ 웹 ↔ 앱은 정해진 메시지 형식으로 주고받음 (로그인 요청·결과, 알림 허용, 결제 등)
   ├─ 웹이 알아볼 수 있게 UA 에 앱 꼬리표를 붙임 (예: "ByeolkongApp/1.0 (ios)")
   └─ 출시 후 핵심 화면부터 리액트 앱 화면으로 하나씩 전환 (토큰으로 API 호출)

 [웹 (Next.js, 기존)]
   └─ "앱 안인가"를 감지해서 로그인 버튼 · 결제 수단 · 알림 안내를 앱 방식으로 바꿈
      (웹 브라우저에서는 지금 그대로 + (C) 안내)

 [서버 (Next.js API, 추가)]
   ├─ 네이티브 로그인 토큰(카카오·애플)을 검증하고 세션 발급
   ├─ 스토어 결제 검증 → charge_stars(거래 ID로 멱등) → payments 기록
   ├─ 스토어 환불 알림 수신 → 별 회수
   └─ 푸시 기기 등록 · 예약 알림 발송(Vercel cron)

 [DB (추가)]
   로그인 수단(애플) · 스토어 결제 기록 · 푸시 기기 · 알림 동의 기록 · 예약 알림
```

- **React Native(Expo) + 웹뷰를 고른 이유** (10-12 사용자 확정, 확장성 기준. 맥·테스트 아이폰 있음):
  - 앱 화면을 같은 리액트로 한 화면씩 늘려 갈 수 있다. Capacitor는 앱 전용 화면을 Swift·Kotlin으로 따로 만들어야 한다
  - 리액트로 만든 앱 화면도 규정 범위 안에서 심사 없이 업데이트할 수 있다(EAS Update)
  - 생태계·채용 시장이 크고, React Native 공식 문서가 Expo를 권장한다. 카카오 로그인 라이브러리도 국내에서 널리 쓰인다
  - 심사에서 '웹 포장' 지적을 받으면 해당 화면만 앱 화면으로 바꾸기 쉽다
  - 비용: 웹 ↔ 앱 메시지 연결을 직접 설계해야 하고, Expo를 1년에 1~2번 업그레이드해야 한다. Capacitor보다 첫 출시가 조금 늦다
  - 검토한 다른 길: Capacitor(가장 단순하지만 앱 화면 확장이 어렵다), React Native 전체 재작성(몇 달, 지금은 아니다), TWA(안드로이드 전용)
- 웹뷰 화면의 업데이트는 지금처럼 웹 배포로 끝난다. 스토어 심사는 앱 쪽 코드(네이티브 모듈·권한·설정)를 바꿀 때만 받는다.
- **로그인 상태는 두 가지로 유지한다.** 웹뷰 안은 지금처럼 우리 도메인의 httpOnly 쿠키. 앱 화면과 앱 쪽 API 호출은 토큰(액세스 + 리프레시, 기기 보안 저장소에 보관). 웹뷰와 앱 화면은 쿠키를 공유하지 않기 때문이다(D3-2).

## 5. 하위 프로젝트 (이 순서로 만든다)

각 항목은 **목표 · 핵심 내용 · 끝났다는 기준**으로 적는다. 상세 설계와 계획은 착수할 때 따로 쓴다.

### ① 앱 껍데기 + 로그인 (기반)

- Expo 프로젝트(iOS·Android)를 만든다. 웹뷰로 원격 웹 로딩, 앱 안 감지, 웹 ↔ 앱 메시지 형식, 딥링크(알림 → 특정 화면), 오프라인 안내 화면을 넣는다.
- **토큰 인증을 처음부터 만든다**(D3-2): 앱 로그인 성공 시 액세스·리프레시 토큰을 발급해 기기 보안 저장소에 보관하고, 서버 API가 쿠키와 토큰을 둘 다 받게 한다. 웹뷰에는 한 번 쓰고 버리는 교환 코드로 쿠키 세션을 만들어 준다(상세는 ① 설계).
- **카카오 네이티브 로그인**: 카카오톡 앱으로 로그인 → 액세스 토큰 → 새 서버 엔드포인트가 카카오에 검증 → 세션을 발급한다. 지금 웹은 서버 리다이렉트 방식이라 이 경로가 새로 필요하다.
- **애플 로그인**: 앱은 네이티브, 웹은 Sign in with Apple JS. 아이디 토큰을 서버가 애플 공개키로 검증한 뒤 세션을 발급한다.
- **계정 구조를 카카오 전용에서 다중 로그인으로 바꾼다.** 영향 범위(코드 확인, 10-12):
  - `users.kakao_id` 가 `BIGINT UNIQUE NOT NULL` 이다. 애플 가입자는 `kakao_id` 가 없다
  - 웰컴·첫충전 보너스의 중복 방지(`bonus_claims.kakao_id_hash`)와 재가입 추적(`account_withdrawals.kakao_id_hash`)이 카카오 ID 해시에 묶여 있다 → 로그인 수단별 식별자 해시로 일반화해야 한다(기존 카카오 해시와 충돌하지 않게)
  - 탈퇴(`app/api/auth/withdraw`)가 카카오 unlink만 한다 → 애플 토큰 revoke를 추가한다(애플 요구사항)
  - 결제 확인(`app/api/payment/confirm`)·첫충전 자격(`app/api/stars/first-charge-status`)·어드민 사용자 화면이 `kakao_id` 를 읽는다
- 카카오 토큰은 지금도 서버에 저장하지 않는다(콜백에서 한 번 쓰고 버림). 애플 지침 5.1.1(v)의 '소셜 토큰을 기기 밖에 저장하지 말 것'과 맞는다. 이 상태를 유지한다.
- **개발용·실서비스용 빌드를 나눈다.** dev 사이트는 Vercel 접근 보호가 걸려 있어 웹뷰에서 열리지 않는다 → 보호 우회 토큰을 쓰거나 로컬 서버로 테스트한다.
- **끝났다는 기준**: 테스트 기기(아이폰·안드로이드)에서 카카오·애플 각각으로 가입·로그인·탈퇴가 되고, 웹 기능이 앱 안에서 정상 동작한다. 웹 브라우저의 기존 카카오 로그인에는 변화가 없다.

### ② 앱 결제

- 별 패키지를 스토어 소모성 상품으로 등록한다. 가격은 보류 결정이 나온 뒤 정한다(애플 가격 칸에 맞는 금액인지 확인).
- 구매 → 서버 검증 → `charge_stars(userId, amount, 거래ID, 'iap_apple'|'iap_google')` → `payments` 에 기록한다(`pg_provider` 'apple'/'google', `pg_tid` = 거래 ID, 기존 유니크 인덱스로 중복 차단).
- 환불 알림(애플 App Store Server Notifications v2, 구글 실시간 개발자 알림)을 받으면 별을 회수한다.
- 첫충전 보너스, 잔액에 맞춘 패키지 제안 같은 기존 결제 로직을 앱 결제에도 적용한다.
- 앱 안에서는 토스 결제와 "웹이 더 싸다"류 안내를 숨긴다.
- 구현 방식은 결정이 필요하다(§10): RevenueCat(검증·환불 알림 대행, 월 매출 2,500달러까지 무료, 외부 처리위탁 추가) vs 직접 구현(StoreKit 2 + 구글 결제 API).
- **끝났다는 기준**: 샌드박스 구매와 환불이 별 잔액에 정확히 반영되고, 어드민 매출에 스토어 결제와 수수료가 따로 잡힌다.

### ③ 푸시 + 연속 기억

- **기기 등록**: FCM을 쓴다(아이폰은 FCM이 APNs로 전달). 알림 허용은 첫 리딩 끝에 '다시 볼 날'을 고를 때 요청한다. 앱을 처음 켤 때 바로 묻지 않는다.
- **광고 수신 동의**: 앱 푸시 매체로 따로 받는다. 미리 체크해 두지 않고, 동의 시각을 기록한다. 야간 별도 동의는 받지 않는다 → 광고성 알림은 21시~08시에 보내지 않는다.
- **알림 세 가지**

  | 알림 | 언제 | 분류 | 비고 |
  |---|---|---|---|
  | 다시 볼 날 | 사용자가 고른 날(3일/1주/2주 뒤) 1회 | 정보성 여지 | 사용자가 직접 요청한 1회성. 홍보·결제 권유 문구 금지 |
  | 이어서 묻기 | 리딩 N일 뒤 1~2회 | 광고성으로 취급 | '(광고)' 표기, 동의자에게만 |
  | 별마루 데일리 | 매일 아침 8~9시 | 광고성으로 취급 | '(광고)' 표기, 동의자에게만 |

- **문구 규칙**
  - 고민 내용을 절대 넣지 않는다(잠금화면에 그대로 보인다)
  - 위기 신호(`has_sensitive`)가 있던 사용자에게는 판매성 알림을 보내지 않는다
  - 불안을 자극하지 않는다(별콩이 페르소나 원칙)
- **법적 뒷정리**: 동의·철회 후 14일 안에 처리 결과를 알린다(앱 팝업 가능). 2년마다 수신 동의를 다시 확인한다. 수신 거부 화면으로 바로 연결한다.
- **발송**: Vercel cron(예: 15분 간격)이 예약 알림을 처리한다. 기존 cron은 `/api/cron/ad-spend-sync` 하나다.
- **연속 기억**: 09-06에 설계·계획한 연속 기억(`specs/2026-09-06-타로톡-연속기억-design.md`)을 이 단계와 함께 실행한다. '이어서 묻기'를 눌렀는데 별콩이가 지난 고민을 모르면 알림의 약속이 거짓이 된다(표시광고법상 기만 소지). 계획은 메뉴판 이후 코드에 맞춰 다시 점검한다.
- **끝났다는 기준**: 테스트 기기에서 세 가지 알림이 오고 눌렀을 때 맞는 화면으로 간다. 동의하지 않은 사람에게 광고성 알림이 가지 않고, 21시~08시에는 광고성 알림이 나가지 않는다.

### ④ 웹 (C) 안내 + 계측

- 웹에서 '다시 볼 날'이나 데일리 알림을 고르는 순간 "알림은 앱에서 받을 수 있어"와 스토어 링크를 보여 준다(아이폰·안드로이드를 구분).
- `page_views.browser_env` 에 앱 값을 추가하고(`lib/analytics/pageview.ts` `detectBrowserEnv`), 어드민에서 앱과 웹을 나눠 본다.
- 메타 앱 설치 광고용 SDK를 붙인다(설치·구매 이벤트). 아이폰 추적 허용 팝업(ATT)을 언제 띄울지 정한다.
- **끝났다는 기준**: 웹에서 스토어로 넘어간 수가 계측되고, 앱 유입·결제가 어드민에 따로 보인다.

### ⑤ 출시 · 심사 · 광고 전환

- **스토어 준비물**: 아이콘·스크린샷·설명, 애플 개인정보 라벨, 구글 데이터 보안 양식, 연령 등급, 지원 URL. 개인정보 처리방침과 약관도 고친다(푸시 토큰, FCM을 통한 해외 이전, 스토어 결제·환불).
- **구글**: 출시 전에 테스터 12명이 14일 연속으로 비공개 테스트를 해야 한다 → 웹의 안드로이드 유저를 베타 테스터로 모집한다(별 선물). 빌드가 나오는 날 바로 시작한다.
- **애플**: TestFlight → 심사. 다음 항목의 소명 자료를 준비한다.
  - 4.2 웹 재포장 아님: 푸시, 네이티브 로그인, 인앱결제
  - 4.3 운세 분야 차별점: AI 대화형 타로, 기억하는 상담, 캐릭터
  - 4.8 애플 로그인
  - 5.1.1 앱 안 탈퇴
- **광고**: 아이폰·안드로이드 앱 설치 캠페인을 따로 만든다. 웹 캠페인에서 예산을 단계적으로 옮긴다.
- **끝났다는 기준**: 두 스토어에 출시되고, 첫 앱 설치 광고가 집행된다.

## 6. 성공 기준 (출시 후 판정)

- **1순위**: 앱 설치 1건당 30일 매출 vs 앱 설치 1건당 광고비. 웹 기준선은 가입당 광고비 약 ₩380, 가입당 7일 매출 약 ₩232다.
- **재방문**: 앱 유저가 14일 안에 다른 날 다시 오는 비율. 웹 광고 유입 기준선은 9.1%다.
- **보조**: 푸시 허용률, '다시 볼 날' 설정률과 그날 실제로 돌아온 비율.
- **수수료 본전선**: 앱이 가입 한 명당 약 ₩35(가입당 매출 ₩230 × 15%) 이상을 더 벌게 해야 수수료를 메운다.
- 판정 기간과 기준치는 출시 전에 따로 미리 정한다(사전 등록). 고래 1명, 공휴일, 성숙도를 통제한다(메모리 `meta-purchase-optimization-2026-08-14` 의 판정 규율).

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|
| 애플 4.3(운세 포화)·4.2(웹 재포장)로 반려 | 앱다운 기능과 차별점을 소명한다. 막힌 화면만 네이티브로 바꾼다. 최악의 경우 안드로이드 앱 + 아이폰은 웹 |
| 앱 설치 광고 단가가 웹 가입 단가보다 높음 | 출시 초기에는 소액으로 시작해 웹과 비교한다 |
| 한 사람이 두 로그인으로 계정을 2개 만듦 | 앱 로그인 화면에서 '기존 회원은 카카오'를 안내한다. 계정 병합은 수요를 보고 나중에 |

| 수수료 15% | 본전선(가입당 약 ₩35 추가 수익)으로 판정한다 |
| 푸시 피로로 알림을 끔 | 빈도를 제한한다(데일리 하루 1회 + 이벤트성 알림 리딩당 최대 2회) |
| 미성년 결제 취소·분쟁 | 스토어 환불 정책을 따르고 약관에 반영한다. AI 청소년 보호 법안(국회 상정 보도) 동향을 주시한다 |
