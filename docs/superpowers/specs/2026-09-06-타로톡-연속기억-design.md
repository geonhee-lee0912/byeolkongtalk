# 타로톡 연속 기억 (크로스-리딩 유저 기억) — 설계

- 날짜: 2026-09-06
- 상태: 설계 확정 대기 → (승인 시) writing-plans
- 관련: 백로그 #13(연속기억) · `lib/relationship/memory.ts`(참고 원본) · `lib/continuation.ts`(기존 얇은 다리)

## 1. 배경 / 문제

타로톡은 **리딩(reading)마다 완전히 독립**이다. 유저가 다른 날(또는 같은 세션에서 곧바로) 돌아와 새 타로톡을 결제하고 고민을 입력해도, 별콩이는 그 유저의 과거 상담을 **전혀 기억하지 못한다**.

- fresh 리딩엔 과거 맥락 주입 훅이 **없다**. `previous_reading_id`(이어가기)가 있을 때만 chat 라우트가 "지난 고민 1줄 + 마지막 한마디 1줄"을 주입한다(`app/api/consultations/tarot/chat/route.ts:139-164` + `lib/claude.ts:buildContinuationBlock`).
- 그런데 그 **이어가기 자체가 사실상 안 쓰인다** — prod 타로 1,780건 중 `previous_reading_id` 세팅은 **34건(1.9%)**. 버튼이 눈에 안 띄고 잘 안 눌린다.

**원하는 것(사용자 시나리오):**
> 타로톡으로 상담 → 다른 날(또는 곧) 돌아와 **그냥 다시 결제 → 고민 입력 → 별콩이가 과거 대화를 기억해 이번 고민에 자연스럽게 활용**. 버튼 없이 자동.

## 2. 목표 / 비목표

**목표**
- fresh 타로 리딩에서 별콩이가 그 유저의 **최근 타로 상담**을 자동으로 기억해, 이번 고민과 이어지면 자연스럽게 참조한다.
- 완전 무음(버튼·배지 없음). 유저는 평소 결제 흐름 그대로.
- 서로 다른 고민을 가로질러 기억(크로스-고민)하되, **적당히**(최근 위주, 오래된 건 압축·감쇠).

**비목표 (이번 스코프 밖)**
- 사주 연속 기억 — 저장소만 확장 가능하게 열어두고 이번엔 미적용.
- 이어가기(deep, 정가×0.6) 상품의 존치/폐지 결정 — 별개 트랙. 이번엔 손대지 않는다(자동 기억과 공존).
- "기억 중" 같은 UI 노출. 신뢰·발견성용 배지도 이번엔 없음.
- 별콩이가 과거 대화를 **원문**으로 회상하는 것 — 요약만 주입(세부는 흐릿, 단정 금지).

## 3. 데이터 근거 — "적당히"의 폭 (prod, 지인 6명 제외)

| 지표 | 값 | 함의 |
|---|---|---|
| 타로 리딩 / 유저 | 1,780건 / 1,539명 | |
| 재방문 유저(2+ 리딩) | 188명 = **12.2%** | 대부분 1회성 |
| └ 딱 2개 | 170명 = 재방문의 **90.4%** | 돌아온 사람의 90%는 "직전 1개"만 |
| └ 3개+ | **18명** = 전체 1.2% (최대 21) | 깊은 히스토리는 극소수 — **그래도 커버 대상** |
| 재방문 간격(중앙값) | **0.01일(~15분)** | 상당수 같은 세션 연속 뽑기 |
| 간격 ≤1 / ≤7 / ≤30 / ≤60일 | 82.6% / 91.7% / 97.5% / **100%** | **60일 창이면 전부 커버** |
| 대화 길이(중앙값) | 8메시지(별콩이 4턴), p90 14 | 리딩 하나가 짧음 → 요약 작아도 됨 |
| [END] 종료율 | **68.4%** | **32%는 종료 안 침** → 접기 시점 함의 |
| 이어가기(previous_reading_id) | 34건 = 1.9% | 사실상 안 씀 |
| 민감 리딩(has_sensitive) | 0건 | 제외 가드는 공짜 안전장치 |

**결론(폭):**
1. **개수** — 롤링 요약을 **개수로 하드컷하지 않는다**. 오래된 리딩을 버리지 않고 **압축**해 다층 아크를 담되, **문자 상한 ~800자**로 bounded. 90%(직전 1개)에겐 "직전 상담 기억", 18명(최대 21회)에겐 상한 안에서 압축된 전체 흐름. → 18명까지 커버.
2. **기간** — **60일 창**. 60일 넘은 리딩은 접기·소환 제외(잃는 것 0, 오래된 게 불쑥 튀는 것 방지).
3. **접기 시점** — 종료율 68%뿐이라 "[END] 시 접기"는 32%를 잊는다. **"다음 fresh 리딩 생성 시" 접기**로 종료·중도이탈 모두 커버.

## 4. 설계 개요

관계 스레드(`lib/relationship/memory.ts`)의 롤링 요약 패턴을 **유저 레벨**로 이식한다. 단, 타로는 관계보다 **단순**하다 — 크로스-리딩 기억은 **과거 리딩의 요약 1개**만 주입하면 되고, 과거 원문 메시지를 재생하지 않는다(현재 리딩의 within-reading 원문은 기존대로 클라 `body.messages`가 담당). 따라서 관계의 "최근창 원문 + 요약" 혼합(`splitThreadMessages`)이 **필요 없다**.

```
[fresh 리딩 생성 POST]
   └─ 직전 미접기 리딩(들)을 접어 유저 요약 갱신 (동기, 게이트, best-effort)
[해당 리딩의 매 chat 턴]
   └─ 유저 요약을 system dynamicPart에 "## 지난 상담 기억" 블록으로 주입 (무음)
```

- **저장 단위**: 유저 × 종목(현재 'tarot'). 신규 테이블 `consultation_memory`.
- **접기(fold)**: 새 리딩 생성 시 = 직전 리딩(들)은 이미 끝난 것 → 미접기분을 haiku로 요약해 유저 요약에 누적(압축), 커서 전진.
- **주입(inject)**: 매 chat 턴 요약 블록을 dynamicPart에 삽입(유저별이라 정적 캐시 불가).

## 5. 데이터 모델 — 신규 테이블 `consultation_memory`

```sql
CREATE TABLE IF NOT EXISTS consultation_memory (
  user_id           UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  consultation_type VARCHAR(10) NOT NULL,          -- v1: 'tarot' (후속: 'saju')
  summary           TEXT,                           -- 롤링 요약 본문 (bounded)
  folded_upto       TIMESTAMPTZ,                    -- 커서: 접기 완료한 가장 최근 리딩의 created_at (NULL=아직 없음)
  updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, consultation_type)
);
ALTER TABLE consultation_memory ENABLE ROW LEVEL SECURITY;  -- 정책 없음 = service_role만
```

- `users(id)` FK는 **ON DELETE CASCADE**(회원 탈퇴 시 자동 정리 — AGENTS.md FK 규칙).
- RLS 활성 + 정책 없음. 서버 라우트는 `getServiceSupabase()`(service_role)로만 접근. AGENTS.md의 DB 권한 기본값(신규 객체 anon/authenticated 차단)과 이중 방어. 새 SECURITY DEFINER RPC는 없음(직접 테이블 접근만).
- 관계는 `rolling_summary`/`summarized_msg_count`를 엔티티(`relationships`)에 뒀지만, 타로는 스레드 엔티티가 없고 주체가 **유저**라 유저 키 테이블이 자연스럽다.

## 6. 접기(fold) 로직 & 시점

**시점**: `POST /api/consultations/tarot`에서 리딩 insert + `spendStars` 성공 직후, 응답 반환 **전**(동기). 이 POST는 카드 뽑은 뒤 결제 시점이라 채팅 첫 턴보다 앞서고, 요청 안에서 처리하면 **서버리스 fire-and-forget 사망 문제가 없다**(관계 chat은 스트림이 함수를 살려둬서 fire-and-forget이 가능했지만, 이 POST는 빨리 반환하므로 await가 안전).

**게이트(latency 보호)**: 접기 대상(아래 조건) 리딩이 **하나도 없으면 haiku 호출 스킵**. 첫 리딩·미접기분 없음 = 90%+ 케이스는 추가 지연 0. 재방문·미접기분 있는 유저만 +1~2s(카드 뽑고 리딩 페이지로 넘어가는 사이에 흡수).

**"계산 대상" vs "요약 대상" 분리** (커서 정확성):
- **계산 대상(커서가 다루는 범위)** = 해당 유저의 타로 리딩 중 `folded_upto < created_at < (이번 새 리딩.created_at)` 전부. 커서는 접기 여부와 무관하게 이 범위의 **max(created_at)**(=직전 리딩 시각)으로 전진한다. → 민감·60일초과로 스킵한 리딩이 커서 앞에 남아 매번 재스캔되는 것 방지.
- **요약 대상(실제로 haiku에 넣는 부분집합)** = 계산 대상 중 추가로
  - `has_sensitive = false` (민감 제외 — 안전)
  - `created_at >= now() - interval '60 days'` (60일 창)
  - 실제 messages가 있는 것(빈 리딩 제외)

**접기 실행**:
1. 요약 대상 리딩들의 messages를 시간순으로 모아 리딩별 블록으로 구성:
   `[YYYY-MM-DD] 고민: {question}\n{유저/별콩이 발화 요지}` (마커 제외).
2. 요약 대상이 비어있지 않으면 `newSummary = summarizeReadingsForMemory(prevSummary, blocks)` — §8 규격, haiku, 상한 ~800자. (비어있으면 요약 스킵, 요약 본문은 유지.)
3. `upsert consultation_memory (user_id, 'tarot', summary := (요약했으면 newSummary, 아니면 기존), folded_upto := max(계산 대상.created_at), updated_at := now())`.
   - 계산 대상 자체가 비면(직전 리딩 없음) 전체 스킵 — upsert도 안 함.
4. **best-effort**: 접기 실패는 `logError`(warn)만 하고 리딩 생성/응답을 막지 않는다. 기억은 부가가치, 상담이 우선.

**멱등**: 커서(`folded_upto`)로 재접기 방지 — 커서는 계산 대상 max로 항상 전진하므로, 스킵된(민감·오래된·빈) 리딩도 다시 스캔되지 않는다.

## 7. 주입(inject) 로직

**시점**: 타로 chat 라우트(`app/api/consultations/tarot/chat/route.ts`)에서 system 메시지 구성 전, 유저 요약 1건 로드:
`select summary, folded_upto from consultation_memory where user_id=? and consultation_type='tarot'`.

**주입 조건**(둘 다 만족 시):
- `summary` 비어있지 않음.
- **신선도 게이트**: `folded_upto >= now() - interval '90 days'`. (60일 창으로 접으니 정상 재방문은 항상 통과. 90일+ 휴면 유저의 낡은 요약은 소환 안 함 — "지난번 이직 얘기"가 반년 전이면 어색.)

**주입 위치**: `buildTarotSystemMessage`(`lib/claude.ts`)의 **dynamicPart**. 유저별이라 정적 캐시(`cache_control ephemeral`) 불가 — 반드시 동적 블록. 기존 이어가기 블록(`buildContinuationBlock`)과 **공존**(둘 다 있으면 나란히).

**주입 블록 형식**(`buildTarotMemoryBlock`):
```
## 지난 상담 기억 (이 유저와 나눈 과거 타로 상담 요약)
{summary}
- 이번 고민과 자연스럽게 이어지는 대목이 있으면 가볍게 참조해. 억지로 다 끌어오지 말 것.
- 관련 없으면 언급하지 않는다.
- 과거는 요약이라 세부가 흐릿할 수 있으니 단정하지 말고 부드럽게 확인하듯.
```

**적용 범위**: fresh + 이어가기(deep/fresh) 모든 타로 리딩의 chat에 주입(유저 레벨 기억이라). 위기(`crisisActive`) 대화에서도 주입은 무해하나, 요약 자체에 위기 내용이 없으므로(민감 리딩 접기 제외) 안전.

## 8. 요약 프롬프트 규격 — `summarizeReadingsForMemory`

`lib/claude.ts`의 `summarizeOlder`(관계용)와 같은 계열의 신규 함수. 저비용 요약 모델(haiku `claude-haiku-4-5-20251001`, 관계와 동일).

- **입력**: `prevSummary`(기존 요약, 없으면 빈 문자열) + `blocks`(이번에 접을 리딩들의 날짜·고민·발화 요지).
- **출력 계약**:
  - 한국어 불릿. **날짜 + 고민 태그**를 각 항목에 (`- 8월말: 이직 고민 — 아직 결정 못함, 상사와 갈등`).
  - **최근 1~2개는 또렷이**, 그 이전은 짧은 테마 한 줄로 **압축(버리지 말 것)**. → 18명(최대 21회) 아크 유지.
  - **상한 ~800자**. 초과 시 오래된 항목부터 더 압축(개수 삭제가 아니라 문장 축약).
  - 사실·중립. 위기/자해/민감 세부는 담지 않는다(민감 리딩은 애초에 입력 제외지만 프롬프트에도 명시).
  - 별콩이 화법을 흉내내지 말 것 — 이건 기록 요약이지 상담이 아님.
- **파라미터**: `max_tokens` ~700, `TAROT_MEMORY_CAP` 상수로 후처리 절단(문장 경계 보존 — 관계 `cleanSummary` 재사용 가능).

## 9. 안전 / 프라이버시

- **민감 제외**: `has_sensitive=true` 리딩은 접기 입력에서 제외. 위기 대화가 나중 리딩에 불쑥 소환되는 것 차단. (현재 prod 민감 0건이나 가드는 공짜.)
- **무음**: UI 노출 없음. 별콩이 말로만 자연 회상.
- **신선도 게이트**: 90일+ 휴면 요약 미주입(§7).
- **탈퇴**: `ON DELETE CASCADE`로 자동 삭제.
- **요약 절단 = 압축**: "몇 번째만 고정" 식 truncation 금지(백로그 #13 규율) — 크기는 상한으로만 cap.

## 10. 비용

- **접기**: 재방문·미접기분 있는 유저만 리딩당 haiku 1회(~₩1 미만). 90%+ 케이스 스킵.
- **주입**: dynamicPart ~800자(≈800토큰) × 리딩당 별콩이 4턴 ≈ 3.2k 입력 토큰/리딩. luna 입력가에서 리딩당 ~₩1 미만. bounded라 flat.
- 백로그 #13 함정(전체 transcript 매턴 재주입) 회피 — 요약만 주입.

- **유닛**(`lib/reco`류처럼 계약): 주입 게이트(빈 요약·90일 stale 시 미주입) 순수 함수화해 검증.

- **QA 하네스**(톤): 과거 요약 있는 상태로 fresh 리딩 첫 턴이 (a) 관련 시 자연 참조 (b) 무관 시 미언급 (c) 단정 안 함. ⚠️ 화법 위반은 정규식/LLM judge로 못 잼 — 표본 골라 육안(메모리 `measure-persona-by-reading-not-matching`).
- **dev 서버 재시작** 후 검증(모듈 캐시).
- **라이브 E2E**: dev에서 유저 세션 주입 → 리딩 A 완료 → 리딩 B 생성 시 `consultation_memory` upsert 확인 + B 첫 턴 system에 블록 주입 확인.

## 13. 미해결 / 리스크 / 플랜 확인 사항

- **생성↔첫턴 타이밍 재확인**: `POST /api/consultations/tarot`가 카드 뽑은 뒤 결제 시점이라 첫 chat 턴보다 앞선다(코드 확인). 플랜에서 리딩 페이지 진입~첫 턴 사이 실제 순서 한 번 더 확인.
- **접기 latency**: 재방문·미접기분 유저만 +1~2s(게이트로 90%+ 무영향). 허용 가능하나 실측 관찰.
- **크로스-고민 혼선**: 서로 다른 고민이 한 요약에 섞임 → 고민·날짜 태그로 완화, 완전 제거는 아님(사용자 감안 완료).
- **이어가기와의 관계**: 자동 기억이 이어가기의 "이어서 상담" 가치를 정가 fresh 흐름에 얹음. 이어가기 존치/폐지는 별 트랙(비목표).
- **베이스라인**: 이 기능 목적은 재방문율(현 12.2%) 상향. 배포 후 재방문·2회차 전환 관찰로 효과 판독.

## 14. 후속 (이번 스코프 밖, 열어둠)

- 사주 연속 기억: 저장소가 `consultation_type` 키라 `'saju'`로 확장 가능.
- 접기 안전망: 만약 생성 훅이 놓치는 경로가 발견되면 chat 첫 턴 lazy 스윕 추가(현재 불필요).
- (선택) 발견성 배지: 효과 확인 후 무음 유지 vs 미세 노출 재검토.
