## 4. 설계 ② — API 원가 로깅

이 프로젝트의 **유일한 신규 인프라**.

### 착점 3곳

| # | 위치 | 성격 |
|---|---|---|
| 1 | `lib/claude.ts:500` `streamChat` | 모든 **스트리밍**의 단일 통로 (어댑터 3종을 덮음) |
| 2 | `lib/claude.ts:912` `anthropic.messages.create()` | 관계 기억 롤링 요약(haiku) — 비스트리밍이라 streamChat을 안 탄다 |
| 3 | `lib/sensitive.ts:155` `anthropic.messages.create()` | 민감 2차 판정(haiku) — **대화 턴마다 호출될 수 있어** 누락 시 원가가 조용히 샌다 |

### 계약 변경 — 바깥 파급 0

```ts
// 어댑터 계약만 바뀐다
- stream(args): AsyncGenerator<string, StopReason>
+ stream(args): AsyncGenerator<string, { stop: StopReason; usage: Usage | null }>

// streamChat 이 usage 를 벗겨 기록하고, StopReason 만 그대로 반환 (시그니처 불변)
```

**호출부 수정 0곳** — 모든 `streamChat` 호출부가 `for await (const chunk of ...)` 형태라 반환값을 이미 버리고 있다. 실제로 읽는 건 `generateOnce` 하나뿐이고 그 계약(`StopReason`)은 유지된다.

프로바이더별 usage 수신:
- **anthropic**: `message_start`(input·cache_read·cache_creation) + `message_delta`(output)
- **openai**: `stream_options: { include_usage: true }` **추가 필요** + 마지막 청크의 `chunk.usage` (choices가 비므로 기존 옵셔널 체이닝이 그대로 안전)
- **gemini**: 각 청크의 `usageMetadata` (마지막 값 채택)

### 테이블

```sql
llm_usage (
  id, created_at,
  route, user_id, reading_id,          -- streamChat 이 이미 들고 있는 logCtx 에서
  provider, model,
  tokens_in, tokens_out,
  tokens_cache_read, tokens_cache_write,
  cost_won NUMERIC(12,4),              -- 적재 시점에 확정. NULL = 단가 미확정(0 과 구별)
)
```

> 🔴 **구현 중 확정된 정정 2건 (2026-09-20, 플랜 A 리뷰)**
> - **`cost_won` 은 `INT` 가 아니라 `NUMERIC(12,4)`.** 정수로 반올림하면 캐시 히트 상태의 짧은 대화 턴
>   (₩0.4616)이 통째로 0 이 되는데, 그게 이 서비스에서 **가장 빈도 높은 호출**이다(luna 캐시 히트 99.6%).
>   한 번 0 으로 적재되면 원본은 복구 불가다 — 하필 sonnet→luna 티어링으로 원가를 줄인 바로 그 지점의
>   성과를 못 재게 된다.
> - **`is_free_user` 컬럼은 만들지 않는다.** 적재 시점에 박으면 나중에 결제한 사람의 과거 행이 갱신되지
>   않아 기준이 섞이고, 대화 턴마다 도는 핫패스에 `payments` 조회가 붙는다. 조회 시점에 계산한다:
>   `NOT EXISTS (SELECT 1 FROM payments p WHERE p.user_id = lu.user_id AND p.status='completed' AND p.created_at < lu.created_at)`

- 기록은 **fire-and-forget**(`void insert(...)`). 실패해도 유저 응답에 영향 없음.
- 에러·재시도 경로에서도 **소비된 토큰은 발생하므로 기록한다.**
- `cost_won`을 **적재 시점에 고정**: 단가는 바뀐다(모델 교체·환율). 조회 시 계산하면 과거 원가가 소급 변조돼 손익 추세가 거짓말을 한다. 토큰 수와 확정 원가를 같이 남겨 둘 다 보존한다.
- 단가 테이블은 코드 상수 `lib/claude/pricing.ts`. 현재 모델 **7종**: `gpt-5.6-luna` · `gpt-5-mini` · `gpt-5-nano` · `claude-sonnet-5` · `claude-haiku-4-5` · `gemini-3.6-flash` · `gemini-3-flash-preview`
- **모르는 모델 id → `cost_won = NULL` + warn 로그.** 0으로 위장하지 않는다(0은 "공짜"와 구별이 안 된다).

## 5. 설계 ③ — 무료 상품 공유 퍼널

### 현재 정의 (코드 기준)

- **신규(`is_new = true`)** ⟺ `user_acquisition.utm_source = '<상품>'` → 그 상품 공유·초대 링크를 타고 와서 **가입한** 사람 = 획득
- **기존(`is_new = false`)** ⟺ 코호트엔 있으나 위가 아닌 사람 → 이미 유저였는데 그 상품을 쓴 사람 = 리텐션

### 확인된 결함 3가지

1. **`admin_cohort_payments`에 날짜 창이 없다.** 코호트 전원의 **전 기간** 결제를 합하므로, 무료상품을 만지기 **전**에 낸 돈까지 들어간다. 인과로 읽을 수 없다.
2. **별자리 ④ 결제 섹션은 분모가 0이다.** 멤버 12명이 전원 익명이라 로그인 브리지가 0명. 결제자·결제율·매출·ARPU 4칸이 0 위에서 돈다.
3. **first-touch 귀속이 공유 기여를 가린다.** `byeolkong_acq` 쿠키는 최초 1회만 기록되고 30일간 **덮어쓰지 않는다**(`components/auth/AuthBootstrap.tsx`). 광고로 먼저 왔던 사람이 30일 안에 공유링크로 재방문해 가입하면 `utm_source='meta'`로 기록돼 신규에서 빠진다. 가입의 91%(2,028/2,224)가 광고 경유라 누락이 작지 않을 수 있다.

> **결함이 아닌 것**: 링크의 utm 부착은 정상이다(`lib/byeoljari/invite-link.ts` · `lib/saju-mbti/share-url.ts`, 유닛 테스트 있음). `page_views`에 `utm_source='byeoljari'` 1건 · `'saju_mbti'` 1건 착지 기록이 있다. `user_acquisition`이 0인 이유는 **그 2명이 가입하지 않았기 때문**이다. 배선은 살아 있고 표본이 0이다.

### 설계

**공통 리졸버 `admin_free_share_funnel(p_product)`** 하나로 무료 상품 전체를 같은 정의로 잰다.

- 코호트 판정은 **utm 쿠키에 기대지 않는 착지 브리지**: `page_views`에서 `utm_source=<상품>`으로 착지한 `anon_id` → 같은 anon이 나중에 로그인한 `user_id`. (MBTI가 이미 "익명 완료 → 로그인"에 쓰는 기법과 동일)
- 퍼널 3단: **착지 → 가입 → 결제**. 분모를 착지로 두면 링크 전체 효율, 가입으로 두면 유입 품질 — 둘 다 표시한다.
- 결제는 **착지 이후 것만** 센다: `p.created_at > c.first_touch_at`. 접촉 시각은 3종 모두 존재(별자리 `star_map_members.created_at` · MBTI `ui_events(saju_mbti_completed)` · 별마루 `byeolmaru_*`).
- **라벨 재해석**: 신규 = *획득 매출*(매출로 읽음) / 기존 = *접촉 후 결제 지속률*(리텐션으로 읽음). 지금처럼 나란히 두면 둘 다 매출로 읽힌다.
- **무료 상품을 "전환율"로 재지 않는다.** 2026-08-24 실측에서 무료→결제는 깔때기가 아니라 **역인과**로 판명됐다(무료 먼저 쓰고 결제한 사람 3명, 유의미했던 건 리텐션 쪽 약한 긍정). 무료 상품 KPI는 **①리텐션 리프트 ②경유 가입(바이럴)** 둘이고, 전환율은 2층 안쪽에 "역인과 주의" 라벨을 달아 참고로만 둔다.

## 6. 설계 ④ — 경로 판독기 + 좁은 로깅 3종

### 판독기 (새 로깅 없이)

`page_views` 37,010행이 이미 모든 라우트를 anon 단위·시간순으로 들고 있다. **부족한 건 로깅이 아니라 읽는 화면**이며, 그래서 §2-6의 로그인 누수가 2개월 넘게 안 보였다. 새 로깅은 데이터가 쌓일 때까지 기다려야 하지만 **판독기는 과거 2개월치를 당장 읽는다.**

2층 `UV ▾` 아래에 배치:
- **첫 N스텝 시퀀스** 상위 경로 + 각 경로의 전환율
- **이탈 지점**(마지막 path) 분포
- 경로별 로그인·결제 도달률

세션 정의는 기존 `SESSION_GAP`(30분)을 재사용한다.

### 좁게 추가할 로깅 3종

1. **로그인 실패 사유** — 지금 `/login → /`가 *카카오 동의 취소*인지 *에러*인지 구분되지 않는다. 496명의 처방이 여기서 갈린다.
2. **페이월 노출 시각** — "봤는데 안 샀다"와 "아예 못 봤다"가 지금 같은 0이다.
3. **별마루 공유 링크 utm** (§5)

### 명시적으로 하지 않는 것

- 세션 리플레이 · 히트맵 — 하루 UV 184 표본에서 비용만 크다
- 전면 클릭 트래킹 — `ui_events`가 이미 요지를 찍고 있고, 늘리면 판독기 없이 데이터만 쌓인다
- 체류 시간 · 스크롤 깊이 — 해석이 모호해 판단을 거의 바꾸지 않는다

## 7. 설계 ⑤ — 소표본 게이트 · 정의 통일

### 소표본 게이트

임계 미만이면 숫자를 **흐리게가 아니라 대체**한다. 컴포넌트 하나(`<Metric n min>`)로 전 화면이 같은 규칙을 쓴다 — 화면마다 다른 임계를 쓰면 그게 또 드리프트가 된다.

| 지표 성격 | 임계 | 미만일 때 |
|---|---|---|
| 비율·전환율 | n ≥ 30 | `n=12 · 판단 보류` |
| 분포·교차표 | 셀당 n ≥ 5 | 표를 접고 총계만 |
| 리텐션 곡선·P90 | n ≥ 50 | 곡선 숨김, 원시 카운트만 |
| K-factor·바이럴 계수 | 초대 n ≥ 30 | 계수 숨김, 초대/도착 원시값만 |

주 대상: 무료 상품 3종 · 연애 상담(패스 6 · 시뮬 16).

### 정의 통일

정본 하나를 골라 `lib/admin-metrics.ts`에 박고, 화면은 거기서만 가져다 쓴다. 계약 테스트로 고정.

| 지표 | 충돌 상태 | 처리 |
|---|---|---|
| 오가닉 비율 | utm_source 기준 **0.0%** / 유입기록 없음 **8.8%**(30일 7.5%) / 메모리 3.8% | **정본 = 유입기록 없음.** `utm_source` 기준은 구조상 항상 0이라 무의미하고(값이 meta·ig뿐), "유입 기록이 없다"가 곧 "utm 없이 들어왔다"다. 한계 명시: 쿠키 차단·30일 만료도 여기 섞인다 |
| 결과 열람 | 리딩 기준 **50.7%** / 로드맵 코호트 기준 65% | **정본 = 코호트 기준.** 로드맵 §3 가드레일 베이스라인이 코호트 65%라, 리딩 기준으로 바꾸면 3층 판정과 1층 가드레일이 서로 다른 말을 한다 |
| UV | 페이지뷰 귀속 / 세션 시작 귀속 | **의도된 공존** — 정본화가 아니라 라벨 고정 |
| 가입당 매출 | 캘린더 귀속 / 코호트 귀속 | 09-19 분석이 코호트로 정정 — 코호트 채택 |
| 어드민 제외 | `account_withdrawals`에 `user_id`가 없어 제외 불가 → 탈퇴율 소폭 과대 | 화면에 한계 명시 |

마이그레이션은 타임스탬프 파일명이라 파일 충돌이 없다 — 적용 순서만 공유된다.

**단계 4(2층)부터는 worktree 분리를 검토한다.** `app/admin/**` 대량 신규라 파일 겹침은 0이지만,
`npm run build`·테스트가 상대 세션의 반쯤 편집된 파일 때문에 깨지는 마찰이 남는다.
