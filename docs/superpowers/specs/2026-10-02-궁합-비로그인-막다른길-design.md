# 궁합 구매 칸 비로그인 막다른 길 — 설계 (2026-10-02)

> `/fortune/compat`·`/fortune/compat-social` 의 구매 칸(`DualSajuPicker`)에서 비로그인·내 사주 없는 유저가 갈 곳이 없던 것을, 같은 날 사주 단일 상품 구매 칸(`FortuneSajuPicker`)이 푼 방식으로 푼다.
> 사용자 확정(2026-10-02): 범위 = ①비로그인 + ②로그인·프로필 0 + ③칸에 생일 없는 내 사주 · 방식 = **A**(선례 `pickerGate` 재사용, "내 사주 먼저") · 설계 승인.
> 선례: `specs/2026-10-02-생일벽-인라인-입력-design.md`(이하 "생일 벽 스펙").

## 0. 왜 하는가

두 페이지는 색인되는 상품 페이지이고 `/fortune` 목록에서 들어간다. 지금(코드 읽기, 2026-10-02 최종 리뷰):

- **비로그인** — `GET /api/profiles` 는 비로그인에게 `200 {profiles:[]}` 를 준다 → 빈 칸 2개·빈 목록·꺼진 "궁합 보기". "+ 새 사람 입력"(`DualSajuPicker.tsx:163-169`)은 로그인 확인 없이 열리고, 폼을 다 채워 저장하면 `POST /api/profiles` 가 401(`app/api/profiles/route.ts:78`) → `NewPersonModal.tsx:49-57` 이 "저장을 못 했어. 잠시 후 다시 시도해줄래?" → 다시 눌러도 같은 실패. `CompatInput` 의 로그인 확인은 "궁합 보기"(`openConfirm`)에만 있는데, 두 칸이 차지 않으면 그 버튼이 꺼져 있어 닿을 수 없다.
- **로그인 · 프로필 0** — "+ 새 사람 입력" 은 지인 폼(`ProfileForm mode="acquaintance"`, 관계 = 친구·가족·연인·기타)이라 **나를 '내 사주'(primary)로 넣을 길이 없다**. 나를 지인으로 넣으면 궁합은 보지만, 별마루처럼 내 사주가 필요한 곳에서 다시 막힌다.
- **생일 없는 내 사주**(`/relationship` 내 정보 '생일 몰라요' 저장으로 생긴다) — 마운트 때 첫 칸에 자동으로 들어가고, "궁합 보기"(`canConfirm` 이 두 칸의 `birthDate` 를 요구)가 꺼진 채 이유도 입력 길도 없다(목록에 '생일 미입력' 표시만).
- 가입 때 생일을 받지 않으므로 **처음 온 유저는 ①에서 로그인하고 돌아오면 ②에 떨어진다** → ①만 고치면 막힘이 한 칸 옮겨갈 뿐이다.
- 빈도는 재지 못했다(prod 조회 토큰 미설정). 근거는 코드 경로다.

## 1. 성공 기준

1. 비로그인 방문자는 두 궁합 페이지 구매 칸에서 카카오 로그인으로 가고, 로그인 뒤 **같은 상품 페이지**로 돌아온다.
2. 로그인 · 프로필 0 인 유저가 화면을 떠나지 않고 "내 사주 → 상대" 순서로 입력해 결제 확인 창에 닿는다.
3. 칸에 생일 없는 내 사주가 있으면 그 자리에서 생일을 넣고, 저장 뒤 **칸 배정이 그대로**다(같은 사람이 두 칸에 들어가지 않는다).
4. 새 사람 저장이 401 이면 "다시 시도" 대신 로그인이 풀렸다고 알리고 로그인으로 갈 링크를 준다.
5. 내 사주(생일 있음)가 있는 유저의 궁합 화면은 **불변**이다. 사주 단일 상품 구매 칸도 불변이다(새 사람 저장의 401 문구·링크만 좋아진다).
6. 자리별 "팝업 열기 → 저장"을 **상품별로** 읽을 수 있다.

## 2. 화면 동작 (`DualSajuPicker`)

| # | 상태 | `pickerGate` | 화면 | 저장 뒤 |
|---|---|---|---|---|
| ① | 비로그인 | `login` | "로그인하면 바로 두 사람 궁합을 볼 수 있어." + **카카오로 시작하기** → `/login?next=<cfg.href>` | — |
| ② | 로그인 · 프로필 0 | `birth` | "내 생년월일부터 알려줘. 그다음에 상대를 고르면 돼." + **내 생년월일 입력하기** | 프로필 재조회 → 나를 첫 칸 · 둘째 칸 활성(지금 마운트와 같은 결과) → 상대는 "+ 새 사람 입력" |
| ③ | 어느 칸에 생일 없는 내 사주 | `list` | 두 칸 아래 "내 생일을 알려주면 바로 궁합을 볼 수 있어." + **생년월일 입력하기** | 재조회, 칸 배정 그대로(PATCH 라 내 사주 id 불변) |
| ④ | 그 밖(생일 있는 내 사주 / 지인만 있음) | `list` | 지금 그대로 | — |
| — | 새 사람 저장 401 | — | 오류 줄 "로그인이 풀렸어. 다시 로그인해줄래?" + **다시 로그인하기** → `/login?next=<loginNext>` | — |

- 벽 카드·카카오 버튼 마크업은 `FortuneSajuPicker` 의 것을 그대로 따른다(`#FEE500` · `#3C1E1E` · 말풍선 아이콘 · `py-3.5`). 공용 부품화는 범위 밖(생일 벽 스펙 §7 과 같은 결정).
- 🔴 **저장 뒤 다음 창(상대 입력·결제 확인)을 자동으로 열지 않는다** — 생일 벽 스펙 §3 과 같은 결정(방식 C 기각).
- 🔴 **로그인을 먼저 받는다** — 비로그인에게 입력을 먼저 받으면 로그인 왕복 동안 값을 보관할 장치가 필요하다(생일 벽 스펙 §3).
- 로그인 확인(`/api/auth/me`)이 실패하면 **로그인한 것으로 본다**(`isAuthenticated !== false`) → ② 화면이 뜨고, 버튼을 누를 때 `BirthPromptButton` 이 다시 확인한다(생일 벽 스펙 §4-2 와 같은 정책).
- `CompatInput.openConfirm` 의 로그인 확인은 그대로 둔다(결제 직전 세션 만료 대비).
- 401 문구가 `SelfSajuEditModal` 과 같은 이유: 벽이 생기면 새 사람 팝업에 닿는 사람은 프로필 목록이 보이는(= 로그인한) 사람뿐이라, 401 은 "세션이 풀렸다"는 뜻이다. 409 는 지인 저장(`relationType ≠ self`)에서 나지 않는다 — `route.ts` 의 409 는 self 생성 전용.

## 3. 구조

### 3-1. `DualSajuPicker` (`components/fortune/DualSajuPicker.tsx`)

- 새 prop
  - `loginNext?: string` — 비로그인 카카오 CTA·새 사람 팝업이 로그인 후 돌아올 곳. `CompatInput` 이 `cfg.href` 를 넘긴다(없으면 현재 경로). 🔴 `cfg.type` 으로 경로를 조립하지 말 것 — `compat_social` 의 href 는 하이픈(`/fortune/compat-social`)이다.
  - `birthSurface: BirthPromptSurface`(필수) — `BirthPromptButton` 의 계측 자리(3-5).
- 프로필 조회를 `loadProfiles()` 로 떼어 마운트와 `BirthPromptButton.onSaved` 가 같이 쓴다(`FortuneSajuPicker.loadProfiles` 와 같은 모양).
  - 조회가 실패하면 지금 목록을 유지한다(`Array.isArray(d?.profiles) ? d.profiles : profiles`).
  - `pickerGate({ profiles, lockPrimary: false, authenticated: true }) !== "list"` 일 때만 `/api/auth/me` 를 부른다(프로필 있는 유저는 요청이 늘지 않는다).
  - 내 사주 자동 배정은 `autoSlotSelf`(3-2)가 true 일 때만 한다 → 첫 칸에 넣고, 둘째 칸이 비었으면 둘째 칸을 활성.
- `pickerGate` 결과로 분기: `login` → 카카오 카드 / `birth` → 생일 카드 / `list` → 지금 피커 + ③ 안내.
- ③ 안내 조건: 두 칸 중 하나의 프로필이 `isPrimary && !birthDate`. 칸 버튼(`<button onClick>`) **밖**, 칸 그리드 바로 아래에 둔다(`BirthPromptButton` 배치 제약 — onClick·submit·키 이벤트 조상 금지).
  조상 체인 확인(2026-10-02): 페이지 `<main>` → `CompatInput <main>` → 피커 루트 `<div>` 모두 핸들러 없음(`AppShell`·`app/fortune/layout.tsx`·루트 레이아웃 포함).
- `NewPersonModal` 에 `loginNext` 를 넘긴다.

### 3-2. 순수 판단 (node:test)

**`components/fortune/dual-picker.ts` — `autoSlotSelf`**

```ts
export function autoSlotSelf(input: {
  selfId: string | null;
  slotA: string | null;
  slotB: string | null;
}): boolean; // = !!selfId && slotA === null && slotB !== selfId
```

- 🔴 지금 마운트 코드(`if (self) { setSlotA(self.id); setActive("B"); }`)를 저장 뒤 재조회에 그대로 쓰면, ③에서 나를 **둘째 칸**에 둔 채 저장했을 때 첫 칸에도 내가 들어가 같은 사람이 두 칸이 된다(`canConfirm` 의 `slotA !== slotB` 에 걸려 버튼이 꺼진다).
- 테스트 5분기: ①첫 조회(두 칸 빔) → true ②내 사주 없음 → false ③첫 칸에 이미 나 → false ④첫 칸 지인 · 둘째 칸 나 → false(중복 방지) ⑤첫 칸 빔 · 둘째 칸 지인 → true.

**`components/saju/profile-save-error.ts` — `profileSaveErrorMessage(status)`**

- 401 → "로그인이 풀렸어. 다시 로그인해줄래?" / 409 → "이미 저장된 사주가 있어. 새로고침하고 다시 열어줄래?" / 그 외 → "저장을 못 했어. 잠시 후 다시 시도해줄래?"
- `SelfSajuEditModal` 의 삼항식을 이 함수 호출로 바꾼다(같은 세 문구 — 동작 동일). 두 팝업의 문구가 따로 놀지 않게 하는 단일 원천이다.
- 테스트: 세 분기 + 문구 고정(400·500 은 기본 문구).
- 네트워크 예외 문구("연결이 잠시 흔들렸어. 다시 시도해줄래?")는 각 팝업에 그대로 둔다(상태코드가 없는 경로).

**`pickerGate`** — 로직 불변. 머리 주석에 궁합 피커가 `lockPrimary: false` 로 쓴다는 것만 더한다(기존 테스트 ⑤ "지인만 있음 → list" 가 궁합에서도 의도된 동작이라는 근거).

### 3-3. `NewPersonModal` (`components/fortune/NewPersonModal.tsx`)

- 새 prop `loginNext?: string`. 없으면 `window.location.pathname + window.location.search`(`BirthPromptButton` 과 같은 기본값).
- 응답 실패 → `profileSaveErrorMessage(res.status)`. **401 이면 오류 줄 아래 "다시 로그인하기" 링크**(`/login?next=<loginNext>`).
- 오류 줄은 뜰 때 보이는 곳으로 당긴다(`scrollIntoView({ block: "nearest" })` + `role="alert"`) — 저장 버튼 아래 줄이 짧은 화면에서 가려지는 문제(생일 벽 Task 3 실측)가 이 팝업에도 같다. 로그인 링크가 그 줄에 붙으므로 보여야 한다.
- 소비처 둘 다 `loginNext` 를 넘긴다: `DualSajuPicker`(cfg.href) · `FortuneSajuPicker`(이미 받는 `loginNext` 를 그대로 — `FortunePurchasePanel` 이 cfg.href 를 넘긴다).
- 입력값은 로그인 왕복에 보관하지 않는다(벽 뒤라 이 경로는 세션 만료뿐이다).

### 3-4. `CompatInput` (`components/fortune/compat/CompatInput.tsx`)

- `DualSajuPicker` 에 `loginNext={cfg.href}` 와 `birthSurface`(`compat` → `compatPicker`, `compat_social` → `compatSocialPicker`)를 넘긴다.

## 4. 검증

1. 단위(`node --import tsx --test`): `autoSlotSelf` 5분기 · `profileSaveErrorMessage` · surface 맵 · 기존 `pickerGate` 6분기 그대로.
2. `npx tsc --noEmit` · `next build`.
3. 브라우저 실물(dev, 375×812). 비로그인은 `http://anon.localhost:<port>`(쿠키 분리 — `127.0.0.1` 은 dev 하이드레이션이 안 된다).
   - 비로그인: 두 페이지 구매 칸에 "+ 새 사람 입력" 없음 · 카카오 href = `/login?next=%2Ffortune%2Fcompat` / `/login?next=%2Ffortune%2Fcompat-social`.
   - 프로필 0 dev 테스트 계정(새로 만든다 — `document.cookie` 세션 주입): ② 카드 → 팝업 → 저장 → 첫 칸 나 · 둘째 칸 활성 → 새 사람 입력 → "궁합 보기" 활성 → 결제 확인 창이 뜨는 데까지(별은 쓰지 않는다). `user_profiles` primary 1행.
   - ③: 테스트 계정의 내 사주 생일을 비운 상태에서 안내 → 저장(PATCH) → 칸 배정 불변. 나를 둘째 칸에 둔 경우도 중복 없음.
   - 401: 목록이 뜬 뒤 세션 쿠키를 지우고 새 사람 저장 → 문구 + 링크 href.
   - 회귀: 생일 있는 계정(궁합 피커 지금 그대로) · 사주 단일 상품 "+ 새 사람 입력" 저장.
   - `ui_events` 에 `compat_picker` / `compat_social_picker` 의 `clicked` / `saved`.
4. 검증 뒤 dev 테스트 계정·프로필 정리.

## 5. 범위 밖 (발견만 기록)

- **로그인 · 지인만 있고 내 사주 없음** → 지금처럼 목록(지인 둘로 보거나, 나를 지인 폼으로). 벽으로 막으면 지금 지인 둘로 보던 유저의 화면이 바뀐다.
- **생일 없는 지인**을 칸에 넣으면 "궁합 보기"가 말없이 꺼진다(목록엔 '생일 미입력'). 지인 수정은 생일 벽 스펙도 범위 밖이다.
- 로그인 뒤 `#buy` 복귀 · 카카오 버튼 클릭/벽 노출 계측 — 생일 벽 작업의 '선택' 항목과 같다.
- `SelfSajuEditModal` 401 에 로그인 링크 — `BirthPromptButton` 의 로그인 확인이 실패했을 때만 닿는다.
- 로그인 `next` 가드 우회(`/\evil.com`) — 별도 작업 칩.
