# 사주 운세 개선 — 중복구매 가드 + 리포트 가독성 재설계 (설계)

작성 2026-08-30 · 상태: 설계 확정(사용자 승인), 구현 플랜 대기

두 개의 독립 사안을 한 스펙에 담되, **구현 플랜은 3단계로 쪼갠다**(#1 → L1 → L2/L3).

---

## Part A — 중복구매 가드 (#1)

### 문제 (확인됨)
동일 사주 상품을 다시 사면 **재과금 + 동일 리포트 재생성**된다.
- `/api/fortune/create` 의 중복 방어는 `findRecentDuplicateReading` 하나뿐인데 **창이 60초**(`WINDOW_MS`)다 — 더블클릭·재시도 전용. 60초 후 같은 상품 재구매는 통과.
- `daily`(하루 1건)·`monthly`(월 1건/프로필)만 별도 "이미 본 것 재사용" 로직이 있고, `monthly` 는 피커에 **"다시보기"** 버튼(`/api/fortune/monthly-existing`)까지 있다.
- `saju_full`·`compat`·`compat_social`·신규 15종은 무방비.

전제: 생성 실패 시 리딩 행을 삭제(`failGeneration`)하므로 **"행 존재 = 완료 또는 생성중"** 이다. 따라서 `(user_id, emotion_tag, profile)` 행 조회만으로 "이미 있음"을 판정할 수 있다(monthly 패턴과 동일).

### 목표 동작
같은 사주(프로필)로 이미 본 상품을 다시 누르면 → 재과금 없이 **보관함의 기존 리포트로 유도**. 단, 사용자가 명시적으로 원하면 **[그래도 새로 뽑기 · ⭐N]** 로 재과금 재생성 허용.

### 설계
1. **서버 권위 가드** (`/api/fortune/create`)
   - `daily`/`monthly` 의 기존 단건 처리 아래에, 나머지 사주 상품용 **기존-리딩 조회**를 추가한다.
   - 대상: `base==="saju"` 중 `daily`·`monthly` 를 뺀 전부(saju_full·good_days·신규 15종) + `compat`·`compat_social`.
   - 키: 단일 프로필 상품 = `(user_id, emotion_tag, profile_id)`. **궁합 = 두 프로필** 모두 일치해야 함 — 현재 `profile_id` 는 A 만 저장하고 B 는 `saju_data` JSON 안에만 있으므로, 궁합 dedup 은 A 일치 후보 중 `saju_data` 의 B(또는 이름) 대조로 확정한다(구현 상세).
   - 발동 시: **요청 바디에 `force:true`(재생성 의사)가 없으면** 기존 id 를 `{ id, alreadyOwned:true, cost:0 }` 로 반환(차감·생성 없음). `force:true` 면 정상 생성 경로.
   - 신규 헬퍼 `findExistingFortuneReading(userId, { emotionTag, profileId, base, saju_data? })` — monthly-lookup 패턴 재사용, 시간창 없음(연간 상품도 v1 은 프로필당 1건).
2. **피커 UX** (`FortuneSajuPicker` / `app/fortune/[type]/page.tsx`)
   - `monthly` 전용이던 `reviewableByProfile`/`onReview` 를 **전 상품으로 일반화**. 진입 시 `/api/fortune/<existing 조회>` 로 프로필별 기존 리딩 맵을 받아, 이미 본 프로필엔 구매 대신 **[보관함에서 보기]** 노출.
   - 이미 본 프로필을 그래도 선택하면 확인 모달에 **[보관함에서 보기]**(주) + **[그래도 새로 뽑기 · ⭐N]**(부, `force:true` 로 POST) 두 버튼.
3. **범위/후속**: 연간 상품(2026사주·올해 연애/재물)은 v1 에서 프로필당 1건으로 막고, **연도 갱신(다음 해 새 리포트 허용)은 후속 과제**로 명시.

### 건드리는 파일
`app/api/fortune/create/route.ts` · 신규 `lib/fortune/existing-lookup.ts`(가칭) · `components/fortune/FortuneSajuPicker.tsx` · `app/fortune/[type]/page.tsx` · `components/common/StarConfirmModal.tsx`(부 버튼 슬롯) · 궁합 입력(`components/fortune/compat/CompatInput.tsx`).

### 계약/테스트
- 유닛: `findExistingFortuneReading` 키 매칭(단일/궁합 양방향).
- 회귀: `force:true` 없이는 재과금 0, `force:true` 는 정상 생성. daily/monthly 기존 동작 불변.

## Part B — 리포트 가독성 재설계 (#2)

### 문제
리포트가 `{ intro, sections:[{heading, body}], note }` 인데 `body` 가 **볼드·문단·표·차트·일러스트 없이 `whitespace-pre-line` 한 덩어리 줄글**이다(`GenericReportView`). bespoke(saju_full·monthly·compat)도 유사. 데이터 구조와 렌더 계층 둘 다 "통짜 텍스트".

자산: 우리는 **결정론적 사주 데이터**(오행 분포 `elementCount`, 대운 `calcDaeun`, 사주판 pillars, 절기/일진 `temporal`)를 이미 계산한다 → LLM 환각 없는 시각요소 소스.

### 공용 비주얼 어휘 (목업 승인됨, 6블록)
① 요약 칩 · ② 아이콘 헤더 + 볼드 리드 · ③ 불릿(강점·조심할 점) · ④ 콜아웃(핵심 조언) · ⑤ 오행 차트 · ⑥ 대운 표.

### 원칙
- **텍스트 richness = 마크다운**: LLM 은 `intro`/`body`/`note` 에 **볼드(`**`)·문단(`\n\n`)·불릿(`- `)** 만 쓴다. 경량 렌더러가 React 요소로 해석(`dangerouslySetInnerHTML` 금지). 스키마·JSON 구조는 그대로라 **parse 실패 리스크를 안 늘린다**(과거 fortune-report parse 실패 이력 대응).
- **시각요소 = 결정론 데이터만**: 칩·오행 차트·대운 표·사주판은 서버 계산값으로 렌더. LLM 은 관여 안 함.

### Generic 엔진 변경 (신규 15종 일괄)
- **스키마**(`lib/fortune/generic-report.ts`): `sections[].body` 는 마크다운 문자열(그대로). 섹션에 옵션 `visual?: "elements" | "daeun" | "pillars"` 추가 — 렌더러가 해당 결정론 모듈을 그 섹션에 삽입. 상단 요약 칩 = **결정론 코어**(일간, 오행 최다/최소 — saju 계산값) + **옵션 LLM 값**(행운 색·방향·키워드 — 파싱된 필드가 있을 때만; 없으면 결정론 칩만). 색/방향은 결정론이 아니라 LLM 산출임에 유의.
- **렌더러**(`GenericReportView`): (a) 마크다운 미니 렌더러(`lib/markdown-lite.ts` 신설: 볼드·문단·불릿·개행만), (b) 섹션 헤더에 신규 아이콘, (c) `section.visual` → 결정론 컴포넌트 주입, (d) 상단 요약 칩 행.
- **프롬프트**(`lib/fortune/prompt.ts`): 각 가이드에 "핵심어는 `**볼드**`, 문단은 빈 줄로, 나열은 `- ` 불릿" 지시 추가. 포맷 지시만이라 저위험.

### 결정론 시각 모듈
- 재사용: `ElementBalanceView`(오행), `LifeGraphView`(인생 그래프), `SajuBoard`(사주판/pillars).
- 신설: `DaeunTable`(대운 10년 표 — `calcDaeun` 데이터), 요약 칩 컴포넌트.

### Bespoke 적용
`saju-full`·`monthly`·`compat`·`daily` 뷰에 같은 어휘 적용. 특히 **saju_full(평생사주)** 이 가장 프로즈-헤비 → 칩·오행 차트·대운 표·콜아웃·볼드로 재구성.

### L2/L3 (폴리시)
- **L2 플래그십 일러스트**: 평생사주·팩폭·전생 등 프리미엄에 힉스필드 히어로 일러스트 소수 신규 생성(해당 리포트만).
- **L3 상품별 새 viz**: 오행 상생상극도 · 궁합 매칭도 · 연애/재물 흐름 타임라인 등 상품 맞춤 컴포넌트.
- **기존 별콩이 일러스트 재사용**: 리포트 히어로 헤더 · note 카드 · 엠티스테이트에 기존 캐릭터 일러스트(`byeolkong-*`, `fortune-byeolkong` 등) 배치.
- **구체 목록은 이 단계에서 확정**: 어떤 리포트에 어떤 히어로 일러스트를 넣고 어떤 상품에 어떤 새 viz 를 붙일지는 L2/L3 플랜에서 **상품별로 목록화해 사용자 승인**을 받는다. 힉스필드 신규 생성은 아이콘 때와 동일하게 **항목별 사전 합의 후** 진행(즉흥 생성 금지). 1단계(#1)·2단계(L1)는 신규 에셋 결정이 불필요하다.

### 건드리는 파일(대표)
`lib/fortune/generic-report.ts` · `lib/markdown-lite.ts`(신규) · `components/fortune/GenericReportView.tsx` · `components/fortune/DaeunTable.tsx`(신규) · `lib/fortune/prompt.ts`(가이드 마크다운 지시) · bespoke 뷰(`components/fortune/{saju-full,monthly,compat}/*`, `DailyReportCard.tsx`) · L2/L3 신규 viz 컴포넌트.

### 리스크/완화
- LLM 은 마크다운 텍스트만 → 포맷 리스크 최소. 시각은 결정론.
- 마크다운 렌더러는 자체 미니 파서(볼드/문단/불릿/개행만)로 XSS 무해.
- 스키마 필드 추가(`visual`)는 옵션이라 기존 저장분과 호환.

## 구현 단계 (각 단계 = 별도 플랜)
1. **#1 중복 가드** — 작고 독립적. 먼저 출시.
2. **L1 토대** — 마크다운 렌더러 + 섹션 아이콘 + 오행/대운/사주판/요약 칩. generic(15종) + bespoke 전 상품. 가독성 핵심.
3. **L2/L3** — 플래그십 일러스트 + 상품별 새 viz + 별콩이 일러스트 재사용. 폴리시.

## 범위 밖 / 후속
- 연간 상품 연도 갱신(다음 해 새 리포트 허용).
- prod 배포는 로드맵 dev 누적분과 함께.
