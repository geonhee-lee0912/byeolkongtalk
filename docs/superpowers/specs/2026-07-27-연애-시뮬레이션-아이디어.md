# 연애 시뮬레이션 상품 — 아이디어 등재 (설계 미완)

> 2026-07-27 (day 1). **브레인스토밍 도중 사용자 지시로 중단·등재.** 배치 결정은 E1(하단탭 IA 재설계)에서 전체 상품 위계와 함께. 이 문서는 그때 다시 열 입력값.

## 아이디어 (사용자 원안)

지금 연애 상담 탭이 자유 채팅 + 인-스레드 스킬(사주·타로) 구조인데, 같은 자리에 **연애 시뮬레이션**을 얹는다.
커플이거나 썸 타는 상대를 등록하고 **사주 + MBTI + 평소 성격**을 입력받으면, 별콩이가 그 사람인 척한다.
유저가 상황이나 발화를 입력하면 그 상대가 어떻게 반응할지 시뮬레이션해준다.

## 확정 1건 — 상품 정체 = **리허설 도구**

사용자 결정 (3택 중). "내가 이렇게 말하면?"을 몇 턴 돌려보고, 끝나면 별콩이가 빠져나와 디브리핑한다 — "이 말은 이렇게 들릴 수 있어, 이 부분만 바꿔봐."
유저가 손에 쥐는 건 **보낼 말**이지 예측이 아니다.

기각된 2택과 이유:

| 안 | 기각 사유 |
|---|---|
| 상대 예측 체험 ("걔는 이렇게 나올 거야") | 근거 0인 단정을 파는 구조 = 페르소나 코어 §단정 금지 정면 위반. 기존 `deep_feelings`(40별) 과 파는 값이 겹침 |
| 감정 해소·못 한 말 (이별/짝사랑 대상 카타르시스) | 수요는 가장 셀 수 있으나 이별 코호트 = 위기 신호 최다 코호트. 망상 강화 위험까지 겹침 |

리허설을 고른 실질 이득: **정확도를 주장하지 않아도 되고**(연습이지 예측이 아니므로), **시뮬이 끝나는 지점이 명확해서** 안전망을 별콩이가 회수할 수 있다.

## 열린 1건 — 배치 (E1로 이관)

사용자 지시: *"이걸 연애 상담이랑 합치는 게 좋을지(신규 상품으로), 따로 할지, 아니면 상품만 홈에 모아두는 쪽으로 갈지(지금 탭 구분이 아니라). 하단탭 논의 시점 즈음에 전체 상품(편지 상품·운세 캘린더 등 앞으로 할 것들 포함)을 모아두고 전체 위계를 다시 구성."*

즉 **단독으로 결정하지 않는다.** E1에서 E3(운세 캘린더)·E4(편지교환)·E6(이 상품)을 한 판에 놓고 IA를 다시 짠다.

그때 쓸 판단 재료:

- **인-스레드 스킬 전용은 도달 유저가 사실상 0.** 관계 등록 → 패스 30별 → 스킬 실행 3중 게이트인데, 7/25 기준 관계 등록 누적 15건 중 14건 무발화. 무료 인트로 3턴이 7/26 배포됐지만 데이터 없음. day 7(8/2) rel 게이트 미달 시 rel 광고를 끌 수도 있는 상태 = 그 탭 생존에 새 상품을 통째로 걸기 위험.
- **역방향 가설(검증 안 됨)**: 시뮬이 우리 사이의 등록 이탈을 고치는 도구일 수 있다. 14/15 무발화의 원인은 등록 직후 마주하는 게 *빈 채팅창*이라 뭘 말할지 모른다는 것 — 반면 "걔한테 뭐라고 보낼지 써봐"는 **뭘 해야 하는지가 자명**해서 첫 경험 난이도가 비교가 안 된다.
- **배관상으로는 진입구가 자유롭다.** `relationships` 는 유저당 1개, 상대는 `user_profiles(relation_type='partner')`. 진입구를 어디에 두든 **관계 파일 하나를 공유**하면 이중 등록이 안 생긴다. 배치는 배관 제약이 아니라 순수 제품 결정.

## 설계를 결정할 리스크 3건

### 1. 코어 페르소나와 정면 충돌 — 화자 아키텍처 문제

`data/persona/byeolkong_core.md` 는 *단정 금지 · 따뜻함 · 판단 안 함 · 위기 시 hotline 우선*이 전제다.
그런데 **시뮬 상대는 차갑게 굴고, 회피하고, 화낼 수 있어야 쓸모가 있다.** 안 그러면 무슨 말을 해도 잘 풀리는 판타지 머신이 되고, 그건 연습 도구가 아니라 자기위안 도구다.

→ 별콩이 목소리가 아닌 **별도 화자**가 필요하고, 그 순간 *"역할극 중에 위기 신호가 뜨면 누가 잡나"* 가 새 문제로 생긴다. 역할극 중인 캐릭터는 hotline 안내를 할 수 없다.
⚠️ 코어 편집은 전 종목 전역 변경 = 광범위 회귀 QA. 이 상품 때문에 코어를 건드리는 선택은 비용이 크다.

### 2. 정확도 근거가 0

별콩이는 그 사람에 대해 **유저가 타이핑한 것 말고 아무것도 모른다.** 사주·MBTI를 넣어도 그건 상대의 데이터가 아니라 *유저 머릿속의 상대 모델*이다.
리허설 프레임을 고른 이유가 이것 — "걔는 이렇게 반응해"로 팔면 근거 없는 단정을 취약한 유저에게 파는 것이고, "네 말이 어떻게 들릴지 연습해보자"로 팔면 정직하면서 가치는 그대로 남는다. **마케팅 문구까지 이 프레임을 지켜야 한다.**

### 3. 등록 마찰 — 이미 한 번 데인 실수

우리 사이 등록 15건 중 14건 무발화의 원인은 *값을 보기 전에 입력을 요구한 순서 문제*였다(P&L 2026-07-25 §액션 2).
그런데 이 원안은 사주 + MBTI + 성격 서술로 **입력을 더 늘린다.** 여기서 같은 함정을 밟을 확률이 1순위.
→ 설계 원칙 후보: **사주·MBTI·성격은 게이트가 아니라 옵션 강화재.** 최소 입력(누구랑 / 어떤 상황)만으로 시작되고, 넣을수록 시뮬이 구체해지는 구조.

## 재사용 가능한 배관 (신규 개발 거의 없음)

| 필요한 것 | 이미 있는 것 |
|---|---|
| 다턴 인-스레드 스킬 | `verdict` — `kind:"dialogue"`, `memo.active_skill` 로 상태 추적, 스레드 안에서 수렴. `lib/relationship/skills.ts` 에 항목 추가 + 페르소나 파일 1개 |
| 상대 등록 | `user_profiles(relation_type='partner')` — `POST/PATCH /api/relationship` 에 이미 있음 |
| 관계 파일 | `relationships`(유저당 1) + `buildRelationshipFileBlock` |
| 기억 | `lib/relationship/memory.ts` — 최근 24메시지 원문 + haiku 델타 요약 |
| 과금 | 패스(30/60/100) + 무료 인트로 3턴 + `skill_grace` 캡 면제 |
| 위기 안전망 | `resolveSensitive` 게이트 + `SafetyBanner` (단, 위 리스크 1 때문에 **그대로는 못 씀**) |
| SSE | `/api/relationship/chat` |

**신규가 필요한 것**: MBTI·성격 서술 필드(현재 스키마에 없음 — `grep -ri mbti` 결과 코드 0건, 문서 2건뿐), 시뮬 화자 페르소나, 디브리핑 전환 로직.

## 다음에 이어갈 질문 (미결)

1. **배치** — E1 하단탭 IA에서 전체 상품 위계와 함께 (위 §열린 1건)
2. **화자 아키텍처** — 별콩이가 "연기 중"임을 유지하는 형태(프레임 보존)냐, 완전 별도 화자냐. 위기 감지 주체는 누구인가
3. **입력 범위** — MBTI·성격을 어디까지 받고, 게이트인가 옵션인가
4. **가격** — 패스 포함이냐 별 단건이냐. 리허설 1회 = 몇 턴이 적정인가
5. **디브리핑 형태** — 시뮬이 끝나고 별콩이가 정확히 뭘 건네주는가 (이게 상품의 실제 산출물)
6. **이별·짝사랑 코호트 취급** — 차단이냐, 톤 조정이냐, 디브리핑 강화냐
