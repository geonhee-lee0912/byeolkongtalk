## 1. 가장 큰 결정 — 구독 축을 "앞당겨 보기"에서 "매일 더 깊게"로

**사용자 판단:** "우리 구독의 핵심은 달력에서 당겨 보는 게 아니라(사실상 없어져도 그만),
매일 들어와서 무료보다 더 길고 제대로 된 리포트를 볼 수 있다는 점이다."

**근거 — 이미 실측으로 한 번 결론이 난 건이다.**

- `/fortune/good_days`(택일 상품, 35별): **18명 열람 · 25뷰 · 재방문 0 · 구매 0건.**
  `2026-08-31-별마루-리텐션허브-design.md` §가 직접 이렇게 적었다 —
  *"good_days 구매 0건은 '택일 수요'에 대한 결정적 반증이다. 택일을 구독 히어로로 세우면 안 된다."*
- 그런데 P5(§1·§6)가 *"무료가 30일 등급을 다 봐서 구독이 깊이 하나로 얇아진다"*는 걱정 때문에
  무료선(지나간 날+오늘)을 새로 그어 **"앞당겨 보기"를 두 번째 축으로 만들었다.**
  즉 그 축은 관측된 수요가 아니라 **페이월을 만들려고 역산한 축**이다. 제품 근거가 아니라 가격 근거였다.

⚠️ **공정하게 남길 반론** — "앞당겨 보기"는 택일과 완전히 같지 않다(택일 = "날을 골라줘",
앞당겨 = "흐름을 미리"). 08-31 스펙도 *"리포트일 땐 1회성이지만 캘린더가 되면 축적형으로 성격이 바뀐다"*는
반론을 달아뒀다. **다만 그건 근거 0의 가설이고, 미래 날짜 가치에 대한 유일한 실측은 0건이다.**
P5 §7 스스로도 *"별마루 실사용이 0이라 '날짜 훑기' 가설에 선지불하는 셈"*이라고 썼다.

### 결과

| | 무료 | 구독 20별 / 30일 |
|---|---|---|
| 오늘 사주 | ~456자 (정적) | **~1,800자** 리포트 |
| 오늘 타로 | ~389자 (정적) | **~1,800자** 7블록 리포트 |
| 우리 오늘 | ~350자 (정적) | ~1,200자 (P5-5 그대로) |
| 달력 | 지나간 날 + 오늘 | 앞으로 3일까지 — **덤이지 파는 물건이 아니다** |

🔴 **무료선(과거+오늘 무료 / 미래 구독) 로직은 유지한다.** 브레인스토밍 중간에 "달력 전면 무료"를
전제로 "무료선 로직이 통째로 없어진다"고 적었으나, 사용자가 **미래 3일 블러**를 택하면서 전제가 바뀌었다.
바뀌는 것은 **표현(점선 → 블러)**과 **미래 날짜 리포트 생성**뿐이다.

## 2. 허브 구조

```
배너(별마루 전용 일러스트)
  ↓
인연 칩  [나] [지민] [＋]
  ↓
롤링 7일 스트립  ← 오늘 가운데 고정 · 2배 폭
  [3일 전][2일 전][어제][ 오늘 ][내일▨][모레▨][글피▨]
  CTA: 앞으로 3일도 미리 볼래? · 3일 무료
  ↓
「이번 달 전체 보기 · 19칸 열림 ▾」  ← 기본 접힘, 첫 방문만 펼침
  ↓
✦ 무료로 다 보는 것
  [오늘 사주] [오늘 타로] [사주 MBTI] [별 인연 지도]   ← 2탭 동형 행
```

**확정 사항**

- **달력이 계속 상단**(사용자 결정). P5 의 "달력이 히어로"를 유지한다.
- **오늘 골드 히어로 타일 제거.** 그 역할은 스트립의 오늘 칸(2배 폭)이 가져간다.
- **하단 크로스셀(`CrossSellCard`) 삭제.**
- **`/byeolmaru/saju` 의 달력 중복 제거** — 허브에 있으므로 상세에는 두지 않는다.

### 2-1. 롤링 7일 스트립

- **오늘 중심 롤링 창**이다. 일~토 주가 아니므로 **"이번 주"라는 개념이 없고 주 바뀜·월 경계 문제가 소멸**한다.
- 지난 3일 + 오늘 = 열림 / 앞으로 3일 = 블러. **흐린 칸이 항상 정확히 3개**로 고정된다
  (요일 기준이면 월요일 6칸·토요일 1칸으로 출렁인다 — 그래서 기각).
- 가려지는 것이 **미래**라 "안 준다"가 아니라 **"아직 안 온 날"**로 읽힌다.
  P5 §2 원칙(*"자물쇠를 쓰지 않는다 · 잠긴 게 아니라 아직 안 온 것"*)과 정확히 맞는 유일한 블러 형태다.
- 칸 구성: 요일+날짜 · 일지 캐릭터 · 하루 이름 · 마크 라벨. **오늘 칸만 2배 폭**이라 정보가 거기 몰리고
  나머지 6칸은 조용하다 → 사용자가 지적한 "A는 번잡 / B는 허전" 딜레마의 해법.
- 스트립 칸 탭 → 그날의 상세(§4). 미래 칸은 비구독자면 구독 안내.

### 2-2. 월간 격자 (기본 접힘 · 첫 방문만 펼침)

- 접힘 버튼에 **"이번 달 전체 보기 · N칸 열림 ▾"** — 채움 서사를 버튼이 지고 간다.
- **첫 방문자에게만 펼친 상태**로 시작해 한 달치 미래 블러(= 구독 이유)를 한 번 보여주고,
  접으면 그 뒤로는 접힌 채 기억한다(localStorage, `useBaitDismiss` 와 같은 패턴).
- 근거: 별마루는 **실사용 데이터가 0**이라 "사람들이 한 달을 훑는가"를 아무도 모른다.
  항상 펼침(S1)은 그 가설에 370px 를 선지불하는 것이고, 폐지(S2)는 확인할 기회를 없앤다.
  접힘 클릭률로 답을 얻고 필요하면 기본 펼침으로 바꾼다(반대 방향보다 싸다).
- 격자 셀은 **날짜 + 톤 색면 + 마크 색 띠**만. 동물·간지는 스트립과 상세가 담당한다.

### 2-3. 무료 목록 4종

- **2탭(`/fortune`)과 동형**으로 맞춘다 — **좌측 4px 금색 세로 바 제거**, 칩 문법 통일
  (`⭐ N` / `무료` / `하루 1회 무료` + 분량 힌트). 사용자 확인 사항 ③.
- 순서: 오늘 사주 · 오늘 타로 · 사주 MBTI · 별 인연 지도.
- **오늘 사주가 목록으로 내려온다**(P5 §3 의 "오늘 사주는 목록에 없다"를 뒤집는다).
  이유는 진입점 통일 — 지금은 오늘 타로만 목록이고 오늘 사주는 달력 안 타일이라 문법이 다르다.

## 3. 달력 시각 (⑤⑦)

**dev 실물에서 확인한 문제**

1. 셀 하나에 **날짜·동물·간지·글리프 4겹**이 42px 안에 들어간다.
2. 제일 큰 요소(동물)가 **의미를 담지 않고**, 진짜 내용인 톤이 제일 약하다.
3. **무난한 날(흰)과 챙길 날(연한 흰)이 거의 같은 색**이라 구분이 안 된다.
4. 끌림/결속/삐걱이 **8px 회색 글리프**라 사실상 안 보인다.

**확정**

| 요소 | 변경 |
|---|---|
| 간지 텍스트(경진·신사…) | **셀에서 제거** — 상세 카드에만 |
| 챙길 날 | `rgba(255,255,255,.45)` → **연보라** `linear-gradient(160deg,#EFE7F8,#DCCFF0)` |
| 잘 맞는 날 | `#E8C26A` → `linear-gradient(160deg,#F7DFA4,#E8C26A)` |
| 마크 | 8px 글리프 → **2글자 컬러 라벨** (셀 하단 띠) |
| 마크 색 | 끌림 `#C99A28` · 결속 `#3E8E8A` · 삐걱 `#C4738E` |
| 미래 칸 | 날짜·동물은 선명(만세력이라 비밀이 아니다), **톤 색·하루 이름·마크가 블러** |

- 나 탭의 마크(천간합·육합·충·빈 곳 채움)도 같은 2글자 라벨 문법을 쓴다.
  `dayMarks`/`pairMarks` 가 이미 같은 glyph 문법을 공유하므로 라벨만 노출 형태를 바꾼다.

### 3-1. 🔴 우리 탭 금색 과다 — 고치기 전에 측정한다

실물에서 **30일 중 13일이 금색**이었다(나 탭은 2일). 코드에서 원인 3가지가 확인된다:

1. `spark`/`bond` 가 **두 사람 OR** (`heavenlyCombo(일진, 나) || heavenlyCombo(일진, 상대)`)
   → 켜질 확률이 1인 대비 대략 2배. 가중치 `SPARK_W=12` · `BOND_W=9`.
2. `baseline`(궁합 좋은 쌍이면 +8~12)이 **30일 전부에 상수로 더해진다** → 잘 맞는 쌍은 달 전체가 통째로 올라간다.
3. 그런데 임계값 **70/45 는 나 탭(`dayGrade`)과 똑같다** — 1인용 눈금을 2인 점수에 그대로 쓰고 있다.

⚠️ **임계값만 올리면 안 된다.** 그 쌍은 고쳐져도 baseline 이 낮은 쌍은 금색이 **영영 0일**이 될 수 있다.
관측은 **한 쌍 한 달치(n=1)** 라 분포를 모른다.

**→ 측정 먼저.** 나 탭은 이미 전수 7,200 케이스를 잰 스크립트(`scripts/byeolmaru-label-freq.ts`)가 있다.
같은 방식으로 페어 분포를 잰 뒤 ①페어 전용 임계값 ②OR→가중(둘 다면 full, 한 명이면 절반)
③baseline 을 점수에서 빼고 설명으로만 사용 — 셋 중 무엇을 고칠지 **근거로** 정한다.
순수 함수라 측정 비용은 사실상 0이다.

### 3-1-a. ✅ 측정 완료 · 처방 확정 (2026-09-20)

**실측** `scripts/byeolmaru-pair-tone-freq.ts` · 16,110쌍 × 30일 = 483,300칸 ·
findings `specs/2026-09-20-별마루-페어-톤-분포-findings.md`

🔴 **위 문단이 n=1 로 세운 전제 2개가 틀렸다** — 관측 "우리 13일"은 **상위 1.7% 쌍**(중앙 7일),
"나 2일"은 **하위 21% 사람**(중앙 5일). 격차는 6.5배가 아니라 1.4배다.
**진짜 결함은 꼬리** — 30일 중 10일↑ 금색인 쌍이 10.6%(나 탭 0.6%).

원인 순위도 바뀐다: **OR 이중계산이 주범**(끌림 1.91× · 결속 1.92×, 둘 다 켜지는 칸은 5%뿐),
**baseline 은 쌍의 76%가 +0** 이라 레벨 요인이 아니다(위 본문의 "+8~12"는 실제로 상위 1.6%).
임계값만 올리는 ①은 기각 — 중앙 4일로 낮추면 3%, ≥80 이면 **12.3% 쌍이 한 달 내내 금색 0**.

**✅ 확정 (사용자 결정 2026-09-20) = ②+③ 둘 다.**

```
spark:  둘 다 → 12 · 한 명 → 6   · 없음 → 0
bond:   둘 다 →  9 · 한 명 → 4.5 · 없음 → 0
friction: 현행 OR 유지(-14)      ← 가중하면 "챙길 날"만 18.9%→15.4%로 희석된다
baseline: 점수에서 제거, 배경 설명으로만 사용
임계값 70/45 유지                 ← 페어 전용 임계는 불필요
```

예상 결과(실측): 금색 **14.2%** · 무난 65.3% · 챙길 20.5% · 쌍당 금색 중앙 **4일** ·
금색 0일 쌍 3.9% · **10일↑ 쌍 10.6% → 0.8%**(나 탭 0.6% 수준).

🔴 **표시 마크는 별개 결정이라 P6-3 이 정한다.** `pairMarks()` 는 같은 OR 불리언을 읽으므로
점수를 반으로 깎아도 셀에는 여전히 "끌림"이 뜬다. 한 명만 끌리는 날도 알릴 값이 있으면 그대로,
점수와 표시를 맞추려면 "둘 다"일 때만 마크를 띄운다.

⚠️ **남은 열린 질문**: "나 탭 눈금(금색 16.7% = 30일 중 5일) 자체가 적절한가"는 이 측정이 답하지
않는다. 양 탭 공통 상향은 페어 버그 수정이 아니라 별도 결정이고 나 탭 회귀를 동반한다.

## 4. 날짜 상세 = "그날의 기록"

날짜 칸을 누르면 **그날 있었던 것이 한 장에 모인다.**

| | 무료 사주 taste | 그날 뽑은 카드 | 유료 리포트 |
|---|---|---|---|
| **지난 날** | 항상 O (룰 계산) | 있으면 O | **있던 것만** — 없으면 "그날은 리포트를 안 받았어" |
| **오늘** | O | 뽑았으면 O / 아니면 뽑기 유도 | O (현행 캐시) |
| **앞으로 3일** | O | "카드는 그날 뽑는 거야" | **누를 때 생성**(캐시) |
| **그 너머 미래** | O | — | 흐름 정보만, 리포트 없음 |

- **과거 소급 생성은 하지 않는다**(사용자 결정). 미래는 아직 안 온 날이라 지금 만드는 게 맞지만,
  과거는 이미 지나간 날이라 **그때 받은 것만** — 규칙이 한 문장으로 선다.
  달력이 "조회"가 아니라 **기록**이 되는 것도 이 선택 덕분이다.
- **미래 리포트는 앞으로 3일까지**(스트립 블러 3칸과 정확히 일치). 그 너머는 하루 이름·톤·마크만.
- **대기 UX** — 리포트 생성은 실측 8.3초다. 무료 부분(일진·하루 이름·taste·그날 카드)은 **즉시 렌더**하고
  리포트 자리만 스켈레톤으로 채운다. 현 구조가 이미 분리돼 있어 추가 비용이 거의 없다.

## 5. 유료 리포트 — 무료/유료 경계

**경계는 고를 수 있는 게 아니라 이미 정해져 있다.** 원칙이 *"비자격자에겐 LLM 을 호출하지 않는다(원가 0)"*
이므로, 무료로 줄 수 있는 것은 **결정론적 계산 + 정적 뱅크**뿐이다. 그 선이 사용자의 직관("앞부분이 무료")과
그대로 일치한다.

### 5-1. 화면 형태 — 한 장의 리포트 + 가로 절단 + 섹션 이름 칩 (C안)

- 지금처럼 "크림 박스(무료) 아래 리포트 카드(유료)" 두 덩어리가 아니라 **한 장**으로 합친다.
- 절단선 위 = 무료(선명), 아래 = 유료(블러). **블러 위에 섹션 이름 칩을 또렷하게 겹쳐** 무엇이 있는지 보이게 한다.
- 블러 아래 깔리는 글자는 **정적 뱅크 문장을 재활용**한다 — 읽히진 않아도 가짜 로렘입숨이 아니다.
- **기각:** 섹션 단위 자르기(무료 2섹션 열고 4섹션 블러) — 무료(정적)와 유료(LLM)를 같은 섹션 옷에 넣으면
  품질 차가 드러나 무료 쪽이 초라해 보인다. P5 §9 도 같은 형태를 한 번 기각했다.

### 6-3. 타로 게이지 — 사주 축 + 카드 보정 덧칠

축 점수(연애·돈·일)는 **오늘 일진 × 내 사주**의 룰 값이고 `card-narrative` 가 **이미 계산해서 프롬프트에
넣고 있다.** 그대로 쓰면 오늘 사주 화면과 똑같은 막대가 두 번 나오므로, **카드 보정분을 덧칠한다.**

- 회색 바탕 = 오늘 사주 축(두 화면이 항상 일치) · **금색 덧칠 = 이 카드가 더한 것**
- 슈트 → 도메인: 컵 = 연애 · 펜타클 = 돈 · 완드/소드 = 일 · 메이저 아르카나 = 전체(카드별 도메인 태그 필요 —
  `suit` 가 마이너 56장에만 있다)
- 정위 **+** / 역위 **−**(빗금 표시)
- 🔴 **보정 폭은 ±15 이내**로 작게. 그보다 크면 "카드가 하루를 뒤집는다"가 되어 단정적 예언 쪽으로 기운다.
- 전부 룰이라 **원가 0**.

### 6-4. 무료 ↔ 유료 역할 분리 (겹침 방지)

**실측 — 표현 수준 중복은 사실상 없다.** 같은 사람·같은 날로 무료 taste 와 유료 서술(luna)을 문자 대조:

| | 4-gram 포함률 | 6자 이상 공통 표현 |
|---|---|---|
| 오늘 사주 | 0.2% | **0개** |
| 오늘 타로 | 1.3% | 1개 ("기다리기보다") |

> 측정 시 사주 taste 는 379자로 나왔다(§5-2 의 456자와 다른 이유는 측정 스크립트가 `relation` 슬롯을
> "보통"으로 고정했기 때문이다). taste 는 슬롯 조합에 따라 **379~456자 범위**로 변동한다 — 어느 쪽이든
> 목표(350)는 넘고 격차 판정도 바뀌지 않는다.

**다만 문자 대조로 안 잡히는 의미 중복이 타로에 있다:**
- 무료: *"완벽한 타이밍을 기다리기보다, 지금 낼 수 있는 추진력으로 밀고 나가는 게 오늘은 더 잘 맞아."*
- 유료: *"모든 조건이 완벽해질 때까지 기다리기보다 네가 잡은 고삐를 놓지 않는 게 중요해."*

글자는 다른데 메시지가 같다. **같은 카드 한 장을 둘 다 읽으니 완전히 피하긴 어렵다.**

→ 프롬프트 규칙의 목적을 **역할 분리**로 잡는다:

| 블록 | 무료가 말하는 것 (정적) | 유료가 말할 것 (LLM · 반복 금지) |
|---|---|---|
| 사주 전반 | 등급의 **결** ("딱 중간쯤의 하루야") | 丙申이 **네 일간과 어떻게 부딪히고 받쳐주는지** — 근거 |
| 사주 애정 | **태도** ("무리해서 확인하려 들지 마") | **오늘 벌어질 장면과 할 말** ("서운한 점을 부드럽게 말하면") |
| 타로 카드 | 그 카드가 **어떤 카드인지**(상징·전통 의미) | **네 사주·오늘 일진의 어디에 떨어지는지.** 상징 재설명 금지 |

`narrative-prompt.ts` 가 이미 같은 장치를 쓰고 있다 —
*"화면엔 이미 오늘 이름과 한 줄 요약이 떠 있다. 그 뜻을 다시 설명하지 말고…"*

### 6-5. 마크다운 (⑧)

- **블록마다 첫 구절 볼드 1개 고정** — 사주 9개 · 타로 7개. 지금은 들쭉날쭉하다(같은 모델이 어떤 날 6개,

## 7. 같이 고치는 결함 6건

개편과 별개로 이번 점검에서 확인된 것들. 전부 재현·코드로 확증했다.

1. 🔴 **JSON 찌꺼기 누출 — 한 단어 버그.**
   `lib/fortune/prompt.ts:691` 이 `.replace("{{TODAY_PILLAR}}", …)` 인데 daily 템플릿에
   `{{TODAY_PILLAR}}` 가 **두 번**(192행 `stars`, 195행 `intro`) 나온다. `String.replace` 는 첫 번째만
   바꾸므로 `intro` 쪽 플레이스홀더가 **치환되지 않은 채** 모델에 들어가고, 모델이 그걸 메우면서
   `오늘 들어온 두 글자({"병신"})는` 이 나온다. → `.replaceAll`.
   (바로 아래 `{{THIS_MONTH_PILLAR}}` 는 이미 `.replaceAll` 이다 — 같은 함정을 한 번 밟고 월간만 고친 흔적.)
   **검증 방법:** 빌드한 system 문자열에 `{{TODAY_PILLAR}}` 잔여가 0개여야 한다(현재 1개).

2. 🔴 **`daily-report` 에 날짜 파라미터가 없다.** 항상 `kstDate(now)` 로 오늘만 만들고,

   **오늘(19일) 리포트**가 "오늘의 운세 · 오늘"로 붙는다. **한 화면에 두 날짜가 섞인다.**
   코드 주석이 이 사실을 알고 있었으나 비구독자 미끼 문구만 손보고 자격자 경로는 그대로 뒀다.

3. **`daily-card` 조회가 오늘 고정.** `getTodayCard(userId, kstDate(now))`.
   `byeolmaru_daily_card(user_id, card_date)` PK 라 **지난 카드가 DB에 전부 남아 있는데 꺼낼 길이 없다.**

4. 🔴 **`card-narrative` 에 캐시가 아예 없다.** 매 요청마다 새로 생성 → 같은 날 다시 들어오면
   **해석이 매번 달라진다.** `pair-narrative` 는 P5-5 에서 캐시를 붙이며
   *"같은 날 서술이 달라지면 운세 앱의 신뢰가 깨진다"*고 적었는데 card 에는 안 붙였다.
   → `byeolmaru_card_narrative(user_id, card_date)` 신설. 마이그레이션 1장, pair 패턴 복제.

5. **프롬프트가 "오늘"로 못 박혀 있다.** `lib/fortune/prompt.ts` 가 `"오늘 들어온 두 글자"`,
   `"오늘 하루에 어떤 영향"`, `{{TODAY_PILLAR}}` 처럼 전부 오늘 기준이다. §4(미래 3일 생성) 때문에
   **날짜별 시제 분기**가 필요하다 — 지난 날 "그날 들어왔던" · 오늘 "오늘 들어온" · 앞으로 "그날 들어올".

6. **`note` 접두 중복.** 출력이 `"별콩이의 한마디: 오늘은…"` 로 시작해 섹션 제목과 겹친다
   (luna 에선 사라졌으나 프롬프트·후처리로 방어).

### 8-1. 뽑는 것 = 배너가 아니라 **투명 배경 캐릭터 1컷**

### 8-2. 소품은 **하나만** — 초승달 (사용자 확정 2026-09-20, 1안)

2탭은 **두루마리**를 들고 **서 있다**. 별마루를 "달력을 든 포즈"로 가면 실루엣이 거의 같아진다

→ **초승달에 걸터앉은 자세.** 실루엣이 갈리고(곡선+앉음 vs 직선+섬), 작은 크기에서도 달 형태가
읽히고, **"별마루 = 별 보는 자리"**(마루 = 앉아서 올려다보는 곳)라는 이름과 맞는다.

- 배경 제거 후 **털 가장자리 흰 테두리** 잔존 여부

### 8-6. 2안 (1안이 레퍼런스와 안 붙을 때만)

2탭과 같은 **직립 포즈 + 두루마리 대신 초승달을 두 팔로 안기.** 포즈 변화가 작아 일관성은 쉽지만
실루엣 구분이 약해지는 트레이드오프. 1안이 3회 시도로 안 나오면 전환.

### 8-7. ✅ 생성·검수 결과 (2026-09-20) — 1안 1회차로 확정, 2안 불필요

§8-3 프롬프트 그대로 `nano_banana` 4컷(멀티레퍼런스 2장, 약 8크레딧). **4컷 전부 캐릭터 일관성 통과** —
귀 스월 · 이마 금별 · 후광 · 망토+부적 태그 · 복슬꼬리 유지. **채택 = 3번**
(job `ee597d70-15af-43fd-9c79-c460444fcb76`, 달이 제일 두껍고 또렷 · 그림자가 본체에서 깨끗이 분리됨).

**§8-5 합격 기준 판정**

| 기준 | 판정 |
|---|---|
| 77×100 에서 "달에 앉은 동물"로 읽히나 | 🔴 **달은 읽히는데 캐릭터가 뭉갠다** — 아래 참조 |
| 보라 그라데이션 위에서 뜨나 | ✅ 통과. 금색 달이 대비를 만들어 2탭보다 오히려 잘 읽힌다 |
| 2탭과 같은 개체로 보이나 | ✅ 4요소 전부 유지 |
| 배경 제거 후 흰 테두리 | 실제 `remove_background` 결과로 판정 |

🔴 **스펙의 "안 읽히면 달을 더 크게"는 방향이 반대였다.** 실측 원인은 **비율**이다 —
잘라낸 후보들은 **세로/가로 ≈ 1.0(정사각)**인데 2탭 에셋은 **1.33(세로형)**이라, `object-contain`
77×100 상자에서 후보는 **77×77만 쓴다**(면적 40% 손해). 그림 품질이 아니라 상자 문제.

**✅ 확정 처방 (사용자 결정): 컨테이너를 키운다.** 별마루 배너는 새 컴포넌트라 2탭 치수에 묶일
이유가 없다. **캐릭터 슬롯 폭 120px**(`object-contain`, 실제 점유 ≈ 120×116). 110 미만이면 얼굴이
다시 뭉갠다 — 실측 하한이다. 크레딧 0 · 에셋 재작업 0.
🔴 **이 슬롯 크기는 P6-3 이 배너 컴포넌트를 만들 때 쓰는 값이다**(§2 허브 상단).

**후처리 주의** — 프롬프트의 "slight soft shadow under the moon only"가 실제로 그려져서,
투명 배경에선 **달 아래 노란 타원이 떠 있는 얼룩**이 된다. 3번은 알파에 빈 행이 있어 자동으로
떨어지지만(831→739), **1·4번은 본체에 붙어 자동 분리가 안 된다**(수작업 마스킹 필요).
다음에 이 프롬프트를 재사용하면 그림자 문구를 빼는 게 낫다.

## 9. 리스크 · 미검증

1. 🔴 **구독자 하루 총량이 4,800자가 된다**(사주 1,800 + 타로 1,800 + 우리 1,200).
   P5 §8 이 *"구독자가 하루 4,200자를 받으면 둘 다 안 읽고, 오늘 사주가 '오늘의 본편'이라는 위계도
   사라진다"*고 경계한 선을 넘는다. 셋이 **각각 다른 화면**이고 우리 오늘은 상대 등록자만 본다는 완화 요인이
   있으나, **"본편이 둘"은 사용자 결정("사주와 타로를 비슷하게")에 따른 의도된 변경**으로 기록한다.
2. 🔴 **타로 1,800자는 반복 위험이 크다.** 카드 한 장으로 사주의 일진만큼 재료가 나오려면 블록마다
   다른 재료를 강제해야 한다(§6-2 표의 "재료" 열). nano 가 587자에서도 같은 말을 다섯 번 돌려 썼다.
   → **검수 항목: 카드 3~4장(메이저·마이너·정위·역위 섞어)으로 반복도 확인.**
3. **문장당 50자 환산은 추정이다.** 실측 45~54자 범위에서 잡았다. 첫 생성에서 목표 대비 ±15% 를 벗어나면
   문장 수를 ±1 씩 조정한다.
4. **메이저 아르카나 22장은 `suit` 가 없다** — 게이지 보정용 도메인 태그를 카드별로 새로 정해야 한다(§6-3).
5. **luna 원가 배수가 저장소에 없다.** 사용자 판단으로 진행하되 배포 후 실측 모니터링.
   → 🔴 **"배포 후 실측"의 수단이 지금은 없다** (2026-09-20 확인: 토큰·모델·비용을 어디에도 기록하지 않는다 —
   테이블·컬럼 0, 원가는 Anthropic 콘솔 수동 파싱). 해소 경로는 **어드민 재설계 §4 `llm_usage` 로깅**이며,
   **그게 P6 배포 묶음에 같이 타야 배포 직후부터 실측이 시작된다.** 나중에 넣으면 그만큼 추세가 짧아진다.
   → `docs/superpowers/specs/2026-09-20-어드민-재설계-design.md` §4
6. **첫 방문 펼침 상태 기억**은 localStorage 라 기기·시크릿창마다 다시 펼쳐진다. 허용 오차로 본다.
7. 🔴 **30일 구독이 올라탈 리텐션이 아직 없다** (2026-09-20 prod 실측): 로그인 유저의 **2일+ 방문 12.1% ·
   5일+ 방문 0.7%**. 결제자 평균 방문일 2.2 vs 미결제자 1.1. 30일 구독은 "다시 온다"를 전제로 하는 상품인데
   그 전제가 현재 관측되지 않는다. 로드맵 v2 는 이미 **단월 판정 금지 · 12주 누적 판정**으로 대비하고 있으나,
   **스펙 차원에서는 "구독이 리텐션을 만든다"와 "리텐션이 없어 구독이 안 팔린다"를 구분할 준비가 필요하다.**
   → 관문은 §10-1③(구독자↔비구독자 방문일수 대조). **리스크 기록이며 별마루 단계 작업은 없다** — 대조 화면은 어드민 플랜 B.

### 11-1. P6-1 실행 중 발견 — P6-2 가 반드시 챙길 것

P6-1 구현·리뷰 과정에서 나온 것들. 전부 **실측 또는 코드로 확증**했다.

1. 🔴 **`saju.temporal` 을 `reportDate` 기준으로 다시 계산해야 한다.** `daily-report` 라우트가
   `calcTemporalLuck(baseDateForKst(todayKst), …)` 로 **항상 실제 오늘** 일진을 계산해 붙인다.
   `?date=` 만 받고 이 기준일을 안 바꾸면 `오늘 날짜:` 줄은 대상 날짜인데 "오늘 들어온 두 글자"
   블록과 `{{TODAY_PILLAR}}` 는 실제 오늘 일진인 모순이 난다(재현 확인). P6-1 Task 8 에 반영돼 있으나,
   이후 이 경로를 고칠 때도 같은 전제를 유지할 것.
2. 🔴 **`byeolmaru_card_narrative.narrative` 는 `TEXT` 다.** 타로 유료가 JSON 7블록으로 바뀌면
   ①`TEXT` 에 JSON 문자열을 그대로 넣거나 ②`JSONB` 로 바꾸는 마이그레이션이 필요하다.
   ②를 택하면 **구버전 자유 줄글 행은 `::jsonb` 캐스트가 실패하므로 `TRUNCATE` 후 타입 변경**할 것.
   형제 `byeolmaru_daily_report` 가 `JSONB` 인 건 "미래 대비"가 아니라 그 리포트가 **처음부터 구조화
   출력**이었기 때문이다 — 지금 `TEXT` 인 건 YAGNI 로 옳은 선택이다.
3. 🔴 **캐시 키에 포맷 버전이 없다.** P6-2 를 하루 중간에 배포하면 그날 이미 캐시된 구버전 행을
   새 렌더러가 읽어 깨진다. 배포를 KST 자정에 맞추거나 배포 시 해당 테이블을 비울 것.
4. **캐시 히트 경로와 생성 경로의 응답 대칭.** 지금은 둘 다 `narrative: string` 하나다.
   구조화로 바꿀 때 **생성 경로만 파싱을 넣고 캐시 히트 경로를 잊는** 실수가 쉽다.
   권장: 파싱·검증은 **저장 전에 한 번만** 하고, 캐시 히트는 그대로 돌려주기만 하게 유지.
5. **동시 요청 창 — 응답 불일치(자가치유, 비손상).** 같은 유저가 동시에 두 번 부르면 둘 다 생성하고
   한쪽만 저장되는데 **응답은 각자 자기가 만든 글**이라, 그 순간 두 탭이 다른 글을 본다.
   dev 는 StrictMode 이중 마운트로 사실상 상시 재현된다(`app/byeolmaru/saju/page.tsx` 주석에
   같은 현상의 실측 기록이 있다). `card-narrative`·`pair-narrative` **둘 다** 같은 구멍이다.
   완화책: `saveCardNarrative` 가 `23505` 를 만나면 승자 값을 다시 읽어 **그걸 응답**하게 한다.
   P6-2 가 이 경로를 어차피 다시 쓰므로 **그때 새 형태로 한 번에** 넣는 것이 낫다(지금 고치면 두 번 한다).
6. **프롬프트 쪽 note 제목 방어.** 스펙 §7-6 은 "프롬프트·후처리"를 요구했는데 P6-1 은 후처리만 했다.
   `lib/fortune/prompt.ts` 의 daily `"note"` 줄 위에 `TODO(P6-2)` 브레드크럼을 남겨뒀다.
7. **캐시 조회 에러가 "없음"과 뭉개진다.** `getCached*` 세 래퍼(`daily-report`·`pair-narrative`·
   `card-narrative`)가 전부 `error || !data → null` 이라, DB 장애로 캐시가 0% 적중해도 아무 데도 안 찍힌다.
   `stripNoteHeading` 발동 여부도 마찬가지로 무계측이다 — luna 로 올린 뒤 이 방어들이 여전히
   필요한지 판단하려면 최소한의 신호가 필요하다.
