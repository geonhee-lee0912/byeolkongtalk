## 0. 무엇을 바꾸나

`/fortune` 목록에서 상품을 누르면 **곧바로 사주 프로필 선택 + 별 차감 모달**이 뜬다. "이게 뭘 주는 상품인지" 읽을 지면이 없다 — 설명이라곤 카드의 `tagline` 한 줄, 해시태그 3개, `약 5,000자` 표기가 전부다.

같은 URL 에 **설명을 먼저 깔고 그 아래에서 사게** 바꾼다. 라우트는 늘리지 않는다.

**대상 = 20개.** `FORTUNE_LIST` 의 활성 19종 + 무료 `사주 MBTI`. 별 인연 지도(`byeoljari`)는 이번 범위 밖.

## 1. 라우팅·렌더 구조

**`/fortune/[type]` 한 장이 설명과 구매를 모두 받는다.** 라우트 신설 0.

- 지금 `"use client"` 인 `app/fortune/[type]/page.tsx` 를 **서버 컴포넌트**로 전환
- 기존 구매 로직 전체(프로필 선택 · `/api/auth/me` 로그인 가드 · 잔액 조회 · `StarConfirmModal` · `/api/fortune/create` · `FortuneRefundModal` · `AlreadyOwnedModal` · monthly 의 `reviewableByProfile` · 중복 POST `inFlightRef` 가드 · `FortuneGeneratingScreen`)는 `components/fortune/FortunePurchasePanel.tsx` 로 **이동만 한다. 동작 변경 없음**
- `valid` 가드(비활성·타로·daily → `/fortune` 리다이렉트)는 서버에서 판정해 `redirect()` 로 처리

**왜 한 장인가** — `cfg.href` 가 계속 정본 URL 이라 목록·`ResultUpsell` 크로스셀·별마루 `FreeList`·`lib/analytics/route-labels.ts` 의 href 역매핑이 **전부 무회귀**다. 색인 URL 도 `/fortune/love_self` 로 깔끔하다.

**마찰 처리** — 이미 살 마음인 재구매자를 위해 히어로에 CTA 를 두고, 누르면 구매 모듈로 스크롤한다(탭 1회).

## 2. 페이지 구성

히어로 → ①이런 게 궁금하면 → ②리포트 목차 → ③샘플 발췌 → **구매 모듈** → ④같이 보면 좋은 것.

("어떻게 만들어지나" 섹션은 구매 결정 기여가 낮다고 보고 **뺀다** — 사용자 확정)

### 히어로
상품 일러스트(§6) · 상품명 · 후킹 한 줄 · 칩 3개(`별 N개` / `FORTUNE_LENGTH_HINT` 분량 / 소요 `1~2분`) · CTA `이 사주로 보기`(구매 모듈로 스크롤).
- 무료 MBTI 는 칩이 `무료` / `12문항` / `1분`, CTA 는 `테스트 시작하기`

### ① 이런 게 궁금하면
상품별 질문 3~4개. 상품이 실제로 답하는 것만 쓴다(목차에 없는 걸 약속하지 않는다).

### ② 리포트 목차
실제 결과 화면에 뜨는 섹션 제목 그대로. 상단에 `N개 섹션 · 약 O,OOO자` 표기.
- 섹션이 7개를 넘으면 5개 + `그 외 N개`로 접는다(평생사주는 대운 구간까지 합쳐 14섹션이라 전부 깔면 지면이 무너진다)

### ③ 샘플 발췌
2~4문장 + `예시 · 실제 리포트는 네 사주로 다시 쓰여` 라벨.
- **시각 3종**(`element_balance` · `saju_report_card` · `life_graph`)은 텍스트 발췌 대신 **결과 시각 요소의 미니 프리뷰**를 넣는다(오행 차트 · 학점 카드 · 대운 곡선). 그림이 곧 상품이라서다. 기존 렌더러(`ElementBalanceView` · `ReportCardView` · `LifeGraphView`)에 고정 더미 데이터를 먹여 축소 렌더한다

### 구매 모듈
`FortunePurchasePanel`. 기존과 동일.

### ④ 같이 보면 좋은 것
**`components/upsell/cross-cards.ts` 의 `RELATED_SAJU` 를 재사용한다** — 이미 상품 간 인접성이 정의돼 있고, 두 벌로 관리하면 갈라진다. 내부 링크가 생겨 SEO 에도 붙는다.

- 그 테이블은 상품당 **2종**이다(3종 아님) → 카드도 **2장**. 지면을 채우려고 세 번째를 지어내지 않는다
- 지금 `const` 라 `export` 로 연다. `cross-cards.ts` 안의 사용처는 그대로
- `saju_mbti` 는 `FortuneType` 이 아니라 테이블에 없다 → `data/fortune/landing.ts` 의 MBTI 항목이 `related: ["nature_self", "love_self"]` 를 직접 들고, 랜딩 셸은 `related` 를 props 로만 받는다(셸은 어디서 왔는지 모른다)

## 3. 데이터 · 목차의 단일 원천

### 3-1. 랜딩 카피
신규 `data/fortune/landing.ts` — 상품별 한 덩어리.

```ts
export interface FortuneLanding {
  hook: string;            // 히어로 후킹 한 줄 (tagline 보다 길게, 2줄까지)
  questions: string[];     // 3~4개
  sample: string | null;   // 2~4문장. 시각 3종은 null(프리뷰로 대체)
  minutes: string;         // "1~2분"
  related?: FortuneType[]; // RELATED_SAJU 에 없는 항목만(= saju_mbti). 있으면 이쪽이 우선
}
export const FORTUNE_LANDING: Record<LandingKey, FortuneLanding>
```

`LandingKey` = 활성 `FortuneType` 19종 + `"saju_mbti"`. **`Record` 라서 상품을 추가하면 타입이 빈 칸을 막는다.**

### 3-2. 목차 (`lib/fortune/outline.ts`)

`fortuneOutline(type): string[]` — 목차가 실제 리포트와 어긋나면 그건 과장 광고다. 두 경로로 나뉜다.

**(a) 공용 엔진 13종** — `nature_self` `talent_path` `user_manual` `element_balance` `life_full` `love_self` `love_year` `marriage` `wealth_vessel` `wealth_year` `career_timing` `fact_bomb` `past_life`

`lib/fortune/prompt.ts` 의 `genericGuide({title, intro, sections, note})` 호출 인자를 `GENERIC_GUIDE_SPEC: Partial<Record<FortuneType, GuideSpec>>` 상수로 묶어 export 하고, `SECTION_GUIDE` 는 그 상수를 돌며 만든다. 랜딩은 `GENERIC_GUIDE_SPEC[type].sections.map(s => s.heading)` 를 읽는다. → **드리프트가 구조적으로 불가능**.

> 랜딩 페이지는 서버 컴포넌트라 `prompt.ts` 를 import 해도 클라 번들에 안 실린다.

**(b) 전용 스키마 6종** — `monthly` `saju_full` `compat` `compat_social` `saju_report_card` `life_graph`

이쪽은 프롬프트가 `{ "key": "money", ... }` 처럼 **키만** 들고 있고 표시 제목은 렌더러 JSX 안에 박혀 있다(`MonthlyReportView` · `SajuFullReportView` · `CompatReportView` · `ReportCardView` · `LifeGraphView`). 그래서 `outline.ts` 에 **손으로 적고**, 구현 시 각 렌더러를 열어 실제 표시 문자열과 1:1 대조한다.

**계약 테스트 `lib/fortune/outline.test.ts`**
- 20개 키 전부 존재, 각 배열 비어있지 않음
- 공용 13종: `fortuneOutline(t)` === `GENERIC_GUIDE_SPEC[t].sections` 의 heading 배열
- 전용 6종: 스냅샷 고정(문자열 배열을 테스트에 박아 대조) — 렌더러가 바뀌면 테스트가 아니라 **육안**으로 잡아야 하므로, 파일 주석에 "렌더러 제목을 바꾸면 여기도 고친다"를 남긴다

### 3-3. 샘플 발췌를 쓰는 법
API 를 태우지 않는다(사용자 확정). 대신:

1. `calcSaju` 로 **가상 생년월일시 1개**를 실제 계산해 명식(일간·오행·기둥)을 얻는다 — 결정적 로컬 계산, 비용 0
2. 그 명식을 근거로, `data/persona/byeolkong_core.md` + `byeolkong_fortune.md` 의 화법과 해당 상품의 `SECTION_GUIDE` 를 따라 세션 안에서 집필
3. 20종 전부 같은 가상 인물을 쓴다(발췌끼리 인격이 어긋나지 않게)
4. 고정 문자열이라 런타임 비용 0

**화법 준수** — 단정적 예언 금지, 반말·호칭 `너`, 흐름·가능성 어휘. 초안 완성 후 사용자 톤 리뷰.

## 4. 예외 3종

### 4-1. compat · compat_social
`/fortune/compat` · `/fortune/compat-social` 는 정적 세그먼트라 Next 라우팅에서 `[type]` 보다 우선한다 — 지금처럼 전용 페이지가 계속 받는다. 같은 랜딩 셸(공용 컴포넌트 `FortuneLandingSections`)을 쓰고 **구매 모듈만 `CompatInput`**(2인 입력)으로 바꿔 끼운다.

### 4-2. 사주 MBTI
공유 링크가 `/fortune/saju-mbti?r=토큰` 이고 그 URL 이 per-result OG 를 뱉는다. 바이럴 루프를 깨면 안 된다.

| 진입 | 동작 |
|---|---|
| `?r=` 있음 | **지금과 완전히 동일** — `SajuMbtiFlow sharedToken` + per-result OG + noindex |
| `?start=1` | 플로우(문항부터). canonical 은 `/fortune/saju-mbti`, noindex |
| 쿼리 없음 | **서버 렌더 랜딩**(색인 대상). CTA → `?start=1` |

`sessionStorage`(`saju-mbti:session`) 에 세션이 있으면 랜딩의 작은 클라 컴포넌트가 `?start=1` 로 보낸다 — "결과 다시 보기" 경로 무회귀. 크롤러는 storage 가 없으니 색인엔 영향 없다.

`SajuMbtiFlow` 의 `window.history.replaceState(null, "", "?r=" + token)` 은 `?start=1` 에서 실행돼도 URL 이 `/fortune/saju-mbti?r=...` 로 정리되므로 그대로 둔다(공유 URL 은 `buildSajuMbtiShareUrl` 이 만들므로 무관).

### 4-3. 비활성 상품
`good_days` · `daily` · `tarot_*` 는 지금 동작(리다이렉트 / noindex) 그대로. 랜딩을 안 만든다.

## 5. 색인 · 계측

- **메타데이터**: 활성 20개는 `lib/seo/metadata.ts` 의 `contentMetadata({title, description, path})` 경유. `app/fortune/layout.tsx` 의 `noindexMetadata` 상속을 페이지에서 덮어쓴다
  - ⚠️ `openGraph`/`twitter` 는 필드별 병합이 아니라 **객체 통째 교체**다. 반드시 `contentMetadata()` 를 쓰고 손으로 부분 선언하지 않는다(AGENTS.md 함정)
  - `[type]/layout.tsx` 의 `generateMetadata` 는 활성/비활성을 갈라 활성은 `contentMetadata`, 비활성은 `noindexMetadata` 를 준다
- **sitemap**: `app/sitemap.ts` 에 활성 20개 추가. `changeFrequency: "monthly"`, `priority: 0.6`. `FORTUNE_LIST` 에서 파생해 하드코딩하지 않는다
- **계측**: `trackUiEvent`
  - `fortune_landing_cta_clicked` (히어로 CTA, `meta: { type }`)
  - `fortune_landing_purchase_reached` (구매 모듈이 뷰포트에 들어옴, `meta: { type }`)
  - 둘을 나눠 찍어야 "설명을 읽고 내려왔나 / CTA 로 점프했나"가 갈린다
- **PV 라벨**: `route-labels.ts` 는 `FORTUNE_CONFIG.href` 역매핑이라 **무변경**

## 6. 일러스트 20컷

**결정: 20컷 전면 신규 + 결과 화면 히어로까지 이걸로 교체해 한 세트로 통일**(사용자 확정).

현재 `lib/fortune/hero.ts` 의 `HERO` 맵은 14컷을 19종이 돌려쓴다 — 연애 3종이 한 장, 자기이해 3종이 한 장, 재물 2종이 한 장, 궁합 2종이 한 장. 랜딩에 깔면 같은 그림이 연달아 나온다. 20컷을 새로 뽑으면 **상품별 전용**이 되고 결과 화면도 같이 승격된다.

### 파이프라인 (아이콘 세트 판의 규율 그대로)
1. **스타일 앵커 1컷 먼저** — 기존 히어로(`public/fortune-hero-*.webp`)를 이미지 레퍼런스로 올려 톤을 잇는다. 1컷 뽑아 **사용자 확인 후** 전량
2. 모델 `nano_banana_pro`. 크레딧 잔량 236, 예상 소모 ~50
3. 규격: 별콩이 전신 + 상품 소품 1개 · 투명 배경 컷아웃 · 팔레트 고정(cream `#FAF6F0` / lilac `#D4C7EE` / gold `#E8C26A`) · 텍스트 금지
4. 후처리: PIL 코너 플러드필 → 정사각 정규화 → WebP. 개당 ≤150KB
5. 배치: `public/fortune-hero-<type>.webp` (기존 경로 규칙 유지 → `HERO` 맵만 갱신)
6. **무인 생성 금지** — 프롬프트·스타일을 사용자와 합의한 뒤 실행

### 남기는 것
`fortune-hero-good_days.webp` · `fortune-hero-daily.webp` 는 **지우지 않는다** — 과거 리딩이 결과 화면에서 아직 참조한다. 나머지 12컷은 새 파일이 같은 경로를 덮어쓴다.

### MBTI
히어로가 없다(16유형 캐릭터만 있음). 20컷에 포함해 새로 뽑고 `lib/saju-mbti` 쪽이 아니라 랜딩 히어로로만 쓴다.
