# 인-스레드 드로우 분량 정합 (Phase C) — 2026-08-13

재화 재설계 4 phase 중 **C**. 원 spec(`2026-08-10-재화-분량-턴수-정합성-design.md` §4)은 "관계·시뮬 턴수"였으나, dev QA + prod 실측으로 **스코프가 "인-스레드 드로우 분량 정합" 하나로 재정의**됐다. 이 문서가 Phase C 정본.

## 0. 전제 — luna 티어링

chat=luna 배선으로 원가 부담 소멸(정가 마진 99%). 분량을 늘려도 마진 병목 아님(luna 별당원가 ₩0.39~0.67 vs 별당매출 ₩91). 남은 레버 = **별당 체감 가치 정합**. → 원가가 아니라 "같은 값에 같은 분량"이 기준.

luna로 관계·시뮬·드로우 전량 실측(dev QA 하네스 + smoke + prod 쿼리):

## 2. 문제 — 동일 스프레드·동일 별값인데 절반

`checkin_6`·`deep_feelings_5`는 타로 상담과 **완전히 같은 `SPREAD_INFO` 스프레드 타입이고 별값도 같다**(공유 상수):

| 스프레드 | 별값 | 타로 상담 첫풀이 (luna 실측) | 관계 드로우 (luna 실측) | 비 |
|---|---|---|---|---|
| `deep_feelings_5` (5장) | 40별 | 3,381자 | **2,024자** | 60% |
| `checkin_6` (6장) | 45별 | 3,858자 | **1,961자** | 51% |

유저가 같은 값(40/45별)을 내고 관계 탭에서 뽑으면 타로 탭의 절반을 받는다. 게다가 **카드수 역전**(6장 1,961 < 5장 2,024) — 카드가 많을수록 짧다.

**원인**: 프롬프트 차이. 타로는 `byeolkong_tarot.md`가 카드당 6~7문장 + 🃏💫🔗 3라벨 골격("구조가 분량을 보장") + 카드수별 목표 밴드를 명시. 드로우는 `byeolkong_relationship_draw.md`가 자리별 해석([CARD:n]) + 흐름([WRAP]) + 처방 + 마무리 순서만 정하고 **분량은 "촘촘하게·확실히 길게" 한 줄뿐** — 카드수 사다리도, 자리당 밀도 지침도 없다. 그래서 luna가 자유롭게 얇게 쓴다.

## 3. 설계 — 드로우 페르소나에 밀도·밴드 부여

타로식 코드 게이트(`WRAP_THRESHOLDS`) 이식이 **아니다**. 드로우는 `[END]` 없는 지속 스레드라 수렴 게이트가 부적합/불필요. Phase B가 타로 **페르소나**에 밴드를 넣은 것과 같은 방식으로, `byeolkong_relationship_draw.md`에 밀도·밴드 지침을 넣는다.

### 3-1. 목표 분량 밴드 (타로 프리미엄 정합)
같은 스프레드·같은 별값이니 같은 밴드에 맞춘다(타로 첫풀이 luna 실측 밴드):

| 카드 수 | 스킬(별) | 목표 총 분량 | 현재 → 상향 |
|---|---|---|---|
| 5장 | deep_feelings(40) | **3,100~3,700자** | 2,024 → ×1.7 |
| 6장 | checkin(45) | **3,500~4,200자** | 1,961 → ×1.9 |

카드수 역전 해소(6장 ≥ 5장). 미래에 다른 카드뽑기 스킬(7장 등)이 추가되면 타로 7장 밴드(3,900~4,800)를 따른다 — **카드 수에 비례**가 원칙.

### 3-2. 밀도 지침 — 자리당 문장 수 (골격 이식은 안 함)
분량은 **자리별 해석의 밀도**로 채운다(타로 원칙 "밀도로 길게, 물타기 금지" 계승). `[CARD:n]` 자리마다:
- **이 자리에 이 카드가 온 의미** + **관계 파일 맥락(호칭·상태·지난 기록·이번 대화 사건)과 구체적으로 엮기** + **정/역 결**을, 타로 프리미엄에 준하는 **자리당 5~6문장 이상**으로.
- 한 자리가 얇게 끝나면(3문장 이하) 다시 늘린다 — 도상/관계맥락 연결을 한 겹 더.

**타로의 🃏💫🔗 3라벨 골격은 이식하지 않는다.** 근거: (a) 드로우는 이미 `[CARD:n]` 마커로 자리 분할되고 `splitByCardMarker`가 렌더하므로 자리당 문장수 지정으로 밀도가 보장된다. (b) 관계 드로우는 "끝나지 않는 대화의 한 순간"이라 타로 상담의 완결형 골격(카드 도상 중심)보다 **관계 맥락 연결 중심**이 정체성에 맞다. (c) 골격 이식은 렌더·톤 변경 리스크를 얹는데 얻는 게 자리당 문장수 지정과 겹친다. → 구조는 현행(자리별 해석 / [WRAP] 흐름 / 처방 / 마무리) 유지, **분량 밴드 + 자리당 밀도만 추가**.

### 3-3. 불변 유지
`[CARD:n]`·`[WRAP]` 마커 규칙, `[END]`/`[SKILL_DONE]` 금지, 마지막 문장 서술문 마무리(물음표 금지), 단정 금지 화법 — 전부 그대로. 후속 grace 턴은 일반 관계 대화라 손대지 않음(관계 상담 "유지"에 포함).

## 4. 검증

- **QA**: `scripts/smoke-draw-inthread.ts`가 이미 `drawLen`을 측정한다. 현재 `drawLen > 200`만 보는 것을 **카드수별 밴드 하한**(5장 ≥ 3,100 / 6장 ≥ 3,500)으로 강화 — checkin·deep_feelings 둘 다 실행해 하한 통과 확인. (하한만 — 과다는 이 단언이 쫓는 실패 모드 아님, 타로 `firstTurnLengthBelowMin`과 동일 철학.)
- **화법 육안**: 밴드를 채우느라 물타기/반복이 생기지 않는지, 관계 맥락 연결이 실제로 두꺼워졌는지 smoke 출력 육안.
- **PROMPT_VERSION 범프**: 드로우 페르소나 변경 코호트.
- **판정**: 스킬 재구매율 · 실측 분량(밴드 도달) · 결과 체감. 목표 밴드는 견인 숫자(도달 아닌 baseline 대비 증가로 판정).

## 5. 배포

`byeolkong_relationship_draw.md`(페르소나) + smoke 하한 + `PROMPT_VERSION`만 — **마이그레이션 없음**. roadmap ④(dev 누적분 한 판 → prod)에 포함.

## 6. 곁가지 기록 (Phase C 밖)

- **관계 등록 무발화 38%** (prod 55스레드 중 21) — 등록만 하고 발화 0. 턴 캡 문제가 아니라 등록 마찰(슬롯·입력 순서). Phase D(첫 슬롯 인트로가, `relationship-slot-gate-drift-fix`)와 등록 UX 소관. Phase C에서 손대지 않음.
- **SIM_TURN_CAP=12** — 시뮬 prod 배포 후 실사용 인형 턴수 분포로 재검(현재 데이터 0).
- **시뮬 인형 리얼리즘(카톡 대화 업로드)** — 검토 후 비추천(제품=리허설 프레임 붕괴·마찰 / 법률=PIPA 제3자 정보 / 보안=제3자 민감정보 / 비용=요약하면 가치소멸). 대안은 유저 능동 제공(말투 예시 입력). 별도 트랙.
