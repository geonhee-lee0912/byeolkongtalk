## 블록 1 — 손익계산서 (스파인)

```
매출         payments(status='completed').amount_won
− PG 수수료   매출 × 3.7% + 월 ₩9,167
− 광고비      ad_spend 입력분 + Meta CSV 실지출(우선)
− 변동원가    Claude API: 콘솔 총액을 리딩별 점수로 배분
− 고정비      Supabase $51.98 + Vercel $20 + 도메인 $0.87 (힉스필드 제외)
= 월 순손익 / 일 번레이트
```

**원가 배분 방법** (총액은 정확, 배분만 추정):

1. 리딩별 비용 점수 = Σ턴 `(입력토큰추정 × 3 + 출력토큰추정 × 15)` — Sonnet 5 단가 비($/MTok) 그대로 가중
2. 입력토큰추정 = 페르소나(정적, 캐시 마킹 → 히트 시 0.1×) + 히스토리 + 사주/타로 컨텍스트. 출력토큰추정 = assistant 글자수 ÷ 한국어 토큰비
   - ⚠️ **종목별 컨텍스트 창이 다르다**: 사주/타로 상담은 매 턴 **전체 히스토리**를 보내므로 입력이 턴 제곱으로 커지고, 연애 상담 스레드는 **최근 24메시지 + rolling_summary**라 입력이 상한에 수렴한다. 같은 식으로 계산하면 스레드 원가를 크게 과대평가하므로 트랙을 분리한다
3. 캐시 히트율은 **가정값 3 시나리오**(0.3 / 0.6 / 0.9)로 민감도 확인 — [[prompt-cache-optimization]]이 "히트율 낮음"을 시사하므로 상품 순위가 가정에 뒤집히는지 반드시 검산
4. 점수 총합을 **콘솔 총액에 스케일링** → 절대 총액 정확
5. haiku 보조(요약·민감 2차 판정)와 운세 one-shot 리포트는 별도 점수 트랙

**테스트 vs 실유저 원가 분리** (2026-07-25 사용자 지시) — 콘솔 총액은 **prod 유저 대화 + QA 하네스 + 로컬 개발 + prod 스모크**가 전부 섞인 값이다. 전액을 유저 COGS로 계상하면 단위 경제가 크게 왜곡된다.

원장 3개로 테스트분을 잡는다:

| 원장 | 무엇 | 모델 |
|---|---|---|
| `qa/out/<타임스탬프>/*.json` | QA 하네스 전사 — 케이스별 `transcript.turns[].{userText,assistantText}` + 케이스당 판정 1콜 | 별콩이 응답·판정 = **Sonnet** / 시뮬레이터 유저턴 = **Haiku** |
| prod `messages` 중 제외 6명 | 스모크·관리자·지인·내부테스트 대화 | Sonnet |
| dev DB (`vtdmxdcetziileynjaxi`) `messages` | 로컬 수동 검증 (하네스는 seed 퍼지 때문에 흔적이 거의 없음 — 7월 총 60건) | Sonnet |

**방법 — clean-day 캘리브레이션**: 일별로 유저 점수와 테스트 점수를 구한 뒤, **테스트 활동이 0인 날**(qa/out 디렉토리 없음 + dev·제외유저 활동 없음)만 골라 `단가 = Σ콘솔(clean days) / Σ유저점수(clean days)` 를 구한다. 실유저 원가 = 단가 × 전체 유저 점수, 테스트 원가 = 콘솔 총액 − 실유저 원가. 점수 비례 배분보다 정확한 이유: 하네스의 판정 콜은 전사에 안 남는 오버헤드라 점수로 잡히지 않는데, 잔여법은 그것까지 테스트 쪽에 자동으로 몰아준다.

**검증 신호**: 7/19 콘솔이 Sonnet $16.83 · Haiku $1.13 로 튀는데(평소 $2~6 / $0.1~0.3), 그날 `qa/out` 에 QA 실행 6건(62케이스 완주)이 있다. **7/19이 테스트로 귀속되지 않으면 방법이 틀린 것** — 멈추고 원인을 찾는다. Haiku 라인이 하네스 시뮬레이터의 지문이라 Sonnet과 독립적인 2차 확인이 된다.

**선수금(미소비 별) 조정** — 이번에 처음 넣는 라인:

결제로 받은 별 중 **아직 안 쓴 별은 원가가 아직 발생하지 않은 상태**다. 현금 기준 손익만 보면 순이익이 구조적으로 과대평가된다. 따라서 두 숫자를 나란히 낸다.

```
현금 순손익      = 위 계산 그대로 (매출 = 결제 시점)
조정 순손익      = 현금 순손익 − (미소비 별 × 별당 예상 변동원가)
```

별은 유상/무료가 섞이는 대체재라 "유상 잔액"이 자동으로 나오지 않는다. **FIFO(무료 별을 먼저 소비) 가정**으로 유저별로 분해한다:

```
F = 무료 지급 누적 (welcome_bonus·first_charge_bonus·무료 운세·환불)
P = 유상 지급 누적 (payment 기인)
S = 소비 누적            B = 현재 잔액
무료 잔액 = max(0, F − S)        유상 잔액 = B − 무료 잔액
```

유상 잔액 = 선수금 부채(향후 원가 발생 예정). 무료 잔액은 매출과 무관하므로 부채가 아니라 **미래 COGS**로 따로 표기한다. 비례배분을 쓰면 유상 잔액이 더 작게 나오므로(무료 소비를 과대 인정), **부채를 크게 잡는 FIFO를 채택**해 순이익을 낙관적으로 만들지 않는 쪽을 택했다. 두 방식 차이는 리포트에 병기.

**파생 지표**:
- 유저당 기여마진 = ARPU − 유저당 변동원가 → **광고비를 얼마까지 감당 가능한가**
- 상품별 마진 순위표 (가격의 원 환산 − 배분 원가)
- **별 → 원 실효 환산율**: 결제 별 단가(패키지 믹스 가중) vs 무료 별 비중 → "무료 별로 태운 원가" 정량화
- CAC vs LTV (창별·소재별) + **주차 코호트 LTV 추세** (baseline ₩102→₩143/인)
- **일별 번레이트 곡선** (일별 매출 − 일별 광고비 − 일별 API) → 예산 결정의 직접 근거

## ⚠️ 실행 중 발견 — 탈퇴 CASCADE 데이터 소멸 (2026-07-25, Q0 검산)

Q0 를 30분 간격으로 두 번 돌렸더니 `readings` 가 594 → 593 으로 **줄었다**. 원인은 회원 탈퇴다. `users` DELETE 시 자녀 테이블이 전부 CASCADE 되고, orphan 검사에서 `payments`·`star_transactions`·`readings`·`user_acquisition` **모두 orphan 0** — 즉 결제·별원장·대화·광고귀속이 함께 삭제된다.

규모: `account_withdrawals` 누적 **44건** (7/10 시작, 일 2~7건, 최근 24h 4건). 현재 유저 526 + 탈퇴 44 = 실제 가입 **570** → **탈퇴율 7.7%**.

이 분석에 미치는 영향:

1. **누적 매출 ₩107,900 은 과소 집계** — 탈퇴자 결제가 사라졌다. 복구 경로는 **토스 정산 총액과 대조**뿐이고, 그 차액이 소멸분이다 (사용자 확인 필요 항목으로 추가).
2. **CAC/ROAS 과대** — `user_acquisition` 소멸로 소재별 가입수가 과소 집계된다.
3. **API 원가 배분 왜곡** — 탈퇴자 리딩이 점수 모수에서 빠져, 남은 상품의 단가가 과대해진다.
4. **탈퇴율 7.7% 자체가 리텐션 신호** — 기존 findings 의 "재방문 0"은 "안 돌아옴"만이 아니라 "계정을 지웠다"를 포함한다. 매일 2~7명이 지운다는 건 독립적인 부정 신호로 findings 에 별도 절이 필요하다.

따라서 과거 findings(07-13/16/20/22)의 숫자는 **그 시점 스냅샷**으로 읽어야 하며, 재실행하면 탈퇴분만큼 작아진다.
