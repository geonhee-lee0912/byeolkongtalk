# 손익 스파인 통합 분석 — 설계 (2026-07-25)

## 목적

**이번 분석이 답할 질문**: 지금 별콩톡은 한 달에 얼마를 잃고 있고, 그 손실이 어디서 새며, 무엇을 고치면 얼마가 회수되는가.

기존 분석들이 "전환율·대화 품질"을 축으로 삼았던 것과 달리, 이번엔 **손익계산서를 스파인**으로 세운다. 리텐션·가성비·개선점·운영 문제는 독립 주제가 아니라 손익 항목에 붙는 가지로 다룬다. 최종 산출은 **금액이 붙은 액션 우선순위표**.

**왜 지금 "판정"이 아니라 "실체 파악"인가**: 07-20 이후 6개 변경(구조 재편·연애 상담 신설·가격 2건·웰컴 20·premium-depth·스킬 인-스레드)이 중첩돼 단일요인 A/B 인과 판정이 불가능하다. 억지로 가르지 않고 현황·손익으로 답한다.

## 블록 1 — 손익계산서 (스파인)

```
매출         payments(status='completed').amount_won
− PG 수수료   매출 × 3.7% + 월 ₩9,167
− 광고비      ad_spend 입력분 + Meta CSV 실지출(우선)
− 변동원가    Claude API: 콘솔 총액을 리딩별 점수로 배분
− 고정비      Supabase $51.98 + Vercel $20 + 도메인 + 힉스필드
= 월 순손익 / 일 번레이트
```

**원가 배분 방법** (총액은 정확, 배분만 추정):

1. 리딩별 비용 점수 = Σ턴 `(입력토큰추정 × 3 + 출력토큰추정 × 15)` — Sonnet 5 단가 비($/MTok) 그대로 가중
2. 입력토큰추정 = 페르소나(정적, 캐시 마킹 → 히트 시 0.1×) + 히스토리 + 사주/타로 컨텍스트. 출력토큰추정 = assistant 글자수 ÷ 한국어 토큰비
   - ⚠️ **종목별 컨텍스트 창이 다르다**: 사주/타로 상담은 매 턴 **전체 히스토리**를 보내므로 입력이 턴 제곱으로 커지고, 연애 상담 스레드는 **최근 24메시지 + rolling_summary**라 입력이 상한에 수렴한다. 같은 식으로 계산하면 스레드 원가를 크게 과대평가하므로 트랙을 분리한다
3. 캐시 히트율은 **가정값 3 시나리오**(0.3 / 0.6 / 0.9)로 민감도 확인 — [[prompt-cache-optimization]]이 "히트율 낮음"을 시사하므로 상품 순위가 가정에 뒤집히는지 반드시 검산
4. 점수 총합을 **콘솔 총액에 스케일링** → 절대 총액 정확
5. haiku 보조(요약·민감 2차 판정)와 운세 one-shot 리포트는 별도 점수 트랙

**파생 지표**:
- 유저당 기여마진 = ARPU − 유저당 변동원가 → **광고비를 얼마까지 감당 가능한가**
- 상품별 마진 순위표 (가격의 원 환산 − 배분 원가)
- **별 → 원 실효 환산율**: 결제 별 단가(패키지 믹스 가중) vs 무료 별(웰컴·보너스·환불) 비중 → "무료 별로 태운 원가" 정량화
- CAC vs LTV (창별·소재별)

## 블록 4 — 개선점·운영 문제 (블록 1~3에서 파생)

- **정성 정독**: 관계 스레드 15건 전수(신규 종목 첫 정독, 서브에이전트 병렬) + 07-20 이후 상담 리딩 샘플. 태깅 축은 기존 65건 정독 방식 재사용(갈증·해소·종료유형·피로) + 관계 전용(패스 미구매 지점·스킬 반응·체크인)
- **운영 현실 문제**: `error_logs` 신호 분류([[expected-log-signals]] 기준으로 정상 신호 제외), 빈 스트림·환불 실패·스킬 머니패스, 민감 오탐, 수동 운영 부채(`ad_spend.clicks` 수기·어드민 미검증 화면·`middleware`→`proxy`)
- **출력**: `[항목 / 영향(₩/월 추정) / 비용 / 근거]` 액션표 — 손익 축에 금액이 붙은 우선순위

## 병행 코드 — 페이지뷰 비콘

**가치 재정의**: Meta 픽셀이 광고 상단을 이미 커버하므로, 비콘의 실익은 ①**가입 이후 앱 내부 라우트 이탈**(현재 완전 블라인드 — 상품 선택 화면에서 몇 명이 새는지 모른다) ②오가닉·직접 유입 UV ③유저 축 조인(anon→user).

- 마이그레이션 `page_views` (anon_id, user_id nullable, path, utm_*, referrer, bot flag, created_at) + 인덱스
- `POST /api/pv` — 서버에서 httpOnly 쿠키 읽음(클라는 못 읽으니 이 구조가 필수), 봇 UA 필터, 실패 무음(제품 영향 0)
- 클라: pathname 변화 감지 → `sendBeacon`
- **anon_id ↔ user_id 브리지**: 로그인 후 요청엔 두 쿠키가 함께 실리므로 row 하나가 자연 조인 키가 된다 (현재 이 매핑은 어디에도 저장되지 않음)
- 개인정보처리방침: 자동수집·쿠키가 이미 명시돼 수정 불필요 (제8조에 "접속 페이지 기록" 한 줄 추가는 검토)
- 어드민 화면 없음 — 당분간 SQL 조회

**순서**: 비콘 데이터 없이 분석을 먼저 완주한다(사용자 지시). 비콘은 병행 구현·배포해 다음 분석부터 데이터를 쓴다.
