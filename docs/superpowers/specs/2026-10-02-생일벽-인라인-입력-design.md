# 생일 벽 인라인 입력 — 설계 (2026-10-02)

> 사주 프로필(생년월일)이 없는 유저를 `/mypage` 로 내보내던 6곳을, 그 자리에서 입력 팝업을 여는 방식으로 바꾼다.
> 사용자 확정: 범위 = 6곳 전부 · 방식 = 입력 팝업(마이페이지 팝업 재사용) · 화면 동작·구조 설계 승인(2026-10-02).

## 0. 왜 하는가

광고를 3상품(타로톡 love ₩10k 유지 + 사주 운세 ₩5k + 별마루 ₩5k)으로 넓히기 전의 전제 조건이다.

- **가입 때 생년월일을 받지 않는다** → 신규 유저는 사주 프로필이 없다(`app/api/auth` 에 생일 처리 0건).
- 아래 6곳은 프로필이 없으면 `/mypage` 링크 하나만 보여주고, `/mypage` 는 저장 후 원래 화면으로 **돌려보내지 않는다**(`SelfSajuEditModal` 은 닫히기만 함).
- 사주·별마루 광고의 착지는 1번·2번이다 → **광고로 온 신규 유저는 전원이 이 벽을 만난다.**
- 실측 근거
  - 별마루 09-28~10-02 방문 20명 중 **16명 `byeolmaru_no_profile`**(기존 유저 포함 수치).
  - 09-12: `/fortune` 열람자의 **79.9%가 결국 타로를 샀다**(대부분 타로로 먼저 온 사람이라 그대로 대입은 못 함).
- 고치지 않으면: 사주·별마루 클릭이 타로 구매로 끝나 세 광고세트가 같은 사람(타로 구매자)을 찾는 쪽으로 수렴한다. 상품 수요도 못 읽는다.

## 1. 성공 기준

1. 6곳 어디서든 생일 없는 유저가 **화면을 떠나지 않고** 생일을 입력하고, 저장 직후 그 화면에서 하려던 일을 이어간다.
2. 비로그인 방문자는 사주 상품 페이지에서 로그인한 뒤 **같은 상품 페이지로** 돌아온다.
3. 생일 있는 유저의 동작은 **불변**이다 — 단 6번("생일 등록하기")은 의도적으로 바뀐다: `/mypage` 이동 대신 같은 자리에서 "내 사주 수정" 팝업이 열린다(§3). 명식판·지인 사주는 마이 탭에서 그대로 볼 수 있다.
4. 자리별로 "팝업 열기 → 저장"을 계측으로 읽을 수 있다.

## 3. 화면 동작

**공통:** "생년월일 입력하러 가기"(이동) → **"생년월일 입력하기"**(팝업). 팝업은 마이페이지의 '내 사주 입력' 팝업과 같은 것(생년월일·시간(모름 가능)·양력/음력·성별). 이미 내 사주가 있으면 같은 팝업이 "내 사주 수정"으로 열린다(마이페이지와 동일).

|---|---|---|
| 1 | "로그인하면 바로 내 사주로 볼 수 있어." + 카카오 버튼 **"카카오로 시작하기"** → `/login?next=<상품 href>` | "생년월일만 알려주면 바로 볼 수 있어." + **"생년월일 입력하기"** |

- **1번의 두 번째 경우 — 내 사주는 있는데 생일이 없을 때**(`/relationship` 의 내 정보 '생일 몰라요' 저장으로 실제로 생긴다): 지금은 사주판 자리에 "생일을 알려주면 사주도 보여줄게" 만 뜨고 확인 버튼이 꺼져 **막다른 길**이다. 그 문구 아래에 같은 **"생년월일 입력하기"** 버튼을 둔다. 🔴 선택된 프로필이 **내 사주일 때만** — 지인 프로필에 생일이 없을 땐 문구만 그대로 둔다(지인 수정은 범위 밖, 버튼은 내 사주를 PATCH 하므로 지인에게 달면 엉뚱한 사람이 고쳐진다). Task 1 품질 리뷰가 찾은 구멍이다.
- 카카오 버튼은 저장소 컨벤션 그대로(`#FEE500` 배경 · `#3C1E1E` 글자 · 말풍선 아이콘 · `py-3.5`). 공용 부품이 없으므로 `ByeolmaruHub` 의 마크업을 따른다.
- 🔴 **1번은 저장 후 결제 확인 창을 자동으로 띄우지 않는다.** 내 사주를 골라 두기까지만 한다. "새 사람 입력"(`NewPersonModal` 의 "저장하고 선택")과 같은 동작이고, 별이 빠지는 확인 창이 갑자기 뜨는 것을 막는다.
- 🔴 **3·4·5번은 새로 불러온다**(`window.location.reload()`). `DayTabsView` 가 캘린더 응답을 한 번 받아 세 탭에 나눠 준다(`injected`). 한 탭만 갱신하면 열려 있거나 나중에 여는 탭이 그 낡은 404 를 받아 "생일 없음"으로 남는다.
- 🔴 **1번은 로그인을 먼저 받는다.** 생일을 먼저 받으면 로그인 왕복 동안 값을 보관할 장치가 따로 필요하다. 별마루 첫 화면과 같은 순서다.

## 4. 구조

### 4-1. `BirthPromptButton` (신설, `components/saju/BirthPromptButton.tsx`, client)

| prop | 필수 | 뜻 |
|---|---|---|
| `surface` | ✅ | 자리 값(4-4). 계측 meta 로만 쓴다 |
| `className` | ✅ | 자리마다 모양이 달라 그대로 받는다 |
| `children` | ✅ | 버튼 글자(6번의 `→` span 포함 가능) |
| `onSaved` | ✅ | 저장 성공 후 그 자리 갱신 |
| `onClick` |  | 기존 계측 유지용(2번의 `byeolmaru_guest_peek_clicked{card:"profile_cta",gated:true}`) |
| `loginNext` |  | 비로그인일 때 돌아올 곳. 기본값 = 현재 `pathname + search` |

누르면:
1. `onClick?.()` → `birth_prompt_clicked{surface}` → 조회 중 버튼 비활성(중복 클릭 방지).
2. `/api/auth/me` 와 `/api/profiles` 를 **동시에** 조회.
3. 비로그인 → `window.location.href = "/login?next=" + encodeURIComponent(loginNext ?? 현재 경로)`. 팝업 없음.
4. 로그인 → `self = profiles.find(isPrimary) ?? null`, 닉네임 = `me.user.nickname` → `SelfSajuEditModal` 을 연다.
5. 저장 성공(`onReload`) → `birth_prompt_saved{surface, created: self === null, hadBirth: Boolean(self?.birthDate)}` → `await onSaved()` → 팝업 닫힘.

- `SelfSajuEditModal` 은 `self` 가 있으면 PATCH, 없으면 POST 한다 → 별마루 404 의 두 원인(primary 없음 / primary 는 있는데 생일 없음)을 모두 덮는다.
- 조회 실패(네트워크·5xx) → `self=null` 로 팝업을 연다(4-3 오류 처리로 이어짐).

### 4-2. 사주 상품 페이지(1번)의 판단 함수 (신설, `components/fortune/picker-gate.ts` + 테스트)

```ts
export type PickerGate = "login" | "birth" | "list";
export function pickerGate(input: {
  profiles: readonly { isPrimary: boolean }[];
  lockPrimary: boolean;
  authenticated: boolean;
}): PickerGate;
```

- `needsSelf = (lockPrimary && 내 사주 없음) || profiles.length === 0` — **지금 벽 조건과 같은 식**이다.
- `needsSelf` 가 아니면 `"list"`(지금 화면 그대로), 맞으면 `authenticated ? "birth" : "login"`.
- 테스트 6분기: ①비로그인(프로필 0) → `login` ②로그인·프로필 0 → `birth` ③로그인·`lockPrimary`·지인만 있음 → `birth` ④내 사주 있음 → `list`(로그인 여부와도 무관 — 아래 탐침이 기대는 계약) ⑤로그인·`lockPrimary` 아님·지인만 있음 → `list`(지금처럼 목록에서 고르거나 새 사람 입력) ⑥내 사주는 있는데 생일 없음 → `list`(벽 아님).
- 로그인 확인(`/api/auth/me`)이 실패하면 **로그인한 것으로 본다**(`isAuthenticated !== false`) → `birth` 가 뜨고, 버튼을 누를 때 `BirthPromptButton` 이 다시 확인한다. 4-1 의 버튼과 같은 정책이다(실패 시 막으면 일시 장애 때 로그인한 유저에게 카카오 버튼이 뜬다).
- `GET /api/profiles` 는 비로그인에게도 `200 {profiles:[]}` 를 줘서 로그인 여부를 못 가른다 → **`needsSelf` 일 때만** `/api/auth/me` 를 추가로 부른다(프로필 있는 유저는 요청이 늘지 않는다).
- 프로필 조회를 함수로 떼어 마운트와 `onSaved` 가 같이 쓴다(저장 후 재조회 → `isPrimary` 를 자동 선택하는 기존 로직이 그대로 돈다).
- 선택된 프로필이 `isPrimary && !birthDate` 면 사주판 자리 문구 아래에 `BirthPromptButton`(같은 surface, `onSaved = loadProfiles`). 🔴 게이트 함수는 바꾸지 않는다 — 이 유저도 지인 프로필로는 계속 볼 수 있어야 해서 이 상태를 벽(`birth`)으로 막지 않는다.
- `FortunePurchasePanel` 이 `loginNext={cfg.href}` 를 넘긴다(prop 이 없으면 현재 경로). 🔴 `cfg.type` 으로 경로를 조립하지 말 것 — `compat_social` 의 href 는 하이픈(`/fortune/compat-social`)이라 404 가 난다(추천 게이트웨이 A 의 실사고).

### 4-3. 오류 처리

- `SelfSajuEditModal` 은 지금 저장 실패 시 **아무 말이 없고** 네트워크 예외는 잡지도 않는다 → 오류 줄을 넣는다. 문구는 `NewPersonModal` 과 같다: 응답 실패 "저장을 못 했어. 잠시 후 다시 시도해줄래?" / 예외 "연결이 잠시 흔들렸어. 다시 시도해줄래?". **마이페이지도 같이 좋아지는 변경**이다(인터페이스 불변).
- 401·409 는 "잠시 후 다시"로 안 풀린다(다시 눌러도 같은 요청 반복) → 문구를 가른다: 401 "로그인이 풀렸어. 다시 로그인해줄래?" / 409 "이미 저장된 사주가 있어. 새로고침하고 다시 열어줄래?"(409 의 흔한 경로 = POST 는 커밋됐는데 응답이 모바일망에서 유실. 새로고침·재열기 시 재조회해서 PATCH 로 열린다).
- 오류 줄은 저장 버튼 아래라 짧은 화면(높이 ~600px 미만)에선 가려진다 → 뜰 때 `scrollIntoView({block:"nearest"})` + `role="alert"`(Task 3 품질 리뷰 실측).
- 저장 뒤 새로고침하는 자리(3·4·5)는 `reloadAfterSave`(끝나지 않는 promise)를 넘겨, 새로고침이 끝날 때까지 팝업이 "별콩이가 펼치는 중…"으로 남게 한다 — 즉시 반환하면 닫힌 팝업 뒤로 낡은 벽이 비친다.

## 5. 계측

- `UI_EVENTS` 에 2종 추가(마이그레이션 불필요 — allowlist 만 늘린다).
  - `birth_prompt_clicked` — meta `{surface}`. 버튼을 누른 횟수(비로그인으로 로그인에 보낸 경우 포함 — 그 몫은 `user_id IS NULL` 로 대략 가른다). 🔴 저장소 관행상 `_opened` 는 "실제로 열렸다"(`recharge_sheet_opened`)라 탭 이벤트는 `_clicked` 다(Task 1 품질 리뷰 반영).
  - `birth_prompt_saved` — meta `{surface, created, hadBirth}`. 저장 성공. `created` = 새 primary 행 생성(POST) 여부, `hadBirth` = 열 때 내 사주에 생일이 이미 있었나.
- 🔴 **신규 생일 입력은 `hadBirth=false` 로 센다.** `created` 로 세면 "primary 는 있는데 생일 없음"의 첫 입력이 PATCH 라 빠진다 — 이 상태는 실제로 생긴다(`/relationship` 의 내 정보 '생일 몰라요' 저장 → `app/api/relationship/route.ts` `optionalBirth:true`). `created`(POST 여부)는 신규 입력을 "내 사주 없음"과 "생일 없는 내 사주"로 가른다 — fortune_picker 에선 벽 버튼(true)과 목록 안 버튼(false)을 가르는 유일한 값이다. `saved` 는 저장 성공 때만 찍혀 409 는 여기 안 보인다.
- 둘 다 **클릭 핸들러에서** 쏜다 → dev StrictMode 의 이중 발화(이펙트 전용)를 타지 않는다.
- 기존 이벤트는 그대로 둔다: `byeolmaru_no_profile`(벽 노출) · `byeolmaru_guest_peek_clicked{card:"profile_cta"}`(허브 CTA 클릭). 판독 = 자리별 `clicked` → `saved`. 🔴 `byeolmaru_no_profile`(벽 노출)은 **surface 를 싣지 않아** 허브·날짜 탭을 가를 수 없고, 날짜 상세에선 열린 탭마다 한 번씩 찍힌다 — 별마루 전체의 분모로만 쓸 것(자리별 분모가 필요하면 meta 추가는 별도 결정, Task 6~8 품질 리뷰).
- 6번은 생일 있는 유저도 "수정"하려고 누른다 → 그 자리의 클릭→저장은 생일 벽 전환율이 아니다(신규 입력은 `hadBirth=false` 만).

   - 비로그인: `/fortune/love_self` 맨 아래 카카오 버튼 href = `/login?next=%2Ffortune%2Flove_self` · `/fortune` 헤더 "생일 등록하기" → `/login?next=%2Ffortune`.
   - **생일 없는 dev 테스트 계정**(새로 만든다 — 기존 QA 봇의 프로필을 지우면 거기 묶인 별마루 데이터가 다칠 수 있다): 6곳 모두 팝업 → 저장 → §2 의 "저장 후" 대로 갱신 · `user_profiles` primary 1행(중복 없음) · `ui_events` 에 자리별 `clicked`/`saved`.
   - **"primary 는 있는데 생일 없음" 상태**: 1번 자리(선택된 내 사주 아래 입력 버튼)와 2번 자리(404 → 팝업)가 PATCH 로 저장되고 `saved` 가 `created:false · hadBirth:false` 로 찍히는지.
   - 생일 있는 계정: 6곳 회귀 없음(1번 목록 정상 · 6번은 "내 사주 수정" · 별마루 벽 미노출).
   - 오류 줄: 저장 요청을 실패시켜(브라우저에서 fetch 가로채기) 문구가 뜨는지.
4. 검증 끝나면 dev 테스트 계정·프로필 정리.

## 7. 범위 밖

- 가입할 때 생년월일 받기 — 생일이 필요 없는 타로 동선에 단계가 늘어난다.
- 저장 후 결제 확인 자동으로 띄우기(§3 결정).
- `/start` 이외 착지에서 웰컴 별 팝업 띄우기.
- 카카오 버튼 공용 부품화 — 지금 6곳이 같은 마크업을 각자 갖고 있는 기존 상태를 건드리지 않는다.

## 8. 배포

dev 까지만. **prod 반영은 사용자가 따로 지시할 때.** 사주·별마루 광고 집행은 이 변경이 prod 에 나간 뒤여야 의미가 있다 — 광고 시작일은 배포일에 맞춘다.
